星野ロミ思想で、会場モードのバグの直し方を決めたい。

## 症状(実機・ユーザー却下)
会場モードの席に、popup 応援レーンの「りんく段」(数値ユーザーID+個人サムネ持ちの常連=みやび/ぺけた/あひろ/kota/ねこまる/すぎ 等の実顔)が【1人も出ず】、匿名(a: 形式)のゆっくり顔(緑/紫/赤)だけが大量に並ぶ。popup レーンには りんく段の実顔が正しく7人出ているのに、会場には出ない。「ぜんぜんだめ」。

## 真因(実コードで特定済み)
共有関数 src/lib/storyUserLaneCandidates.js:97 の安全ルール:
```
if (!broadcasterUid && !ownPostedForUid && /^\d{5,14}$/.test(uidRaw)) continue;
```
=「配信者ID(broadcasterUid)が未確定なら、数値ユーザーIDの人を全員スキップ(匿名段に倒す)」。意図は『配信者ID未確定で数値IDを出すと配信者本人を誤って常連扱いするのを防ぐ』安全策。

- popup は broadcasterUid を【2経路】で解決: ①storage の watch snapshot ②inferBroadcasterUserIdFromComments(コメントの表示名から配信者本人 uid を推定)。だから broadcasterUid が埋まり、97 をすり抜けて数値IDの常連が出る。
- 会場(venueBar.js)は broadcasterUid を【storage の broadcaster ctx だけ】で解決(_bcUidForExclude)。この配信(みあ・lv350808680)は watchSnapshotMeta=null で broadcaster ctx が空=会場の broadcasterUid が空。→ 97 が誤発火し、数値IDの常連(りんく段)が全員スキップ=会場が匿名だらけになる。

## 確認できた事実
- inferBroadcasterUserIdFromComments(src/lib/inferBroadcasterUserIdFromComments.js)は純関数。入力=(entries, snapshot{broadcasterUserId/broadcasterPageUrl/broadcasterName})。snapshot に配信者名/ページURL/IDが無いと、entries(コメント)の表示名と配信者名の一致で推定する=配信者名が要る。
- 会場の集約候補(aggList=userLaneCandidatesFromStorage の戻り)は userId/nickname/avatarUrl/commentCount 等を持つが、配信者名や生コメント本文は持たない可能性が高い。会場の broadcaster ctx(KEY_LIVE_BROADCASTER_CTX)は uid/iconUrl/liveId を持つが broadcasterName/PageUrl は不明。
- 97 の安全ルールの本来の目的=配信者本人(1人)が常連列に紛れるのを防ぐ。だが副作用で『配信者ID未確定の配信では数値IDの常連が全員消える』。

## 選択肢(ユーザーは星野ロミ会議で決めたいと)
A. popup と同じ inferBroadcasterUserIdFromComments を会場でも使う(2経路に揃える)。ただし会場に配信者名/コメント本文が無いと推定が効かない=この配信では救えない可能性。
B. 「配信者ID未確定なら数値IDを隠す」を会場では緩める=未確定でも数値IDの常連を出す。配信者本人が1人混じるリスクより、常連が全員消える方が実害大(会場は見せる場)。popup より緩い基準。
C. 両方(推定を足しつつ、なお未確定なら会場では出す)。

## 問いたいこと(星野ロミ思想=動いてるものを活かす・てこの原理・最小実装・過剰実装しない)
1. 星野ロミならどれを採るか。会場は『見せる場』、popup は『確認用』という役割差を踏まえて。
2. 97 の安全ルールを会場でだけ緩めるとして、配信者本人の混入をどう最小化するか(broadcasterUid が取れた時だけ本人除外は効かせる、等)。共有純関数 buildStoryUserLaneCandidates にどんな引数を足すのが最小か(例: allowNumericWhenBroadcasterUnknown フラグ)。popup の挙動は1mm 変えない(既定 false=従来)。
3. この設計の穴。配信者本人が会場席に常連として出てしまうケースの実害と、その許容可否。
4. 会場で inferBroadcasterUserIdFromComments を活かす余地(配信者名が storage のどこかに有るか・無ければ B/C に倒すか)。

簡潔に。最小ブラスト半径で。推測で不可能なこと(無い情報の捏造)を提案しない。
