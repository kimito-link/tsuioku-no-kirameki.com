# お題: まずChrome拡張版を「ユーザー最優先」で完璧に仕上げる（スマホ化は将来の制約として頭に置くだけ）

## 優先順位（最重要）
**今回のメインの狙いはChrome拡張版そのものの完成度を上げること。**
スマホ化は「今すぐ着手する話」ではなく、「将来やるとしても手戻りが少なくなるよう、
Chrome版の設計を無駄に歪めない」程度の軽い制約として扱ってほしい。
議論の9割はChrome版のユーザー体験・情報設計・品質に使うこと。
スマホ移植の具体設計(PWA化・ネイティブ化の詳細)は今回のスコープ外。

**体験の質感として「ゲームセンターの太鼓の達人・カラオケ採点みたいに楽しくしたい」**
(ユーザーが「パチンコみたいに」と言った後、「太鼓の達人・カラオケ採点」と具体化して言い換えた)。
狙いは2段構え:
1. **プレイ中(配信視聴中)の楽しさ** = 太鼓の達人のような、リアルタイムのノリ・テンポ・
   コンボ感・演出の畳み掛け。ギフト/コメント/イベントに合わせて気持ちよく盛り上がる体験。
2. **終わった後(配信終了後)の楽しさ** = カラオケ採点のような、結果画面での得点表示・
   評価・振り返り。既存の「配信スコアパネル」構想はまさにこの2番目に該当する。
ギャンブル・射幸心・課金ガチャ的な要素は一切含まない(ゲームセンターのアーケードゲーム的な
「上手にできた/盛り上がった」達成感がモデル)。念のため誤解防止のため明記する。

## 背景
「つみき-no-kirameki」は現在 Chrome 拡張機能(Manifest V3)として実装されている。
構成は主に以下:
- ①POP(embed_watch): 配信中に開くポップアップ。応援レーン・ランキング・ギフト演出・診断など主機能が集中
- ②プレビュー: ①の内容をミラーして表示する別窓
- ③WEB: ①と同等の内容をブラウザだけで見られる公開ページ
- ④会場モード: 座席型の一覧表示(全員表示・満席判定などを含む)
- 配信スコアパネル: カラオケ採点/太鼓の達人風の新機能(実装途中・popup.html配線待ち)
- 診断層: パリティ診断・ギフト演出診断・状態速報CLIなど多数

これまでの開発は「バグ修正」「ちらつき対策」「3画面パリティ」を積み重ねてきたが、
**そもそもの情報設計・UI設計を、ユーザー体験最優先の視点でゼロから見直したことはない**。
まずはこのChrome拡張版そのものを「配信を見にきた一般ユーザーにとって最高の体験」に
仕上げることが最優先。スマホ化は今回のスコープ外だが、Chrome版の設計判断で
「後でスマホに移すときに無駄に壊れる」ような選択(例: Chrome固有APIへの不必要な密結合)は
避けたい、という程度の軽い配慮に留める。

## 問いたいこと(会議で発散・批判・具体化してほしい)

1. **ユーザー最優先の設計とは何か**
   - 現状の①②③④+スコアパネルの情報量・操作導線は、実際の配信視聴ユーザーにとって
     「見たい情報がすぐ分かる」構造になっているか？ 過剰な診断・玄人向け機能が
     一般ユーザーの体験を圧迫していないか？
   - 「配信を楽しく応援する」という原体験に対して、今の機能群は何を足し引きすべきか？

1.5. **「太鼓の達人・カラオケ採点みたいに楽しく」を実装するには**
   - **プレイ中の楽しさ**: 既存のギフト投擲演出・効果音・カウントアップ演出は既にある程度
     この方向だが、何が足りないから物足りないのか？(演出の緩急・畳み掛け方・音との同期・
     テンポ感・コンボ的な積み重ね感など)。配信のどのイベント(コメント数マイルストーン・
     ギフト・順位変動)に、どういうリアルタイム演出をマッピングするのが自然か？
   - **終わった後の楽しさ**: 既存の「配信スコアパネル(カラオケ採点/太鼓の達人風)」構想を
     どう仕上げれば「見終わった後も楽しい」結果画面になるか？ カラオケ採点の何が
     気持ちいいのか(点数の内訳表示・ランク演出・カウントアップ・コメントでの講評等)を
     分解し、配信の文脈にどう翻訳するか？
   - この2つ(プレイ中演出 / 終了後スコアパネル)は別レイヤーとして両方実装すべきか、
     どちらかを優先すべきか？
   - 演出過多で逆に鬱陶しくならないための歯止め(頻度・on/off設定・控えめモード等)は何か？

2. **（軽い制約として）将来スマホ化するとしたら壊れやすい選択は何か**
   - 深追いはしなくてよい。ただしChrome版の設計判断の中で「これはChrome固有APIに
     不必要に密結合していて、将来スマホに移す際に丸ごと作り直しになりそうな箇所」があれば
     一言指摘してほしい程度でよい。これを理由にChrome版の実装を複雑化・抽象化しすぎるのは
     本末転倒なので推奨しない。

3. **根本療法として優先すべき順序（Chrome版内で）**
   - Chrome版のユーザー体験を最優先で仕上げるとき、着手すべき順序は？
   - 今すぐ直すべき部分と、後回しでよい部分の切り分け。
   - 既存の複雑な診断層(パリティ診断・ちらつき対策のdiff-skip機構など)を
     壊さずに、UI再設計を進める安全な進め方は？

## 地雷マップ(過去に踏んだ失敗・却下した案・触ると危険な箇所)

- **ちらつき/churn対策のdiff-skip機構は繊細**: 応援レーンのちらつき問題は7版(v1037〜v1042)
  かけて解消した。真犯人は「消す/空にする側」(empty-guides・reset・gift-ad毎pollリセット)に
  計器もdiff-skipも無かったこと。UI再設計でレーン描画に触るなら、この教訓を踏まえ
  「消去経路」を必ず洗うこと。参考: `story-userlane-churn-filllanetier-v1039`
- **会場=応援レーン=別窓は「見た目も完全に同じ」であるべき、とユーザーが確定済み**。
  ひな壇レイアウトは廃止し、レーン段組みDOMに統一する方針が既に決まっている。
  スマホ化検討でも、この既定方針を覆す提案は理由を明記すること。
  参考: `venue-equals-lane-same-layout`
- **3画面パリティ(①=②=③)の「✅」は行数/ack突合だけでは不十分**と判明済み。
  実際のstat-card実数値まで突合しないと嘘の緑になる。UI再設計で新しい画面/鏡を
  増やすなら、この教訓(値そのものを突合)を踏襲すること。
  参考: `parity-check-must-compare-values-not-just-ack`
- **鏡(mirror)はキーごと・tickごとに別々に書かれるため、同一tickでの一貫性が無い**のが
  数字ズレ/嘘の緑の構造的真因。スマホ化で同期方式を変えるなら、この構造的欠陥を
  引き継がない設計にすること。参考: `mirrors-written-per-key-per-tick-root-of-parity-lie`
- **限界値(48枠等)を増やすときは、対応する鏡capも同時に追随させる**必要がある
  (v1051で全員表示limitを200にした直後、鏡capが据え置きで①211≠③99の不一致が発生、v1052で追随)。
  UI再設計で表示件数の考え方を変えるなら、鏡層とセットで見ること。
  参考: `lane-limit-200-mirror-cap-parity-v1051-1052`
- **スマホ化は今回スコープ外**。過去に会議・設計を行った記録も無い。今回は深追いせず、
  Chrome版の設計を歪めてまで先取りしないこと。
