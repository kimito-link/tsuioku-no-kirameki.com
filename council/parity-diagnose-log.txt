#### 結論  
「3画面パリティ合格」の判定式は現状の既存指標で構築困難。特に②③の描画確認がstorage経由で不可能であり、新計測が不可避。既存設計の制約に矛盾が生じる。

#### 根拠  
1. **描画確認の技術的制約**  
   - ②応援プレビュー・③WEBプレビューの描画プローブ（render probe）は、別タブ/別ドメインで実行されるため、status.htmlから直接観測不可。  
   - 現行の`storyUserLaneRenderProbe`や`northStarRenderProbe`は、Chrome拡張のメインプロセス内にデータを保存せず、storage経由での公開も設計されていない。  

2. **既存指標の不十分性**  
   - 鏡の整合チェック（apiRows vs 鏡件数）はデータ同期の有無を示すが、描画の「完全性」（例: スクロール白化）を含めない。  
   - perfDiag.jsのpaintMsや白化検知は、描画成功の「証拠」ではなく「副作用」に過ぎず、逆算して判定できない。  

3. **保留状態の明確化不足**  
   - 未publish（e）やwatchタブなし（診断信頼性メタ）の「保留」条件を、既存指標が明示的に管理していない。例: WEBプレビューのpublish未実行時に「一致」と誤判定するリスク。  

#### 反論・リスク  
- **「storageにrender probeを書き戻す」提案の反論**:  
  設計文書のRole-Separation-Design §6に明記された

## 総合・統括による一貫案：【パリティ診断エンジン】設計提案

現状の課題は、「複数の場所（①②③）での描画状態が一致しているか」という**総合的な合否判定ロジック**と、その**原因特定フローチャート**の欠如です。既存指標を「観測結果」として再構成し、単なるデータ羅列から「診断レポート」へと昇華させることが最重要となります。

### 結論：パリティ合格のための「三層構造の統合判定ロジック」と「優先度決定木」の導入

「同一で完全であること」を証明するには、**「①②③がすべて最新かつ描画されている（＝観測可能）」という前提条件を満たし、さらにそのデータに矛盾がないこと**が必要です。これを単一の判定ロジックとしてまとめます。新規計測は最小限にとどめ、既存指標の解釈レイヤーを刷新します。

### 根拠：現状の課題構造と設計方針

1. **「同一で完全」の定義の明確化:**
    * 「同一で完全」 $\iff$ (①が描画) AND (②が描画) AND (③が描画) AND ($\text{Data}_1 = \text{Data}_2 = \text{Data}_3$)。
2. **観測レイヤーの統合:** 既存指標はそれぞれ「データ存在」「描画起動」「パフォーマンス」という側面をしかけています。これらを「**パリティ合格判定エンジン**」として統合し、どの条件が満たされていないかをスコアリングする構造が必要です。
3. **誤検知リスクへの対応（重要）：** 「保留(判定不能)」状態を最上位のロジックに組み込むことで、鮮度やロード状況による「×」判定の誤りを防ぎます。

### 🔴 詳細な設計案（4ブロック）

#### 1. 「3画面パリティ合格」の判定式 (The Core Logic)

**✅ 合格条件 $\iff$ (A) AND (B) AND (C)**

*   **(A) データ存在性チェック (Data Presence):**
    *   `apiRows` の貢献度（例: 10）が、①, ②, ③のデータソース全てで同等に観測されていること。（最も基本的な一致点）
    *   $\text{Status}_{\text{data\_match}} = \text{TRUE}$

*   **(B) 描画実行性チェック (Render Execution):**
    *   ①（POP）：`renderProbe.started` が真であり、かつ $\text{PaintMs} > 0$ であること。
    *   ②（応援）：$\text{storage}_{\text{user\_lane}}$ からの読み取りが成功し、かつ描画完了を示す専用フラグ（後述）がセットされていること。
    *   ③（WEB）：`liveviewPublishSelfDiag.js` が示す「最新送信済み」ステータスと $\text{renderProbe}$ の整合性が取れており、**未送信による古い値の誤判定がない**こと。
    *   $\text{Status}_{\text{render\_active}} = \text{TRUE}$

*   **(C) タイムスタンプ/鮮度チェック (Freshness & Consistency):**
    *   全ての観測値（データ、プロブ、パッチ）が、同一のセッション内での最終更新時刻 $\Delta T$ の許容範囲内にあること。特に③（WEB）の場合は、`publish` 実行からの経過時間が短すぎないことを確認するメタ情報が必要。
    *   $\text{Status}_{\text{fresh\_sync}} = \text{TRUE}$

**💡 総合判定：** 上記A, B, Cが全て $\text{TRUE}$ であり、「保留フラグ」も立っていない場合にのみ「合格 (✅)」とする。

#### 2. ×のときの原因切り分けを一意にする決定木 (The Diagnostic Flowchart)

最上位の判定（総合パリティ判定）で「×」が出た場合、以下の優先順位で診断を強制的に実行させます。

1. **[P0] データ不一致/欠損:** $\text{Status}_{\text{data\_match}} = \text{FALSE}$
    *   **原因特定:** どの鏡（①, ②, ③）と、生データAPI ($\text{apiRows}$) の値が乖離しているかを具体的に指摘。（例: 「②の貢献度が10に対し、③は4に留まっている」） $\rightarrow$ **(b)のパターン**
2. **[P1] 描画未起動/失敗:** $\text{Status}_{\text{render\_active}} = \text{FALSE}$
    *   **原因特定:** プロブが全て0、またはパフォーマンス指標（$\text{perfDiag}$）に異常な白化パターンが見られる場合。→ **(a)のパターン** (描画トリガーの問題)
3. **[P2] 鮮度/同期問題:** $\text{Status}_{\text{fresh\_sync}} = \text{FALSE}$
    *   **原因特定:** ①と②は最新だが、③が古い値（未Publish）を参照している場合。→ **(e)のパターン** (WEB側の遅延) または単なるリロード前の状態 $\rightarrow$ **(d)のパターン**

**【補足】** これにより、複数の問題が同時に発生しても、最も根源的で影響度の高い原因（P0 > P1 > P2）から順に切り分けが可能になります。

#### 3. 既存指標の最小組み合わせと信頼条件 (Minimal Set & Guardrails)

| 判定軸 | 使用するコア指標 | 役割/目的 | 必須の信頼条件（ガードレール） |
| :--- | :--- | :--- | :--- |
| **データ整合性** | `apiRows` vs. ③の公開値 (Storage経由) | データ源の一致確認。 | $\text{watch}$ タブが有効であること。（手動確認を前提とする） |
| **描画実行度** | ①/②/③それぞれの $\text{renderProbe}$ / $\text{paintMs}$ | 実際にUI層に処理が到達したか。 | $\text{refreshAllStarted}$ が真であること。（リロードのトリガー確認） |
| **鮮度管理** | `liveviewPublishSelfDiag` のタイムスタンプ | WEB側の最新状態を保証する。 | この指標の値が、他の①②の観測値と時間差が許容範囲内であるか。 |

*   **新規計測の最小化:** 描画実行性（B）の確認に特化した「**各ビューからの自己報告フラグ**」の導入のみを検討します。（後述の⑤参照）。これを追加しない場合、②と③は「観測可能かどうか」の判定が困難になります。

#### 4. 総合パリティ判定の文言設計 (The Single Line Verdict)

状態速報の最上部に固定表示するサマリー行として、以下の構造を採用します。

**`[総合パリティ]: ✅合格 / 🟡保留(△△要確認) / 🔴不一致(原因: [P#] - [具体的な乖離点])`**

## 結論
「3画面パリティ合格」の判定式は、①②③それぞれの「描けている」を観測し、次の条件を満たす場合に ✅同一で完全 と言える。
- 各鏡の有無と鮮度が一致する。
- 整合チェックが正常である。
- 描画 probe が正常に起動している。
- パフォーマンス診断が正常である。

## 根拠
既存の指標を使用して、次の観測値を取得する。
- 状態速報の各鏡の有無と鮮度。
- 整合チェックの結果。
- 描画 probe の結果。
- パフォーマンス診断の結果。
これらの観測値を組み合わせて、3 画面のパリティを判定する。

## 反論・リスク
- ②③が実際に描けているかを status から知る方法がない。
- 誤検知を出さない設計が必要である。
- 画面の描画パスにキャッシュを足さない・丸ごとコピーしない・記録の心臓部に集計を足さないという制約がある。

## 具体案
1. 「3画面パリティ合格」の判定式: 
   - 各鏡の有無と鮮度が一致する。
   - 整合チェックが正常である。
   - 描画 probe が正常に起動している。
   - パフォーマンス診断が正常である。
2. ×のときの原因切り分けを一意にする決定木: 
   - a: データはあるのに描画 probe が 0 の場合。
   - b: 鏡が空または古い場合。
   - c: スクロールで白化する場合。
   - d: 新コード未ロードの場合。
   - e: WEB が publish 押下後しか更新されない場合。
3. 既存指標の最小の組み合わせで作れるか: 
   - 状態速報の各鏡の有無と鮮度。
   - 整合チェックの結果。
   - 描画 probe の結果。
   - パフォーマンス診断の結果。
4. 状態速報の先頭に出す「総合パリティ判定」1行の文言設計: 
   - ✅: 3 画面が同一で完全である。
   - 🟡: 保留(判定不能)。
   - 🔴: 3 画面が同一で完全ではない。
5. ②③が実際に描けているかを status から知る方法: 
   - ②③側が自分の描画結果を storage に書き戻して status が読む案。
6. 誤検知を出さない設計: 
   - 鮮度差/未ロード/未 publish を ×と誤判定しない。
   - 「保留(判定不能)」を明示的な状態として持つ。

**結論**  
> 「① POP、② 応援プレビュー、③ WEBプレビューが **同一で完全**」であるかを、**1 行の総合パリティ判定**と **決定木‑ベースの原因切り分け**で示す診断を実装すれば、運営者は「○/×/🟡」を即座に読め、× のときは唯一の原因を瞬時に特定できる。  
> 既存指標だけで **最小化** した構成にし、**保留** 状態（未ロード・未publish・watch なし）を明示的に扱うことで誤検知を根絶する。

## 根拠  

| 目的 | 必要な観測項目 | 既存指標で取得できるか | 補足・信頼条件 |
|------|----------------|------------------------|----------------|
| **① POP が描画できている** | `popupRenderProbe.started` が `true` かつ `popupRenderProbe.finished` が `true` | `src/lib/diagnosticsTrust.js` の `popupProbe` | POP は拡張内部なので常に取得可能。watch が無くても即時判定可。 |
| **② 応援プレビューが描画できている** | `passiveViewRenderProbe.started` / `finished` が `true` **かつ** `storage.mirror.2` が **最新**（`lastUpdate >= now - Tfresh`） | `render probe` は `storyUserLaneRenderProbe.js` にあり、**同一タブ** からは取得不可 → **追加**: `passiveView` が描画完了時に `chrome.storage.local.set({preview2Ready:true, preview2Ts:Date.now()})` だけを書き込む（観測のみ）。 | ① と同様に watch が無くても OK。`Tfresh` は 30 s くらいに設定し、古い鏡は “保留”。 |
| **③ WEBプレビューが描画できている** | `webViewRenderProbe.started` / `finished` が `true` **かつ** `storage.mirror.3` が **最新** | `liveviewPublishSelfDiag.js` が `publishStatus` と `lastPublishTs` を保持。`publishStatus === "published"` かつ `lastPublishTs >= now - Tfresh` で OK。 | WEB は「publish」ボタンが押されるまで更新されないので、未publish 時は **保留**。 |
| **データ整合性** | `apiRows.count === mirror.count`（3 つすべて） | `diagnosticsTrust.js` の `integrityCheck` が提供。 | `apiRows` が取得できない場合は **保留**。 |
| **パフォーマンス基準** | `perfDiag.paintMs < Pmax` かつ `perfDiag.whiteout === false` | `perfDiag.js` が提供。 | しきい値は実測で調整。遅延が大きいだけで **×** にはしない（情報提供だけ）。 |

**判定式（簡易化）**  

```
PARITY_OK =
  POP_ready
  && PREVIEW2_ready
  && WEB_ready
  && DATA_integrity
  && (perfDiag.paintMs <= Pmax)   // optional, only for warning
```

- いずれかが **取得不能**（例: watch が無い、未publish） → `PARITY_PENDING`.
- いずれかが **false** → `PARITY_FAIL`.

## 反論・リスク（既存回答への批判）  

### 1. local/gemma4:latest の案  
* **危うい点**：**「総合判定ロジックはスコアリング」** とだけ書き、**具体的な観測項目の取得手段** を示していない。特に ②・③ の「描画起動」を status から直接読めない問題を **回避策なし** で放置している点は致命的です。  
* **見落とし**：`watch` が無い状態で `render probe` が取得できないケース（拡張がバックグラウンドで起動していない）を **保留** として扱うロジックが欠如しています。結果、未ロード時に **偽陽性（×）** が頻発します。

### 2. groq/llama‑3.3‑70b の案  
* **危うい点**：**「既存指標だけで」** と書きながら、**②・③ の描画可否を測る手段を「追加しない」** と宣言。実際には **何も観測できない** ため、判定は常に **保留** になるか、**誤検知** が起きます。  
* **見落とし**：**「鏡が空 or 別配信」** のケースで `mirror.count===0` だけを見て「×」にするのは、**古い鏡が残っている**（更新遅延）場合に **誤判定** します。鮮度チェックが必要です。

## 具体案  

### 1. 「3画面パリティ合格」の判定式  

| 観測項目 | 条件 | 取得元 | 判定ロジック |
|----------|------|--------|--------------|
| POP 描画 | `popupProbe.finished === true` | `diagnosticsTrust.js` | 必須 |
| 応援プレビュー描画 | `preview2Ready === true && preview2Ts ≥ now‑Tfresh` | `chrome.storage.local`（← **追加**） | 必須 |
| WEB 描画 | `webReady === true && webTs ≥ now‑Tfresh && publishStatus==="published"` | `liveviewPublishSelfDiag.js` | 必須 |
| データ整合 | `apiRows.total === mirror.total && apiRows.liveId === mirror.liveId` | `diagnosticsTrust.js` | 必須 |
| 鏡鮮度 | `mirror.lastUpdate ≥ now‑Tfresh`（全 3 鏡） | `diagnosticsTrust.js` | **保留** 判定に使用 |
| パフォーマンス | `perfDiag.paintMs ≤ Pmax && !perfDiag.whiteout` | `perfDiag.js` | **警告**（🟡）のみ |

**判定フロー**  

```
if (any required metric missing) → PARITY_PENDING (🟡)
else if (all required true)      → PARITY_OK (✅)
else                               → PARITY_FAIL (🔴)
```
