# お題: エラーパターンを機能マップに常時記録し「症状→経路→過去の真因」を引けるカタログを作る

## ユーザーの発想（採用済み・これを実現する）
「エラーパターンをマインドマップに常に記録されればかなりよくなのでは？」

毎回、司令塔(AI)が状態速報を貼られるたびに「この state は何のコードのどの経路が原因か」を
手で辿っている。それをマップ側に蓄積すれば、次は一目で「この症状＝この経路＝過去の真因」と分かる。
ユーザーも私も原因の当たりが即つく。

## 確定方針（ユーザー選択済み・前提）
1. 記録源 = **両方**:
   - (自動) 状態速報の診断 JSON(fastDiag)の症状を機械検出
     例: 北極星レーンの `iframe_unrendered` / `fetch_error` / `event_present_unscrapable`、
         `romiDebug.backfill.rows:0 && running:true`(進まない)、`giftSubAppDiag.failureReason` など。
   - (履歴) 過去の修正履歴(changelog / memory の reference)と紐づけ
     例: 「backfill rows:0 が裏タブで続く」→ 既知制約(裏タブ backfill は前面のみ・session_2026-06-10)。
2. 読み手 = **まず AI**。次に状態速報を貼られたとき、私が質問せず
   「この症状=この経路=過去の真因/既知制約」と即答できるようにする（開発者向けドキュメント）。

## いま現に困っている実例（最初のパターン登録候補）
状態速報(2026-06-16 22:08)で「ぜんぜんうまくいってない」:
- 3配信記録中・全部【裏タブ】・取得率 22%(3,291/14,775)。
- lv350717950: 経過3h08m・19%・`romiDebug.backfill rows:0 seg:0 running:true`=**実際に進んでいない**。
- 公式値レーン全滅: 貢献度=iframe_unrendered / 広告=fetch_error / Eスコア=event_present_unscrapable。
- v0.1.794 の「取り込み中…」は概要に出ていない(=拡張が古い or 別問題)。
- **既知制約(memory)**: 「backfill は前面タブのみ・裏でも取り切るは別テーマ(星野ロミ式バックグラウンド継続)」
  (session_2026-06-10 追記)。今回まさにこれ=全裏タブで誰もスロットを得られず rows:0。

→ もしエラーパターンカタログがあれば、この状態速報を貼った瞬間に
  「backfill rows:0 × 全裏タブ = 既知制約『裏タブ backfill 不可』。前面化 or 別ウィンドウ2枚で解決。
   根治は別テーマ」と即出せた。今は私が毎回コードを辿っている。

## このプロジェクトの制約（必ず守る）
- Windows + PowerShell。`npm run verify:cc` で test/lint/typecheck/build/bump を通す。
- 重い新規依存は入れない(機能マップ feature-map.mjs は esbuild metafile+正規表現の自前解析)。
- 「1変更=patch 1つ」。生成物は docs/feature-map/ に置き dist を汚さない。
- 既存資産: scripts/feature-map.mjs(機能マップ生成)、docs/feature-map/storage-bus.md(断線図)、
  memory/reference_*.md(過去の真因の正本)、changelog.js(EXTENSION_CHANGELOG)。

## 会議への質問（役割分担 + 結論→根拠→反論→具体案）
役割: 総合役=全体設計と保守性 / 発散役=別の切り口・他OSS事例 / 批判役=各案の穴を最低1つ /
実装役=具体的なファイル・データ形式・コマンドまで。

### Q1: エラーパターンの「正本」をどこに置き、どんなデータ形式にするか
- 候補: (a) 機械可読な JSON/JS 配列(症状の検出条件 + 経路 + 過去 reference へのリンク)
        (b) Markdown の表(人が書きやすい)
        (c) memory/reference に散らばっている知見を1つに集約
- AI が「症状→経路→真因」を引くには検出条件が機械可読である必要がある。
  検出条件をどう表現するか(JSON path + 比較? 小さな述語関数?)。
- このカタログは feature-map と統合すべきか、独立させるべきか。

### Q2: 診断 JSON からの「自動検出」をどこまでやるか
- 状態速報を貼られたとき、診断 JSON をカタログの検出条件に通して該当パターンを出す
  「マッチャ」を作るか。それとも検出条件は人(AI)が読む索引にとどめるか。
- 自動マッチャを作るなら: 純関数 `matchErrorPatterns(fastDiag) => [{pattern, route, reference}]` を
  作り、status ページ自体に出す? それとも開発時に node で回すツール?
- 偽陽性(正常なのにパターンに当たる)をどう抑えるか。

### Q3: 「過去の修正履歴」とどう紐づけるか
- changelog の各エントリ・memory の reference には既に「症状→真因→修正」が書かれている。
  これをカタログの各パターンから参照(リンク)する形にするか、抜き書きを持つか。
- 二重管理(reference とカタログがズレる)をどう防ぐか。

### Q4（批判役の核心）: これは本当に役立つか・形骸化しないか
- カタログを作っても「更新されず古くなる」「パターンが増えすぎて引けない」リスク。
- 今回の broadcaster(v0.1.793 storage 断線)や backfill rows:0(裏タブ制約)のような
  「過去に実在した症状」が何個あれば元が取れるか。最初に登録すべき高頻度パターンは何か。
- そもそも「症状→経路」は feature-map の storage-bus 図で既にかなり引ける。
  カタログを別に作る価値は何で、図の拡張で足りないのはどこか。

## 期待する最終成果（司令塔が1案に統合）
最小で価値が出る第一歩(MVP)と拡張を分けて。
今回の実例(裏タブ backfill rows:0)を最初のパターンとして必ず登録できる形にする。
退行ゼロ・既存 feature-map/reference 資産を活かす。
