## 結論  
会場の3D演出を廃止し応援レーンの段組みに統一する場合、応援レーンDOMを全画面に流用する際の**タイル間比率の崩壊**が最大のリスク。CSSの`aspect-ratio`と`min-width`でタイルを固定し、`grid`レイアウトで段数を動的制御する必要がある。

## 根拠  
応援レーンDOMはpopup幅(通常1280px)に最適化されており、全画面(3840px)で拡大するとタイルが1:1の正方形からずれ、ギフト/こん太等のアイコンが「縦長に伸びる」か「横長に広がる」両方の破綻が発生する。これは`flex`レイアウトの特性上、子要素の比率を固定できないため。`grid`でタイル数を計算し、`min-width`で最小幅を設定することで、応援レーンの密着感を保ちながら全画面でも崩れない。

## 反論・リスク  
応援レーンの「静けさ重視」ポリシーと矛盾する可能性がある。例えば、会場のVIPバッジや3キャラをレーン上に重ねると、静けさが損なわれる。2026-07-01会議で「レーンはピカピカ演出なし」と決議したため、VIPバッジの光りやキャラアニメーションは会場専用に維持すべき。逆に、レーンに会場演出を流用する場合、VIPバッジの光りをオフにするロジックを追加する必要がある。

## 結論（この問いへの答えを1〜2文で）
「3表示の見た目統一」を実現するための最優先事項は、**会場固有のDOM構造（ひな壇/visibleSeats）を完全に破棄し、応援レーンで使用している平坦なフラットな段組みDOMをコアUIとして採用すること**です。この際、会場特有の高揚感の代替案として「密度の高い情報量」と「アニメーションによる参加感」に焦点を当て、段階的な実装計画が必要です。

## 根拠（なぜそう言えるか）
提示された確定事実から、データソース、タイル描画ロジック、そしてコアなDOM構造（平坦な段組み）はすでに応援レーンと会場で大部分が共通化されつつあります。今回の目標「見た目そっくり同じ」を達成するためには、最も差異が大きい**会場固有のレイアウトロジック（`buildVenueTiers`, `visibleSeats`）を捨てるか、フラットな構造に強制的にマッピングし直す**しかありません。これにより、`inline`/`別窓`で共通化されている`venueBar.js`が最も効率よく機能する土台ができます。

## 反論・リスク（自分の案の弱点や、別の正解の可能性を最低1つ）
**【最大の反論ポイント：ユーザー体験（UX）の損失】**
「見た目そっくり同じ」を追求しすぎた結果、会場特有の「高揚感」「没入感」「満員感」といった情緒的な価値が完全に失われ、ユーザーから「ただの静的なリスト表示になった」と酷評されるリスクがあります。ユーザーは「似ていること」と「体験が同じであること」を混同しがちであり、特にニコ生のようなライブ空間では後者が重要です。

**【技術的リスク：座標系の再計算負荷】**
吹き出しやギフトの座標系（`seatAnchorEl`基準）は、ひな壇構造によって特定の場所（座席）に紐づいているため、これがフラットな段組み構造に変更されると、単なるX/Y座標の移動ではなく、「どの仮想的な「人の頭上」を指しているか」という**論理的な再計算が必要**になります。これを無視すると、演出が場違いになる可能性が高いです。

## 具体案（実際に動く/作れる形で具体的に）
### 1. 設計方針：コアコンポーネントの強制統一とレイヤー分離
*   **捨てるもの:** `buildVenueTiers`による3D変換、`visibleSeats`による表示間引きロジック。
*   **残す・共通化するもの:**
    *   **DOM構造:** 応援レーンのフラットなFlex/Gridベースの段組みを「会場の基本レイアウト」とする（`renderStoryUserLaneDom.js`の骨格をメイン）。
    *   **データ処理:** `userLaneCandidatesFromStorage(純関数)`の結果を利用する点は維持。
    *   **共通ライブラリ化:** `venueBar.js`は、描画エンジン（Canvas/DOM）と座標計算ロジックのみに絞り込み、「どのレイアウトモードか」を引数で渡す形に変更し、レンダリング層を抽象化する。

### 2. 段階的実装ロードマップ (フェーズ分け)
**✅ フェーズ 1：表示パリティの確保（最優先）**
*   目的: 「データが同じ」「構造が平坦」であることを保証し、回帰を防ぐ。
*   作業内容: `renderSeats`内の3D変換ロジックを完全にコメントアウト/スキップさせ、応援レーンと同じFlexコンテナに子要素（タイル）を直接配置する。（CSSのみの変更で対応可能か検証）。
*   成果物: どの表示モードでも「全員が平坦な横並び」になること。

**⚠️ フェーズ 2：UXの補填（重要度高）**
*   目的: 「見た目そっくり同じ」を「体験的に許容できるレベル」に引き上げる。
*   作業内容: ひな壇による「立体感/崇拝感」の代替として、以下の要素を導入する。
    1.  **背景群衆Canvas:** 常に動く背景（z:0）で「満員感」を担保。
    2.  **アニメーション強化:** タイルが単に配置されるだけでなく、登場時にフェードインやわずかなスケールアップのアニメーションを付与し、「参加している感覚」を演出する。（静的なDOM以上の動き）。

**🚀 フェーズ 3：機能の完全統合と最適化（最終目標）**
*   目的: 全ての要素が新しいフラット構造上でシームレスに動作すること。
*   作業内容: ギフト投げや吹き出しなどの座標計算ロジックを、`seatAnchorEl`から「仮想的なタイル位置(Row, Col)」ベースの抽象化された座標システムへ移行し、再利用性を高める。

### 🚩 【司令塔による統合と最終提案】
上記の分析に基づき、最も安全で実行可能性の高い案は、**フェーズ1を核としつつ、フェーズ2のアニメーション要素を早期に組み込む「ハイブリッド・フラット化戦略」**です。

*   **残しつつ共通化するもの:** データ処理ロジックとタイル描画は維持。会場のDOM構造から、単なる`display: flex; flex-wrap: wrap;`による横スクロール可能なグリッドレイアウトに置き換える。
*   **最重要ポイント（司令塔の指示）:** ユーザーが最も失うと感じる「高揚感」の代替として、技術的な再現性よりも**アニメーションと情報密度の向上（フェーズ2の内容をフェーズ1で実施）**にリソースを集中投入すべきです。これにより、「見た目が違う」という批判を、「演出が洗練された」というポジティブな評価に転換できる可能性が高いです。

## 結論

## 根拠
既にデータ源は同一であり、会場のひな壇レイアウトと表示間引きがズレの真因であることが裏付けられている。会場の表示を応援レーンの段組みDOMに統一することで、ズレを解消し、「3表示そっくり同じ」の目標を達成できる。また、inline会場と別窓会場は同じvenueBar.jsを共用しているため、1箇所の修正で両方に効く。

## 反論・リスク
会場の"SHOWROOM感/崇拝感/満員感"が失われてユーザー体験が劣化する可能性がある。段組みでも満員感/参加感を出す方法を検討する必要がある。また、吹き出しとギフト投げの座標がseatAnchorEl基準で再利用できるか、段組みDOMでavatar位置が変わらないかの検証が必要である。

## 具体案
1. 会場のrenderSeatsをrenderStoryUserLaneDomの段組みDOMに置き換える。
2. 段組みDOMを全画面に流用可能なように設計する。
	* 幅・段数・スクロール(overflow-y)・タイルサイズを可変にする。
	* inline(映像圧力あり)と別窓(映像コーナーのみ)で同じDOMを成立させる。
3. 段組みでも満員感/参加感を出す方法を検討する。
	* 背景群衆Canvasを利用する。
	* 発言反応スケールを利用する。
4. 吹き出しとギフト投げの座標をseatAnchorEl基準で再利用する。
	* seatAnchorElの位置が変わらないことを検証する。
5. 段階リリースを実施する。
	* まずinline会場を修正し、別窓会場を後に修正する。
	* 回帰(横スクロール/映像はみ出し/重さ/満席ロジック)を機械的に守る。

## 結論  
会場側の **renderSeats** を **renderStoryUserLaneDom** の段組みロジックに置き換え、**visibleSeats** の間引きロジックだけを残しつつ 3D ひな壇演出を完全に除去する。段組みDOMは幅・段数・タイルサイズを CSS カスタムプロパティで動的に調整できるよう汎用化し、inline と別窓の両方で同一コンポーネントを使用できるようにする。これにより「見た目もレイアウトまでそっくり同じ」状態を実現しつつ、既存の満席ロジックや演出は安全に保持できる。

---

## 根拠  

1. **データ供給は統一**  
   - `userLaneCandidatesFromStorage` が 3 表示すべての入力であり、表示対象のズレは **visibleSeats** と **buildVenueTiers** のみ。データ層を触らなくても UI 層だけで統一できる。  

2. **venueBar.js の共通化は既に実装済**  
   - inline と別窓は同一 `venueBar.js` を共有しているため、ここに段組みロジックを差し込めば両方に即効。  

3. **段組み DOM は既に統一**  
   - `buildPersonTileEl` が共通化済みで、レーン側の DOM 構造 (`guideTop → laneLink → laneGift → laneKonta → laneTanu → guideBottom`) は平坦で 3D 変形が無い。これをそのまま venue に流用すればレイアウトは完全一致。  

4. **パフォーマンスと安定性**  
   - ひな壇の 3D transform は GPU 負荷とレイアウト計算コストを増大させ、特に 500 人規模での横スクロールバグの温床。除去すれば描画コストは **O(N)** に抑えられ、過去の「更新◯秒前が56年前」バグ再発リスクも低減。  

5. **可変幅・段数の設計は CSS カスタムプロパティで実装可能**  
   - `--lane-width`, `--lane-height`, `--lane-columns` をルート要素に設定し、メディアクエリや JavaScript から動的に変更すれば、popup 幅から全画面、inline の 35vh 制限まで同一 DOM が自然に適応できる。  

---

## 反論・リスク  

1. **ユーザー体感の崩壊リスク**  
   - 3D ひな壇が提供していた「満員感・崇拝感」を失うと、会場利用者から「盛り上がりが薄くなった」苦情が出る可能性がある。  

2. **座標系の不整合**  
   - 吹き出しやギフト投げは `seatAnchorEl`（avatar 位置）を基準にしているが、段組みは平坦化されるため `seatAnchorEl` の取得ロジックが変わり、座標計算がずれる恐れがある。  

3. **visibleSeats の過度緩和**  
   - inline では映像下端 35vh の制限があるため、間引きロジックを緩めすぎると横スクロールが出て映像が隠れる。逆に別窓で緩めすぎると 500 人超えでスクロールが重くなる。  

4. **実装コストと段階的リリースの複雑さ**  
   - 完全に 3D を除去した後に、代替の「満員感」演出（例: 背景群衆 Canvas の密度調整）を追加する必要が出てくると、リリースが二段階になる。
