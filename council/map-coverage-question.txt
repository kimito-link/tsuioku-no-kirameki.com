お題: 機能マップ(特に機能逆引き索引「○○を司るのはここ」=feature-sitemap / FEATURES辞書)を「全機能を網羅」にする設計を1案にまとめる。ユーザー要望「読み上げ・会場の吹き出し・ギフトが出るタイミング・すべてのタイミングの正確さ…マップに全部載っていない/抜けがある」。手で全部書くのは非現実的なので自動化の設計が要る。

# 実コードで測った現状(これが前提・覆さない)
- マップは2層: (a)code-tree.html=全ファイル網羅ツリー(git追跡を機械全網羅+先頭コメントから役割自動抽出)。voice17/venue16 等すべて載る。 (b)feature-sitemap.html=機能逆引き「○○を司るのはここ」=FEATURES辞書(scripts/repo-tree-map.mjs)で手動の代表選抜。
- **逆引きの抜けが甚大**: src/lib の純ロジック435本中、FEATURES辞書が参照するのは31本だけ=404本(93%)が逆引きに無い。
- ドメイン別の規模(逆引きに大半が無い): gift 32本 / comment 57本 / diag 21本 / backfill 18本 / venue 16本 / report 16本 / lane 15本 / avatar 14本 / official 13本 / voice 9本。
- FEATURE_CATEGORY(マインドマップの分類枝)と CATEGORY_CHARA_NOTE は scripts/repo-tree-map.mjs にある。tree-map:check が腐り検知。
- 各ファイルは先頭コメントに役割を書いてある(code-tree が自動抽出済=全499ソースに役割コメント有り)。
- ⚠️ ユーザーが特に気にする「タイミング」系=timingConstants.js / venueBubbleLifecycle(吹き出し追い出し) / giftThrowProjectile(ギフト演出) / voiceReadQueue(読み上げ順) / persistThrottle / diagPaintDeferGate / domHarvestScrollDefer などが逆引きにほぼ無い。「いつ何が起きるか」が地図で引けない。

# 問い(これに答えて)
1. 「網羅」の正しい定義は何か。(A)FEATURES辞書を手で404本ぶん書き足す(非現実的・腐る) (B)code-tree(全網羅ツリー)を逆引きにも使えるよう強化し、FEATURES手動辞書は「特に重要な代表」に絞る役割分担にする (C)ファイルの先頭コメント+tags から逆引き索引を半自動生成し、手動辞書は上書き/補足だけにする。星野ロミ式(落とさない・既存活かす=先頭コメント既にある・過剰実装回避)でどれを正本に。
2. タイミング/演出/読み上げのような「機能ドメイン×ライフサイクル(いつ)」を地図でどう表現するか。ファイル列挙でなく「コメント実時刻→吹き出し→読み上げ→ギフト演出 の時系列」を1枚にするビュー(timingConstants 中心の時系列図)は価値があるか過剰か。
3. 自動生成の設計: 先頭コメント(役割)とファイル名/ディレクトリ/tags から、機能カテゴリへ自動分類して逆引きに流し込む案。誤分類のリスクと、手動 FEATURES で上書きする余地。tree-map:check の腐り検知をどう網羅版に拡張するか(新規ファイルが必ず地図に出ることを保証)。
4. 「全部載せる」と情報過多で逆に引けなくなる過剰のリスク。404本を全部フラットに出すと埋もれる。カテゴリ折りたたみ/重要度/検索 で「網羅しつつ引ける」両立の最小設計は。code-tree が既にやっている折りたたみと役割抽出を逆引きに転用できるか。
5. やってはいけない過剰実装を1つ以上(批判役は必ず穴を指摘): 例=404本を手で辞書化(即腐る)/AIで毎回全ファイル要約(重い・非決定的)/巨大フラット一覧で検索性ゼロ/タイミング図を手描きで腐らせる。

# 制約(星野ロミ式)
記録本体不可侵・新storage不要(これはdocs生成系)・生成は決定的(scripts/repo-tree-map.mjs の npm run tree-map/feature-map で再現)・既存データ活かす(先頭コメント/tags/code-tree の役割抽出は既にある)・過剰実装回避・tree-map:check で腐り検知を網羅版にも効かせる・no CDN・手で書く辞書は最小に。

出力は『結論 → 根拠 → 反論・リスク → 具体案』の4ブロックで。具体案は「逆引き網羅をどう自動生成するか(どの既存データから)」「タイミング系をどう1枚にするか」「腐り検知の拡張」を実装の置き場所(scripts/repo-tree-map.mjs のどこ)まで。
