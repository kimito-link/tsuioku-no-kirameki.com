**① 修正系譜マップ(Bug Lineage Map)= changelog 177版を「バグ系統」で枝化**=最優先・最大効果・既存データのみ。
② 依存グラフは「影響3以上のノードだけ」に絞って次段階。③④(データフロー/カテゴリツリー)は既存で十分=軽い装飾のみ。

🔴 **司令塔が実データで①の実現性を確定**: changelog 177版は系統キーワードで綺麗に分類できる
(実測=記録62/会場67/表示83/取得58/読み上げ35/ギフト29/匿名25/診断13版)。v0.1.840 の
classifyFeatureCategory を流用=機械生成・腐らない・人手辞書ゼロ。git log の生グラフ複製は不要(即腐る)。

## 根拠

- 会議3/3一致: ①最優先(再発防止核心)・②影響3以上に絞る・③④既存で十分・git log複製は腐る。
- 再発防止の核心(全員)=「同系統のバグを過去にどう直したか」を即辿れること。実績=記録件数系は
  v0.1.792→804→838→839 と4回も触っている。これを1本の枝で繋げば「またこの系統だ」が一目で分かる。
- 既存データ(星野ロミ式・活かす): changelog.js(177版・日本語要約)+ classifyFeatureCategory(分類辞書)+
  既存の決定的生成(npm run tree-map)+ --check 腐り検知。新規データ源ゼロ。

## 反論・リスク(司令塔の選別)

- ❌ qwen「1枚の動的シミュレーター(リアルタイム解析・インタラクティブ)」= 却下。実装コスト膨大・
  決定的生成の制約を破る(批判役 gpt-oss が的確に指摘・司令塔も同意)。
- ❌ groq「依存グラフ全体出力(500+エッジ)」= 却下。腐り検知がノイズ化・ブラウザ重い。→ ②は影響3以上に絞る。
- ❌ git log の生グラフを docs に複製 = 却下(即腐る・重い)。changelog の構造化データから生成する。
- ⚠️ 機械分類の誤分類(qwen/gpt-oss): items の系統分類が外れると誤誘導。→ classifyFeatureCategory の
  辞書を「正解ラベル」に流用+一致しない版は「未分類(黄)」で人手確認を喚起(嘘の系統で安心させない)。
- やってはいけない過剰実装(会議+司令塔): ①4枚同時描画 ②動的シミュレーター ③500+ノードSVG
  ④git log複製 ⑤外部グラフライブラリ(no CDN違反)。

## 具体案(段階導入)

### 第1(最優先・これだけ先に作る): 修正系譜マップ
- 純ロジック src/lib/changelogLineage.js(+test): EXTENSION_CHANGELOG を入力に、各版の summary+items を
  系統キーワード(記録/会場/表示/取得/読み上げ/ギフト/匿名/診断/マップ…)で分類し、
  `{ tag, versions: [{version, date, summary}] }[]` を返す純関数。classifyFeatureCategory の語彙を流用
  (or 専用の系統辞書を小さく持つ)。1版が複数系統に該当しうる(multi-tag)。未分類は 'その他'。
- 生成: scripts/repo-tree-map.mjs に renderLineageHtml/Md を足す or 既存 feature-sitemap に
  「🧬 修正系譜(この系統を過去にどう直したか)」セクションを追加。各系統=折りたたみ、中に版を時系列で
  (新しい順)。版に summary とリンク(GitHub commit へは版→commit対応が要る=なければ版番号+日付だけ)。
- 描画は重いSVGにしない=code-tree と同じ details 折りたたみ+CSS の縦線で「枝」を表現(no CDN・軽量)。
- 再発防止への効き: 「記録件数系をまた触る」とき、この枝を見れば v0.1.792/804/838/839 の修正と
  「なぜ毎回触るか(複数ソース×複数ゲート)」が即分かる=同じ轍を踏まない。

### 第2(次段階・条件付き): 依存サブグラフ(影響3以上だけ)
- 既存 impact-map(ほぼ空)を「直接/間接インパクト3以上のファイルだけ」ノード化。自前の軽量 import
  パーサ(正規表現 import 抽出・外部ライブラリ禁止)。--check で「新規インパクト増」を検知。
- 影響先が修正系譜の系統と一致したらハイライト=「ここを触ると過去の○○系バグが波及」警告。
- ⚠️ 500本フル解析は重い=影響3以上フィルタ必須。腐り検知がノイズ化しない範囲で。

### 第3(任意・軽装飾): データフロー/カテゴリツリーに接続線
- SPINE_STAGES と feature-sitemap は既存のまま。GitHub 風の枝分かれ線を CSS で薄く足す程度(過剰にしない)。

### 腐り検知の拡張
- changelogLineage は changelog.js から決定的生成=既存 changelogConsistency ゲートと同経路で腐り検知。
- 「未分類(その他)の版が増えた」を --check で warn(系統辞書 or summary 書き方の改善を喚起)。

## 段階の進め方
- 第1(修正系譜マップ)だけ先に実装・push して「効くか」をユーザーに見てもらう。第2(依存)は第1の手応えを
  見てから(過剰回避)。substantial=フェーズ・フロー図 docs/*-flow.html 対象。

## 制約(星野ロミ式)
記録本体不可侵・新storage不要(docs生成系)・決定的生成・既存データ活かす(changelog/classifyFeatureCategory)・
過剰実装回避(動的シミュレーター/500ノードSVG/git log複製は禁)・--check で腐り検知・no CDN(外部グラフlib禁止)・
手書き辞書は最小(系統語彙だけ)。
