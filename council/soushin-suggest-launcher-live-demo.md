# お題: クイックペーストランチャーの「動画みたいな動的デモ」をLPに作りたい

## 背景
soushin-suggest.link のLPには既に「SEE IT LIVE」という、Chatwork⇔AIチャット間でカーソルが動いてコピー&ペーストする様子を再現する本格的なJSアニメーションデモがある（`.thx-stage`）。

ユーザーから「クリップボード履歴・定型文機能についても、動画みたいな動的なデモが欲しい」という要望が来た。

前段階として、まず静的なCSSモック（ランチャーの見た目をHTML/CSSで再現した2枚の画像的な表示）を作ってLPに追加したが、ユーザーの反応は「これじゃない、動画みたいな動的なものが欲しい」だった。静的モックは撤回済み。

## 既存の動的デモエンジンの構造（コード調査済み・一次情報）

`index.html`の`.thx-stage`（1877-2298行目付近）:

- **フェーズ構成**: `playBefore()`→`playWipe()`→`playAfter()`→`playPayoff()`の直列関数。各関数は`seg(fn, delay)`ヘルパーで累積時間を進めながら`at(fn, delay)`（自前のsetTimeoutラッパー）にスケジューリングするリレー方式。
- **カーソル移動**: JSでの座標計算はせず、`setCursorAt(xPct, yPct)`が`style.transform`をセットするだけで、実際の滑らかな移動はCSS `transition: transform 0.9s cubic-bezier(...)`が担う。
- **軌跡線**: SVG `path`にベジェ曲線をJSでセットし、`stroke-dasharray/dashoffset`のCSS transitionで「描かれていく」演出。
- **長押しリング**: SVG円2つ、`stroke-dashoffset`をCSS transitionで0にすることで時計回りに満ちるリングを表現。JSは`classList.add/remove('is-filling')`を叩くだけ。
- **HUD（左手○回、右手操作、秒数）**: テキスト直書き、ストップウォッチは実時間を表示用の秒数にリニアマッピング。
- **リセット**: `resetVisuals()`が全クラス除去＋入力欄プレースホルダー復元＋HUD初期化。`play()`冒頭で`clearAll()`→`resetVisuals()`の順で呼ぶことで多重再生に強い。
- **再利用可能な部品**: `setCursorAt`、`flashKey/flashMouse`、`at/clearAll`、`resetVisuals`、`startWatch/stopWatch`、長押しリングのCSS機構はシナリオ非依存の汎用ユーティリティ。CSSは`.thx-`プレフィックスで名前空間分離済み。
- **決め打ちの部分**: `.thx-app`が2ペイン固定（Chatwork/AIチャット）、`.thx-msg`/`.thx-input`など要素がテキストチャット専用構造。「シーン設定オブジェクト」のような抽象化層はなく、ランチャーのポップアップUI（履歴リスト・定型文タブ）を表現するには不向き。新規に`.thx-launcher-*`的なDOM構造と、独立したシーン関数を新設するのが現実的（既存シーンは一切壊さず並存できる）。

## 地雷マップ（守るべき既存の設計規約）

1. **`prefers-reduced-motion: reduce`の二重対応が必須**: グローバルに`* { animation: none !important; transition: none !important; }`があり、`thx-stage`固有には`matchMedia`判定で`showStaticPayoff()`（アニメーションさせず最終結果のみ静的表示）に切り替える2段構え。新シーンもこのパターンを踏襲しないとアクセシビリティ違反になる。
2. **オートプレイのトリガーはIntersectionObserverではなく、`getBoundingClientRect`によるスクロール/リサイズ監視＋50msスロットル**（コメントに「一部プレビューiframeでIntersectionObserverが確実に発火しないため」と明記）。現状は単一の`played`フラグがグローバルにつき、複数ステージを同時に持つ場合はスコープ分離が必要。
3. **モバイル対応**: `.thx-screen`は`@media (max-width: 620px)`で2カラム→1カラムに切替。カーソル座標がパーセンテージ＋`viewBox`ベースなので要素サイズが変わってもレイアウト崩れしにくい。新パネルも同じ方式を踏襲すべき。
4. **前回の静的モックで学んだ地雷（ダミーデータの中身）**: ユーザーが実際に見せたスクリーンショットの定型文名・件数・時刻は本人の実業務データの可能性が高く、転用禁止。完全に架空の内容に作り替える。
5. **看板の誇張禁止**（過去の「幻の星評価」事故の教訓）。
6. **プライバシー訴求との整合**: 「勝手に覗かない安心」が核心価値。デモが「本物のユーザーデータを覗いている」ように誤読されない一言（サンプルである旨）が必要。
7. **診断ページには手を入れない**（前回設計の結論を踏襲、総合判定を汚さない原則）。

## 問い（会議で検討してほしいこと）

1. 「動画みたいな動的デモ」として、クイックペーストランチャーのどんな操作シーケンスを再現するのが最も訴求力が高いか（例: サイドボタン長押し→ランチャーが開く→履歴を選ぶ→貼り付けられる、という一連の流れ、または定型文を番号キーで呼び出す流れ等）。
2. 既存の`.thx-stage`エンジンの部品（カーソル移動・長押しリング・タイマー管理）をどこまで流用し、どこを新設すべきか。「別のステージとして独立させる」か「既存のBefore/Afterの中に新しいペインとして統合する」か。
3. アニメーションの尺（何秒程度が離脱されずに見てもらえる長さか）と、ループ/リプレイの扱い。
4. サイドボタン長押し→ポップアップ出現、という「長押し」演出は既存の長押しリング機構を流用できそうだが、ポップアップ自体の出現アニメーション（フェードイン/スケールイン等）をどう作るか。
5. MVP（最初の1歩）として何を選ぶべきか？ フル機能のアニメーションシーンを一から作るのは工数が大きいため、段階的な実装順序も示してほしい。
