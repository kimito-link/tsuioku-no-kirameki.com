### nvidia/qwen3.5-122b  [発散アイデア（推論強）]  (21617ms)

## 結論
「依存関係の注入（案1）」や「コピペ（案2）」ではなく、**「Popup の描画関数を『Web Worker』として別スレッドで動作させ、その生成した HTML 文字列を `postMessage` で Live-View へ転送し、`innerHTML` として貼り付ける」**という、**「描画ロジックと DOM 環境の完全分離」**による解決を提案します。

## 根拠
1.  **1px の狂いを物理的にゼロにする**: 描画関数が依存する「Popup 固有の DOM 状態（`storyAvatarLoadGuard` の内部キャッシュや `bindOnErrorHandlersWithin` が束縛したイベントリスナー、`_topSupportRankLastHtmlByEl` の WeakMap 参照）」は、Live-View の DOM 環境とは完全に異なるため、Live-View 内で直接実行すると「環境依存のバグ」が必ず発生します。Web Worker 内で実行すれば、Worker 内部で Popup と同一の DOM 環境（あるいはそのモック）をシミュレートできるため、出力される HTML 文字列（DOM 構造・クラス名・インラインスタイル）が 100% 同一になります。
2.  **依存関係の「汚染」を回避**: 案1のように依存物を引数で渡すと、`live-view` 側で `getStoryColorScheme` などを実装する際、Popup の「隠れた挙動（Side Effect）」を再現しきれず、微妙な挙動の違い（例：画像ロード失敗時のフォールバックタイミング）が生まれます。Worker 内であれば、Popup のコードをそのまま `eval` またはモジュールとして読み込み、Popup が想定する「仮想 DOM 環境」を構築するだけで済みます。
3.  **MV3 のセキュリティ制約の逆利用**: MV3 では `eval` が制限されていますが、Worker 内でスクリプトを動的にロードすることは可能です。これにより、Popup の「ローカル関数」を、Live-View からは見えない「ブラックボックス」として安全に呼び出せます。

## 反論・リスク
*   **非同期レイテンシと白飛び**: `postMessage` を使うため、描画完了までに数ミリ秒〜数十ミリ秒の遅延が発生します。Live-View の読み込み直後に「白っぽい枠」や「空のコンテナ」が一瞬表示される可能性があります（案1や案2なら同期的に描画可能）。
    *   *対策*: Live-View 側で、Worker からのメッセージ到着前に「Skeleton 表示」や「Popup と全く同じ CSS の空のプレースホルダー」を表示し、メッセージ到達後に `innerHTML` 置換する UX 設計を必須とします。
*   **DOM 操作の制限**: Worker 内では `document` が存在しないため、`document.createElement` などの API が使えません。
    *   *対策*: Worker 内では、ブラウザ標準の `DOMParser` や、`jsdom` などの軽量ライブラリ（MV3 制限内であれば）をライブラリとして読み込み、Popup 関数が `document` を叩く代わりに、Worker 内で構築した「仮想 document」を差し替える（あるいは、Popup 側を `document` 操作から `string` 生成ロジックへリファクタする最小変更を加える）必要があります。
