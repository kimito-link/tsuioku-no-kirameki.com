# お題: 「全体を見渡せて根幹が分かる」WEB視覚マップをどう作るか

## このお題は「カラ会議」用です（役割分担で『結論→根拠→反論→具体案』）

役割: 総合役=全体設計の整合と実現可能性 / 発散役=既存と違う切り口・他OSSの先行事例 /
批判役=各案の穴を最低1つ / 実装役=具体的なファイル名・コマンド・出力形式まで。

## 背景・動機

ニコニコ生放送 Chrome 拡張のコードベース。規模が大きい（content-entry.js は16000行超）。
過去にこういう事故が出た:
> 会場モード(venueBar.js)に配信者本人のサムネが「匿名」として混入。
> 真因は content-entry.js の broadcasterUid/IconUrl が venueBar.js に「届く経路がない」こと。
> データの流れが途切れていたのに、それが誰の目にも見えていなかった。

ユーザーの言葉:
> 「全体を見渡せて**根幹**が分かるマップがほしい」
> 「このマップは md なので **WEB で視覚的にわからないと意味がない**」

## 確定した前提（ユーザー選択済み・変更不可）

1. **網羅でなく「根幹（背骨）」**。既存マップは全部「網羅型」で細かすぎる（下記）。
   今回ほしいのは、データが入口→記録→表示まで通る**背骨1本**を、枝葉を削いで見せるもの。
2. **出力は WEB で視覚的に分かる HTML が必須**。`.md` 単体（GitHubでしか図にならない Mermaid 含む）は不可。
   ブラウザでファイルを開いたら、図として根幹がひと目で分かること。AI もテキストとして読めること。
3. 既存の自動生成パイプライン（git追跡＋人間辞書→生成・`--check` で腐り検知）の流儀に合わせる。
   `docs/` に置き dist に焼かない。重いライブラリは入れない（既存 html は素の HTML+CSS、依存ゼロ）。

## ⚠️ 既に存在するマップ（重複生成は禁止・これを「束ねる/補完する」前提）

| 既存 | 何 | 形式 | 視覚HTMLか |
|---|---|---|---|
| `docs/MAP.md` | 全地図の入口ハブ | md | ❌ テキストのみ |
| `docs/repo-tree-map.md` / `.html` | ディレクトリ役割＋機能逆引き＋冒頭Mermaid | md + **html** | ⭕ html あり（自動生成・手本) |
| `docs/feature-map/index.md` | 機能ごと依存図(entry単位) | md | ❌ md のみ |
| `docs/feature-map/storage-bus.md` | storage の producer/consumer＋断線検知 | md | ❌ md のみ |
| `docs/feature-map/impact-map.md` | このファイルを変えたら何が壊れるか | md | ❌ md のみ |
| 拡張 `status.html` の「全体マインドマップ」 | 実行時の状態(別レイヤー) | html | ⭕ 但し実行時状態であり静的コード地図ではない |

→ **足りていないのは『静的コードの根幹データフロー1本を、ブラウザで図として見せる html』**。
   既存 html は repo-tree-map（ディレクトリ羅列）だけで、データの流れ（背骨）は誰も図にしていない。

## 実コードで裏取り済みの「背骨」（会議はこれを前提に。ハルシネ禁止）

データの一生（取得→記録→集計→表示）の実体:
- **取得**: NDGR(protobuf 直読み) と watch DOM 観測 → `src/extension/content-entry.js`（メインエンジン）
- **記録**: content-entry が IndexedDB / chunk / tail バッファへ。純ロジックは `src/lib/*`、ドメインは `src/domain/`
- **集計**: 保存コメント → レーン候補/会場/ランキング（`src/data/`, `src/domain/`, `src/lib/*`）
- **表示**: `src/extension/popup-entry.js`(パネル) / `venueBar.js`(会場) / `status-entry.js`(状態)
- データの受け渡しは主に **chrome.storage.local のキー**（producer/consumer）= 断線が起きる箇所。
- 生成スクリプトの手本: `scripts/repo-tree-map.mjs`（git追跡＋ROLES/FEATURES辞書→md＋html、`--check`）。
  `scripts/feature-map.mjs` は md/Mermaid 止まり（html 化されていない＝今回の不足の核心）。

## 会議への質問

### Q1: 「根幹（背骨）」の単位は何にすべきか
データの一生（取得→記録→集計→表示）を1本のフロー図にするのが妥当か。
それとも「機能の幹（記録/会場/応援/読み上げ/ギフト）」を縦に並べ、各機能のデータ源→表示を1行で描くか。
枝葉（個々の純関数）を**描かない**ための線引き基準は？（例: entry境界とstorageキーだけ描く、等）

### Q2: 視覚HTMLの実現方法（依存ゼロが前提）
既存 `repo-tree-map.html` は素のHTML+CSSのカード。データフロー図は線・矢印が要る。候補:
- (a) `repo-tree-map.html` と同じ手書きCSSで、ノードを縦に並べ CSS で矢印（疑似要素/罫線）
- (b) インライン SVG をスクリプトで生成（ノード座標を計算して `<line>`/`<path>`）
- (c) Mermaid を **html に埋め込み**（mermaid.js を同梱 or CDN）— だが依存・CDN は方針に反する
- (d) `<details>`折りたたみで階層（status.html の折りたたみツリー流儀）
どれが「依存ゼロ・ブラウザで図・AIもテキストで読める」を最も満たすか。批判込みで。

### Q3: 自動生成 vs 半手書き
背骨は「重要なものだけ」に削ぐ必要がある＝機械が全importを辿ると枝葉まみれになる。
- 人間が「背骨の節（取得/記録/集計/表示の代表ファイルとstorageキー）」を辞書で定義し、
  実在検証（`--check`でファイル/キーの消失を検知）だけ機械化する案（repo-tree-map の FEATURES 方式）
- それとも storage-bus の既存データ（producer/consumer）を入力に、主要キーだけ自動で背骨化する案
どちらが「腐らず・かつ根幹だけ」を両立するか。

### Q4: 「ミスがなくなる」に図だけで足りるか／既存verifyとの役割分担
既に `verify:cc` に storage 断線検知(feature-map:check)・腐り検知(tree-map:check)がある。
今回の根幹html図は、それらと何が違う「ミス防止」を新たに足すのか。
broadcaster バグ（venueBar に届かない）は、この根幹図があれば気づけたか？図と lint の役割分担は？

## 期待する最終成果（司令塔が1案にまとめる）

「何を・どの順で・どのコマンドで作るか」が分かる1案。最小で価値が出る第一歩(MVP)と拡張を分けて。
MVP は必ず「ブラウザで開いて根幹がひと目で分かる html が1枚できる」ことを満たすこと。
