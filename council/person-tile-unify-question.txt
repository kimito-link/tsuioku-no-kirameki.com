あなたは「君斗りんくの追憶のきらめき」という Chrome 拡張（ニコニコ生放送のコメント記録＆可視化ツール）のプロダクト設計会議に招かれたフロントエンド設計の専門家です。日本語で回答してください。

## お題（1行）
ニコ生視聴者を表す「丸いサムネイル（アイコンタイル）」を1つの正本コンポーネントにして、popup（ポップアップの応援アイコン列）と会場モード（venue の客席）で使い回し、その同じタイルに【その人のコメント本文・ギフト・広告（貢献度）】を userId で関連づけて、文脈に応じたアクション（吹き出し・読み上げ・ギフト投擲演出）を載せたい。星野ロミ思想で設計するとどうなるか、具体設計を出してください。

## 星野ロミ思想（この4本柱を設計原則として使う）
1. 摩擦除去 — 価値到達までの距離を極限まで短く。
2. 元からあるデータを最大限活かす（捨てない）— もう手元にあるデータを再取得・破棄しない。
3. 同じものを2回作らない（1つの正本）— 重複実装を排し、1コンポーネント/1純関数に集約。ドリフト（食い違い）を構造的に防ぐ。
4. 軽く・有界に・絶対に落とさない — 重い再計算をしない。上限を設ける。失敗時も画面を壊さない（fail-open）。

## 現状の【確定事実】（司令塔が Chrome DevTools の実 DOM と実コードで裏取り済み。ハルシネ防止のためこれを前提にせよ）

### データ集約は既に共通化されている
- popup の応援アイコン列も、venue（会場）の客席も、同じ純関数 `userLaneCandidatesFromStorage(rows, liveId, opts)` でコメント行を userId 単位に集約している。
- 戻り値の型 `UserLaneCandidateFromStorage` は { userId, nickname, avatarUrl, avatarObserved, liveId, commentCount?, giftCount?, _laneSortAt? }。
- 両者とも opts に requireText:true（本文ありの行だけ参加者にする）と broadcaster 除外ガードを渡す。集約結果はほぼ同一になるはず。

### 描画（DOM）は完全に別物（ここがズレの根）
- popup: `renderStoryUserLane()` → `paintStoryUserLaneDomFilled()`（story/renderStoryUserLaneDom.js）。横並びの丸サムネタイル（アイコン＋数値ID＋ニックネーム）。匿名(a:xxx)も別の段に出す。
- venue: `buildVenueSeating(rows, { maxSeats, prevSeatByKey, isGenericName, promoteUserIds })` → ひな壇（tier）状の客席 DOM。席数に上限(maxSeats / visibleSeatCount)があり、表示しきれない匿名は「観客 N 人」のクラウド Canvas に集約。promoteUserIds=spokenUserIds（しゃべった人）を優先して席に出す。
- つまり「データは同じ候補リストなのに、描画と採用基準が venue だけ独自」。これが「popup のアイコン列には出るのに会場の席に出ない人がいる」の構造的な根。

### 【最重要・方針確定】アクティブユーザー＝アクションした人。匿名/非匿名は無関係。全員着席
- アクティブユーザーの定義: コメント・ギフト・広告(貢献)のいずれかを出して【素性(userId)が観測できた人】。匿名(a:xxx)か数値IDかは一切関係ない。アクションした時点で全員アクティブ＝会場の主役。
- 新方針: アクティブユーザー(匿名含む)は全員、会場の席に座らせる。popup の応援アイコン列と会場の顔ぶれを完全一致させる。
- 旧方針(2026-06-13)「匿名はアリーナじゃない＝名前のある人だけ席・匿名は『ほか観客 N人』に集約」は破棄。旧コードは「アクティブかどうか」と「名前があるかどうか」を取り違えていた(アクションしたのに名前が無いだけで席から弾いていた)。これが誤り。
- 現状コード `collectVenueParticipants`/`venueParticipantKey`(venueSeats.js)は名前のある人だけ席キーを返し、匿名/無名は null を返して `collectAudienceFaceUserIds` の totalAnonymous(「ほか観客 N人」テキスト)に集約していた。この「匿名を席から弾く」分岐を撤廃し、userId が観測できた人は匿名でも席に座らせよ。
- 席上限(VENUE_FULLSCREEN_MAX_SEATS=150)と入れ替え制は維持。匿名込みで「直近アクション優先で150席、超過は入れ替え」をどう設計するか示せ。匿名が大量に来ても落とさない・重くしないこと。

### 来場者数(PV)は席ではなく背景群衆で表現する
- ニコ生の「来場者数」(例 5,043人)は PV 的な延べアクセス数。同じ人が入り直しても増え、無言の通りすがりも含む。拡張は無言視聴者の userId を取得できない(NDGR で素性が取れるのは発言/ギフトした人だけ)。
- ゆえに来場者数を席に出すのは原理的に不可能。来場者数は【背景の群衆 Canvas の密度】(既に crowdCanvas/drawCrowdOnCanvas が存在)で「たくさん来ている」賑わいとして表現する。席=アクティブユーザー(顔が見える)、背景群衆=来場者数(顔は出ない密度)、という二層で設計せよ。
- 「ほか観客 N人」という現行テキストは来場者数(PV)とユーザーに取り違えられて紛らわしいので、アクティブを全員着席させたうえで、この表示の意味を「席に表示しきれない超過アクティブ数」か「来場者数」かに明確化/再定義すること。

### 会場の付加機能（venue だけが持つ。popup には無い）
- 席に座った人物の【吹き出し】（コメント本文を表示）。読み上げ ON のとき「仮(previoice)→本(speaking)」の2段階で出す。
- 【読み上げ】VOICEVOX 合成（voicePlayer.enqueue → 鮮度ゲート voiceAgeGate → 再生）。新着コメントを起点に鳴る。
- 【ギフト投擲演出】giftThrowProjectile。発射点はその人の席アイコン中心。
- 会場には常駐3キャラ（りんく・こん太・たぬ姉＝案内役）も居る。

### 各データはもう userId を持っている（捨てていない）
- 保存コメント行 withUid ほぼ100%（userId が乗っている）。コメント本文・ギフト・広告（貢献度ランキング）も userId 単位で取れている。
- だから「userId を主キーに1人の人物へ comments[]/gifts[]/ads[] を畳み込む」ことは、新規 storage 書き込みゼロ（読むだけ）で原理的に可能。

## 制約（厳守）
- 記録本体（IndexedDB のコメント記録・チャンク・テールバッファ）は不可侵。新規 storage 書き込みは増やさない（読むだけで畳み込む）。
- venue は hot path（毎フレーム renderSeats が走る）。重い全件再計算・無界蓄積は禁止。上限を設ける。
- 退化リスク最優先で回避：会場の「席・吹き出し・読み上げ連動・ギフト演出・常駐3キャラ」は既存挙動を壊さない。読み上げのゼロ音声回帰・画面溢れ・配信者アイコン取り違え（既知バグ v0.1.793）を再発させない。
- popup の応援アイコン列も既存の見た目・匿名段・診断パネルを壊さない。
- 違法・グレー手法は不可。
