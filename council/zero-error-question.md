# お題: Chrome拡張機能で「エラーを0にする」ための恒久設計

## 状況（事実・地雷マップ）
Manifest V3のChrome拡張機能（content script + Service Worker構成、ビルドツールなしの素のJS）を開発中。
`chrome://extensions`のエラーパネルに繰り返しエラーが表示されるという相談が続いており、
「エラーを0にする」ための根本対策を検討したい。ただし過去の調査で、現状のエラーは
以下の2系統に分類されることが分かっている。

### 系統1: 既に構造的に解決済みのエラー
- `copy.save.failed`（chrome.storage.syncの書込制限120回/分に起因）→ storage.localへ移行し構造的に解消
- `[object Object]`とだけ表示され内容が読めないエラー → ログを整形済み文字列に統一して解消
- 拡張リロード後に残る「孤児content script」が吐く`Cannot read properties of undefined (reading 'sendMessage')`
  → `isOrphaned()`ラッチで検知し、以後のイベントリスナーを自己解除して完全に沈黙させる設計で解消

### 系統2: 意図的に「警告(warn)へ降格」させて残しているエラー（構造上ゼロにできない）
- `copy.save.transient`: 「通信がタイムアウトしました」（`CLIPBOARD_SEND_TIMEOUT_MS=6000ms`超過）
  - 原因: MV3のService Workerは呼び出す(`chrome.runtime.sendMessage`)とアイドル状態から起こされるが、
    起床に数百ms〜数秒かかることがあり、その間にタイムアウトする
  - 対処方針: 「ユーザー対処不能」「コピー履歴は24時間で失効する揮発データなので1件の欠落は許容範囲」
    という理由で、赤エラーに積まず60秒スロットルのwarnに固定する設計にした
  - 過去に「タイムアウト時の遅延リトライ」実装は"過剰設計"として明示的に却下した経緯がある
- chrome.storage.local の容量/書込スロットル系エラーも同様にwarn降格

### 直近バージョンの変遷（CHANGELOG）
- v7.7.7: storage.local移行でcopy.save.failed根治、ログ可観測性改善
- v7.7.8: 孤児content script対策（isOrphanedガード）
- v7.7.9: 実コードのバグではなく「chrome://extensionsのエラーパネルが古い行番号のエラーを
  表示し続ける」表示上の誤認、およびOneDrive配下開発での非アトミック書込による
  「実在しない構文エラー」表示への対策（ビルド識別子刻印、OneDrive外ミラー運用）

## 問い
1. 「エラー0」という目標そのものについて、上記の地雷マップを踏まえたときに、
   目指すべきは「表示件数0」なのか「ユーザーが対処可能な・実害のあるエラーが0」なのか。
   MV3のService Workerライフサイクル（アイドル→終了→再起動）という構造的制約がある中で、
   「エラー0」を素朴に目指すことの危険性・落とし穴を指摘してほしい。
2. 系統2（意図的warn降格）のエラーを、warnにすら出さず完全に消す方法があるとすれば何か。
   ただし「ユーザーに見せない」ことと「本当に問題が起きていないこと」は別物である点に注意し、
   隠蔽になっていないかも批判してほしい。
3. 開発者（人間）が「頻繁にエラーが出る」と感じる体験そのものを改善する方法
   （エラーパネルの運用・可観測性ツール・ダッシュボード等）を提案してほしい。
   コードのエラー発生率を下げるアプローチと、エラー"を見る頻度・見え方"を変えるアプローチの
   両方を検討してほしい。
4. Service Workerのコールドスタート起因のタイムアウトを構造的に減らす技術的な打ち手
   （例: keep-aliveパターン、事前ウォームアップ、タイムアウト値の動的調整等）を、
   実装コストとMV3の制約（chrome.alarms等の許可されたAPIの範囲内）を踏まえて提案してほしい。
