お題: status(診断ページ)の配信カードにある「🌐 WEBサイトURLで見る」ボタンを押したとき、ユーザーが見たいのは「応援ライブビュー(live-view.html?lv=...)と同一の画面」である。最小・確実に実現する方式を1つに決めたい。

== 確定済みの事実(実コードで裏取り済み・推測しないこと) ==
1. 拡張内「応援ライブビュー」= `chrome-extension://<id>/live-view.html?lv=<lv>`。
   - 中身は薄いシェルで、本物の `popup.html?inline=1&dock=liveview&lv=<lv>` を【iframe で全面埋め込み】している。
   - だから popup そっくりそのまま(配信者カード・応援レーン段組み・数字カード・ギフト貢献度…)が出る。
   - dock=liveview = 受動ビュー(storage 書かない/watch 注入しない/外部 fetch しない)。
   - これは chrome-extension:// 内ページ=【拡張が入っている本人だけ】見られる。リアルタイム。
2. 「🌐 WEBサイトURLで見る」ボタン= 今は status の現状スナップショットをサーバー(api/status.js Vercel+Upstash)に
   POST 送信し、純Web版 `https://app.tsuioku-no-kirameki.com/?v=<token>` を新規タブで開く。
   - 純Web版は【拡張なしで他人に共有できる】。データは送信した時点のスナップショット(リアルタイムではない)。
   - 純Webにも `/live-view?v=<token>` があり、応援レーンを「本物の描画関数(paintStoryUserLaneDomFilled/
     buildPersonTileEl)」で“そっくり”再描画している(が、これは応援レーンだけで、popup 全体の iframe 埋め込みではない)。
3. つまり「拡張内 live-view(?lv=)= 本物popupのiframe・本人専用・リアルタイム」と「純Web版(?v=)=共有可・スナップショット・
   応援レーンのみ再現」は、技術基盤も用途も別物。
4. 純Web /live-view?v= の実装現状(裏取り済み)= laneMirror(応援レーン)だけを本物 paintStoryUserLaneDomFilled で
   再描画している。statCardsMirror(数字カード)は受信するが、配信者カード・ギフト貢献度・diag は出していない
   =popup 全体そっくりではない。案B(純Web を popup 全体そっくりに)は、この差を埋める実装が必要=重い。

== 論点(ここを決める) ==
ユーザーの「WEBサイトURLで見るを押すと応援ライブビューと同一画面にしたい」は、次のどれを意味するか/どれが最善か:
- 案A: ボタンの遷移先を、純Web状態速報(?v=)ではなく【拡張内 live-view.html?lv=<lv>】に変える。
   = 一番“同一画面”だが、共有(拡張なしで他人が見る)はできなくなる。送信も不要になる(別タブで本人が見るだけ)。
- 案B: 純Web版(?v=)側を、応援レーンだけでなく popup 全体そっくりに寄せる(純Web live-view を強化)。
   = 共有可のまま“同一画面”に近づけるが、実装が重い(popup 全体の純Web移植 or iframe 方式の純Web版)。
- 案C: ボタンを2つに割る/文言で区別する。「①この画面で見る(拡張内 live-view・本人用)」と「②URLを共有(純Web)」。
   = 用途の取り違えを無くすが、ボタンが増える。

- 具体案: 触る画面・最小の実装ステップ・検証方法

== 制約(過剰実装を避ける) ==
- 単純だが確実に。大規模な作り替え(popup全体の純Web全面移植・新フレームワーク)は基本不可。やるなら別フェーズ提案に留める。
- 拡張内 live-view(?lv=)の iframe 方式・popup 本体・会場・レーンの見せ方は壊さない。
- 「リアルタイムで本人が見る(拡張内)」と「スナップショットを他人に共有(純Web)」の用途差をユーザーが取り違えない誠実な設計を高く評価する。
- storage read を増やす案は反論欄で自己申告する。
