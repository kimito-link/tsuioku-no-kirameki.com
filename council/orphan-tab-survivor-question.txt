【お題】Chrome 拡張(MV3)で「Alt+Tab に出てこない裏 watch タブ(孤児タブ)」が生き残る問題を根治する設計

# 背景(実コード・実機診断で確定した事実)
- ニコ生コメント記録 Chrome 拡張(MV3)。watch タブに content script が常駐してコメントを記録する。
- 過去に「自動巡回(autopatrol)」機能が、ランキング上位の配信を `chrome.tabs.create({ url, active: false })`
  で【裏タブ】として開いていた。active:false なので Alt+Tab に出ないが content script は普通に走り、
  「記録中・視聴中」になる。
- この自動巡回は現在 KILL_SWITCH で完全停止済み(`AUTOPATROL_KILL_SWITCH = true`、getAutopatrolEnabled は
  常に false を返す)。よって【新規の裏タブはもう開かれない】。
- 別の真因も判明済み=以前ユーザーの Chrome に【同じ拡張の古い重複インストール(別ID・旧バージョン)】が
  入っていて、それが裏で autopatrol を動かし裏タブを開いていた。これは既に削除済み。

# 今ユーザーが踏んでいる症状(実機診断 JSON で確定)
- 状態速報(status.html)の「視聴中の配信」に lv350813252 が出る。
- 実機診断では content script が完全に生きている(recording:true, NDGR を 0.8 秒前に受信, video 要素 1個)。
- だが Alt+Tab にそのタブが出てこない=【裏タブ(active:false)】として生き残っている。
- 状態速報が重い・カクつくという体感もある(裏タブが CPU/storage を食う疑い)。

# 既存の掃除ロジック(これが取りこぼす)
拡張の background SW は起動/更新時に sweepOrphanAutopatrolTabsOnce() を1回走らせる。これは
chrome.tabs.query({ url: 'https://*.nicovideo.jp/watch/*' }) で watch タブを列挙し、各タブについて:
  - tab.active が true(前面で見ている)なら絶対に閉じない(誤爆防止)
  - URL に `#nls_autopatrol=1` マーカーが残っている → 孤児として閉じる
  - マーカーが無くても、その lv が autopatrol の visited 履歴(自分が過去に自動で開いた lv の集合)に
    在る → 孤児として閉じる
  - それ以外(マーカー消失かつ visited 履歴に無い lv) → 閉じない(=取りこぼす)

【取りこぼす理由】
  (1) ニコ生の SPA がページ遷移で URL ハッシュ `#nls_autopatrol=1` を消して素の watch URL に正規化する。
  (2) 古い重複拡張が開いたタブの lv は、今の拡張の visited 履歴には入っていない(別拡張だったから)。
  → 「マーカー消失 かつ visited に無い」孤児タブは現状の掃除では永久に拾えない。

# 制約・絶対に壊してはいけないこと
- ユーザーが【自分で手動で開いて今まさに視聴している watch タブ】を絶対に閉じてはいけない(最重要)。
  手動視聴タブは visited 履歴に無い・マーカーも無い=「取りこぼす孤児」と見分けがつかないのが難しさの核心。
- 記録(録画)・手動視聴に影響を与えない。
- MV3 の background は service worker=常駐できない(イベント駆動・すぐ寝る)。タブを監視し続ける常駐は不可。
- ユーザー環境を壊さない(過去に検証用 navigate で backfill を壊した事故あり=自動で watch タブを触るのは慎重に)。
- 過剰実装を避ける(最小ブラスト半径)。

# 問い(設計判断)
裏タブ(active:false)の孤児を、手動視聴タブを誤爆せずに、どう安全に処理するのが最善か。
候補を比較し、推奨を1つ挙げてほしい。各候補の「手動視聴タブを閉じる危険性」「MV3 SW 制約との相性」
「実装の小ささ」を必ず評価すること。

候補A: 「active:false かつ content script が autopatrol/孤児由来だと自己申告したタブ」だけ閉じる。
  content 側が起動時に sessionStorage 等で「自分は autopatrol タブか(URL に過去マーカーがあったか/
  source=autopatrol で記録開始したか)」を覚えておき、background がそれを問い合わせて閉じる。
  手動視聴タブは自己申告しないので誤爆しない。

候補B: タブを自動で閉じるのをやめ、status の「視聴中の配信」表示側で「このタブは Alt+Tab に出ない
  裏タブ(active:false)」だと判定して警告し、ユーザーに手動で閉じさせる導線(ボタン)を出す。
  自動で閉じない=誤爆ゼロだが、生き残ったタブの CPU/storage 消費は続く。

候補C: 掃除の対象判定を「active:false(裏タブ) かつ そのタブの content script が記録している lv が
  『今ユーザーが前面で見ている別タブの lv』と重複している」等の状況証拠で広げる。

候補D: その他(あなたの案)。

最も重視するのは「手動視聴タブを絶対に誤爆しない」かつ「MV3 SW の制約下で確実に動く」かつ「最小実装」。
