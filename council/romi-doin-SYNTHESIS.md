## 統合役による裏取り（会議出力の事実検証）

会議の素材は有用だが、2点で星野ロミ思想を**誤読**している。一次調査レポートに当てて補正した。

1. **「自動ツイート」は思想の核とむしろ逆。**
   - ソース版レポート: 星野ロミの実装判断は「会話の重さを軽くし、低圧リアクションに寄せる」「SNSを作らない」（`deep-research-report -sorcecode.md` 17行）。自動ツイートはユーザーに**SNS投稿の“圧”**をかける＝低圧設計の逆。
   - 複数モデル自身が「スパムでX規約違反リスク」「ブランド毀損」を自己申告（log 33,205,208行）。**思想にも制約（X規約順守）にも触る。**
2. **「供給側インセンティブ」の本質を取り違えている。**
   - 公開版レポート 67-69行: 供給インセンティブとは「**供給者＝元サイト/主催者が“数字で見える得”を得る**」こと（Share Videos=再生数連動報酬、mmake=“作ったサイトを宣伝してもらえる”＝露出という外部報酬）。
   - 動員ちゃれんじの**供給者は「イベント主催者＝推し本人・幹事」**。多数派Aは「一般ユーザーに拡散させる」発想で、供給者本人への“得”が薄い。Bの方が思想に忠実。
3. **「検索直結リッチリザルト」(openrouter)は即時価値の柱と矛盾。** Google構造化データの審査依存で、1スプリントで価値が出る保証が薄い（モデル自身も log 118行で審査落ちリスクを認める）。SEOは“結果”であって“最初の1機能”ではない。

→ 結論: **B（応援の即時可視化＋主催者ダッシュボード）を主軸に、A/Cの良い部分（ワンクリック動線・既存資産の再利用）を吸収**し、自動投稿は「強制」でなく「任意の手土産」に格下げする。これが四本柱を最も健全に満たす。

# 最終1案（統合）

## 結論
最初に作るべきは **「応援が“今この瞬間”積み上がるのが見える＝動員ライブメーター＋主催者リアルタイム・ダッシュボード」**。
ファンは1タップで「行く／応援する」を表明、その数が**イベントページのメーターに即時に積み上がって見える**。同時に**主催者（推し本人・幹事）専用ダッシュボード**に「今日◯人、◯県から、メッセージ◯件」が数字で返る。これを最初の1スプリントの目玉にする。

## 根拠（四本柱との対応）
- **① 摩擦除去**: 既存の「参加登録」を**1タップの意思表明（ログイン済みなら即時・未ログインは表明だけ先に通す）**へ短縮。価値到達＝「押した瞬間メーターが伸びる」即時フィードバック。検索→着地→即数字、の星野式「結果画面へ直行」を踏襲。
- **② 供給側インセンティブ（最重要）**: 供給者＝**主催者本人**に「応援数・都道府県分布・メッセージ」を**リアルタイムの数字**で返す。これは Share Videos の「供給者が得する」/ mmake の「露出という外部報酬」の健全な再現。主催者が**自分から告知したくなる**＝供給（イベント立ち）が自然増。
- **③ 参入障壁を機能に埋め込む**: メーター・都道府県分布・達成バッジ（「100応援」「全47都道府県制覇」）・過去イベントの**推移グラフ**という**反復して見たくなる資産**を主催者ページに蓄積。データが貯まるほど離脱コストが上がる（推移グラフ＝星野式の継続コンテンツ）。
- **④ 計測志向と即時価値**: 「表明クリック→来場/参加確定」のファネルを最初から計測。ボタン文言・メーター演出を A/B 可能に。検索意図（「〇〇 生誕祭」）の着地点をこのメーターページにしてSEOの受け皿に。

## 反論・リスク（と対策）
- **R1: 数字が伸びないイベントで“閑古鳥”が可視化され、主催者が傷つく/逆効果。** ← 主催者側で**目標値・公開閾値を設定**でき、小規模時は「累計」より「直近の勢い（24h増分）」を主表示。ゼロ表示を避けるデフォルトに。
- **R2: 「動員数」の水増し・不正表明。** ← Xログイン必須＋同一アカウント1イベント1票、IP/デバイスのレート制限。`hermes`/`llama`が挙げたCAPTCHAは最終手段（摩擦になるので段階導入）。
- **R3: 多数派の自動ツイートを捨てる判断への反論（拡散が減るのでは）。** ← 拡散は**強制でなく任意の「シェアカード（自分の応援が映った画像/OGP）」**として残す。低圧・編集可能・OGP画像で“映え”を作り、規約圏内で自然拡散。星野思想の「便利だから自分で広める」を圧をかけずに実現。
- **R4: リアルタイム＝WebSocket実装で月0円が崩れる懸念（批判役deepseekの趣旨）。** ← **真のリアルタイムは不要**。tRPC + ポーリング（数秒〜10秒間隔の`useQuery` refetch）で「ほぼ即時」を達成。星野式マッチャも“5分バッチで十分”という現実主義（ソース版19行）。WebSocket/位置SDK等のスタック外技術は**入れない**。

## 具体案（最初の1スプリント＝約2週間で作れる粒度）
既存資産（参加登録・都道府県可視化・応援メッセージ・統計ダッシュボード・event共通モジュール）の**再配線**が中心なので新規コストは小さい（実装役coderの指摘＝低コスト路線を採用）。

1. **DB（Drizzle）**
   - `event_cheers`（id, event_id, user_x_id, prefecture, created_at, source）— 応援/参加表明の1行。既存の参加登録テーブルがあれば`source`列追加で流用。
   - 集計は**マテビュー不要**、`count()` + `group by prefecture` のクエリで足りる規模。
2. **API（tRPC）**
   - `event.cheer(eventId)` … 1タップ表明（冪等：同一ユーザー再押下はトグル）。
   - `event.liveStats(eventId)` … `{ total, last24h, byPrefecture, messages }` を返す。フロントは`useQuery`を5–10秒`refetchInterval`でポーリング。
3. **フロント（Expo Router）**
   - イベント詳細に**動員メーター**（累計＋直近24h増分のアニメーション）と**47都道府県ヒートマップ**（既存可視化を流用）。
   - **主催者ダッシュボード**（`creatorXId`一致時のみ表示）: 数字・分布・メッセージ・推移グラフ（過去イベント横断）。
   - 1タップ「行く／応援」ボタン（プライマリ）。押下後に**任意**で「シェアカードを作る」を提示（自動投稿はしない）。
4. **シェアカード（任意・低圧）**
   - OGP画像を動的生成（イベント名＋現在の動員数＋自分のアイコン）。Xシェアは**ユーザーが文面を見てから**送る。テンプレは短文＋ハッシュタグのみ、編集可。
5. **計測 / A/B**
   - `cheer_click` / `cheer_success` / `sharecard_open` / `share_sent` を記録。メーター演出ON/OFFと文言の2バージョンでA/B（フラグ切替）。
6. **SEO受け皿**
   - イベントページに `Event` JSON-LD を付与し、「〇〇 生誕祭」等の検索の着地をこのメーターページにする（リッチリザルト“審査”には依存せず、まず構造化データだけ入れておく）。

### 共通モジュール方針
この機能は `modules/event`（surechigai-romi と共通）の上に**`cheer`サブ機能**として載せ、ドメイン/スキーマ名に密結合させない。doin-challenge と surechigai-romi の両方で再利用できる形にする（HANDOFFの「doin-challenge.com への modules/event 移植」とも整合）。

## 一言まとめ
**「星野ロミだったら」自動ツイートで拡散を強制するのではなく、“応援が数字で積み上がるのが見える”体験を作り、その数字を主催者（供給者）に即時に返して「自分から告知したくなる」エンジンを回す。** 摩擦除去×供給側インセンティブ×反復コンテンツ×計測を、既存資産の再配線だけで1スプリントに収める——これが思想の健全な核を最大化する最初の1機能。
