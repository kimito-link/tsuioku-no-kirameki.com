# 問い(これに答えて)
1. 4種のグラフのうち「エラー再発防止」に最も効くのはどれか、優先順位は。星野ロミ式(既存データ活かす=changelog 177版/impact-map/spine は既にある・過剰実装回避・腐らせない)。全部作るとして段階順は。
2. ① コミット履歴グラフを地図にどう描くか。git log の生グラフ(Git Graph 風)を docs に複製するのは過剰(腐る・重い)では? changelog の {version,summary,items} を「系統(タグ)」でグルーピングし、バグ修正の系譜(例: 記録件数系=v0.1.792→804→838→839)を枝で繋ぐ「修正系譜マップ」の方が再発防止に効くのでは? どう自動生成するか(changelog の items から系統を機械分類できるか・classifyFeatureCategory を流用できるか)。
3. ② 依存グラフ(impact-map がほぼ空)をどう充実させるか。全ファイルの import を静的解析して「このファイルを変えると波及する先」を出す。ノード数500超で巨大化する過剰リスク。「変更時に影響大(3機能以上波及)」だけ出す既存 impact-check の発想を地図に。決定的生成で腐らせない設計。
4. ③④ は既にある(spine/feature-sitemap)。これを「GitHub 風の枝分かれ/接続線つき」ビューに強化する価値はあるか過剰か。SVG/canvas で線を引くのは no CDN で重くないか。code-tree の details 折りたたみで足りるのでは。
5. 「全部地図化」で情報過多・腐り・メンテ不能になる過剰リスク(批判役は必ず穴を指摘)。4枚も地図が増えると誰も見ない/生成が重い/git log 複製は即腐る。再発防止に本当に効く最小セットは何か。やってはいけない過剰実装を1つ以上。

# 制約(星野ロミ式)
記録本体不可侵・新storage不要(docs生成系)・決定的生成・既存データ活かす(changelog/impact-map/spine/classifyFeatureCategory)・過剰実装回避・腐り検知(--check)を全グラフに効かせる・no CDN(SVGは手書き or 軽量・外部ライブラリ禁止)・手で書く辞書は最小。

出力は『結論 → 根拠 → 反論・リスク → 具体案』の4ブロックで。具体案は「どのグラフを・どの既存データから・どう自動生成するか」「再発防止にどう効かせるか」「腐り検知の拡張」を実装の置き場所(scripts のどこ)まで。
