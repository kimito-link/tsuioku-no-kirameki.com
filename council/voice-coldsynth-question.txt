【お題】読み上げの取りこぼしを最小にする（合成が遅い実機での最適化）

## 現状（すべて実機実測値・推測ではない・2026-08-04）

ノートPCの実配信(視聴者3904人・コメント9937件)で計測1475分ぶんの実測:

```
処理時間      4405ms/件
実効上限      2
間引き        199件
voiced率      52.1%（直近40.6%）
合成失敗      52件 ← 【全件が「時間切れ」】
判定          coldsynth
体感遅延      7.7秒（平均5.3秒）
需要28.3/分 vs 供給13.6/分  ← 供給が需要の半分以下
```

処理時間4405msの内訳（3分解の実測）:
```
合成待ち   3343ms  (76%)  ← 支配的。VOICEVOXの合成そのもの
再生準備     35ms  ( 1%)
実再生     2204ms  (50%)  ※合計が100%を超えるのは別EMAのため
```

**同じPCの数時間前の実測（比較用）**:
```
合成待ち   1310ms → 3343ms  【2.5倍に悪化】
実再生     3922ms → 2204ms  （改善）
合成失敗      0件 →   52件  【新規発生・全部時間切れ】
```
つまり「実再生が重い」問題から「合成が遅い」問題へ支配要因が移った。

## 実装の現状（コードを読んで確認済み・推測なし）

- 合成は audio_query → synthesis の2段（src/lib/voicevoxClient.js）
- タイムアウト: audio_query 3000ms / synthesis 8000ms
- 既に打ってある最適化:
  - outputSamplingRate=16000（v0.1.1063・実測で合成30%高速化 1465→1025ms）
  - outputStereo=false
  - 12kHzはこれ以上速くならず音質だけ落ちると実測済み
- 読み上げ文字数上限 60文字（buildVoiceReadingText）。ただし実際の平均は20〜30文字相当で
  上限に届いていない＝ここを下げても効果は限定的（既に検証済み）
- 速度補正（playbackRate）実装済み。速度底上げ+0.35が659件に適用され、速度飽和3件
- キュー上限は 6000ms(予算) ÷ 処理時間 で動的算出、床4・天井8
- 時間ゲート（安全網）8000ms。予算は必ずこれ未満という不等式をテストが固定

## 制約（守れない案は不採用・前回の会議で実現不可能案が結論になった反省）

1. **Chrome拡張(MV3)である**。JSサンドボックスから
   プロセス列挙・ファイアウォール設定読み取り・OSの優先度変更は【できない】。
   ネイティブメッセージングホストの配布は配布形態を変えるため今回は不可。
2. VOICEVOXは**ユーザーのPCで動く外部アプリ**。拡張から設定を変更できない。
   （話者の選択・speedScaleなどaudio_queryのパラメータは拡張から渡せる）
3. 外部送信を増やす案は不可（ローカル保存のみの方針）。
4. CWS審査に通る必要がある（v0.1.1244が2026-08-03に公開されたばかり）。
5. 「推測で直す前に測る」がこのプロダクトの規律。
6. 過去の地雷: 時間ゲートを再生1本ぶんより短くすると【全stale＝音声ゼロ】に落ちる(v0.1.773)。
   件数ゲートを主軸にする設計(わんコメ式)は不可侵。

## 検討してほしいこと

Q1. 合成待ち3343msを削る現実的な手は何か。優先度順に。
    拡張側から渡せるものだけで考えること（audio_queryのパラメータ・リクエストの出し方・
    並列度・プリフェッチ・キャッシュ等）。VOICEVOX本体の設定変更を前提にした案は
    「ユーザーに案内する話」として別枠に分けること。

Q2. 供給13.6/分 < 需要28.3/分 のとき、何を捨て何を読むべきか。
    現状は「最古から捨てる」(FIFO)。これが最適か？
    代替案（短いコメントを優先／同一人物の連投を1件に統合／読み上げる人数を絞る等）の
    是非を、【応援の可視化】というこのプロダクトの目的に照らして判定すること。
    ※ただし「誰の声を読まないか」を機械が選ぶことの是非も論点に含めること。

Q3. voiced率52%（半分が読まれない）は、ユーザーにどう伝えるべきか。
    現状は状態速報に数字が出るだけ。配信者は気づけない。
    「読み上げが追いつかないので簡潔モードに切り替えました」のような
    自動降格＋通知は有効か、それとも余計か。

Q4. 実装順序。1つだけ先に出すなら何を出すか。
    次の版で審査を通す必要があるため、審査リスクの高い変更は避けたい。

## 判定基準（この順で優先）

1. 取りこぼしが減ること（voiced率が上がる）
2. 遅れが増えすぎないこと（体感遅延7.7秒をこれ以上悪化させない）
3. 実装が小さく、審査リスクが低いこと
4. 速いPCでの挙動を変えないこと（退行させない）
