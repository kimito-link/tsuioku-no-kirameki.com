# お題: 会場の席が「時間が経つと減る」問題 — 誰を残し誰を入れ替えるか

## 背景(司令塔が実コードで確認済みの事実。ここは推測でなく確定)

ニコ生視聴を盛り上げるChrome拡張。「会場モード」は、応援した視聴者を客席アイコンとして並べてライブ会場の満員感を演出する。

- 参加者の集約(誰が応援したか)は **累積で増え続ける**(`mergeUserLaneAggregates`)。減らない。
- だが会場に表示できる **席は最大150**(`VENUE_FULLSCREEN_MAX_SEATS=150`)。これは性能の安全弁(席DOMを起動時に固定数生成。増やすほど重く、3時間配信で"ページが応答しません"に直結した過去あり)。
- 150を超えると **入れ替え制**になる。`rankVenueParticipants` が参加者を下記の優先度でソートして `slice(0,150)` で切る:
  - 現状ソート: ①実サムネ持ち(顔写真設定済み) → ②ギフト参加 → ③**最終発言が新しい順(lastAt降順)** → ④発言数
- **「減る」の正体** = ③のせいで、満席後にしゃべった人が来るたび、一番長く黙っている人がランキングから押し出されて席を失う。
- 一度落ちた人は `assignVenueSeats` の sticky 維持にすら届かない(ランキングで先に消えるため)。

## ユーザーの要望と気づき(生の声)

- 「せっかく満席にしないといけないのに減らす意味がわからない」= 一度入った人は残したい。満員のまま増えてほしい。
- 「サムネあり優先で」「発言数多い人優先で」= よく応援した常連・顔出しの人を残したい。
- 「さむねありや発言数多い人で150こえるのはなかなかない」= 実機でもサムネあり＆常連は150に届かない。押し出されるのは匿名・1〜2回だけの人。
- 「あーそうか、最近喋った人も重要」= ただし"今まさに盛り上げている人"を締め出すのも違う、と気づいた。

## 実機の実数(今日のfastDiagより)

- 来場 1,160人 / 記録コメント 3,134件 / ユニーク発言者 482人(intercept) / 顔写真あり avatarMapSize=5(うちニック一致1)。
- つまり「サムネあり」はごく少数。「発言数が多い常連」も数十人規模。150席が常連＋顔出しで埋まることは実際ほぼ無い。

## 問い(これに答えてほしい)

150席を超えて入れ替えが必要になったとき、**誰を残し誰を降ろすか**。具体的には:

1. **発言数(多い=常連)・サムネ有無(顔出し)・最近の発言(今盛り上げてる)** の3要素をどう統合して優先度を決めるか。単純な一本ソートで決めきれるか、それとも「枠を分ける(常連枠/新着枠)」べきか。
2. 「一度入った人を降ろさない(満席維持)」と「今しゃべった新規も座らせたい」は、150という有限席では両立しない瞬間がある。この矛盾をどう捌くか。
3. 実装は `rankVenueParticipants(participants, maxSeats)` の純関数1つの中で完結させたい(prevSeatByKey=前回の席割りを引数で渡すことは可能)。過度な新状態を持たない、テストしやすい案が望ましい。
4. 落とすしかない人が出るとき、ユーザーに「減った」と感じさせない見せ方(満席維持・"+N人応援中"テキスト等)はどうするか。

## 必ず検討してほしい2つの観点(ユーザー指定)

### 観点A: 「並列」の発想 — 席集合を分割して奪い合いを消す
今は「150席という1つの土俵に全参加者を並べ、上位150だけ残す」=単一ランキングの奪い合い。これだと
「常連が新着に押し出される / 新着が常連に締め出される」の二者択一が原理的に避けられない。
そこで **席を複数の枠(プール)に並列分割**する案を真剣に評価してほしい。例:
  - 常連枠(発言数上位) / 顔出し枠(サムネあり) / ライブ枠(直近に発言) / にぎやかし枠(残りの匿名)
  - 各枠に席数を配分し、**枠ごとに独立してランキング**すれば、常連と新着が同じ枠で奪い合わない。
  - 枠の重複(常連かつ顔出し)はどう扱う? 配分はどう決める(固定 or 人数比動的)? 空き枠の融通は?
この「並列分割」が単一ソートより本当に優れているか、過剰な複雑さでないか、批判役は特に詰めること。

### 観点B: 「星野ロミならどう設計するか」(この拡張の設計思想の軸)
星野ロミ的発想 = **重くしない・有界・割り切る・体感(満員に見えるか)を最優先・凝った正確さより軽さ**。
彼ならこの問題をどう捌くか、という視点で1つ案を立てること。想定される方向:
  - 150を増やすより「満員に見えればいい」を取る。落ちた人は "+N人応援中" の数字で吸収。
  - O(N²)や毎フレーム全走査を絶対に作らない。ソートは1回・有界。
  - 「誰を残すか」を厳密に最適化しすぎない。ざっくり良ければ体感は十分、という割り切り。
  - 演出で「減った」を感じさせない(満席を常に埋める・空席を作らない見せ方)。
この思想から見て、観点Aの分枠案は「凝りすぎ」か、それとも「枠を分けたほうがむしろ軽い・単純」か、評価すること。

## 制約

- 席DOM上限150は動かさない前提で考える(性能のため)。150を増やす案は副次的にだけ触れてよいが主軸にしない。
- 新しい永続状態やstorage書き込みを増やさない(storage飽和の過去事故あり)。純関数＋前回席Mapの引数渡しで完結が理想。
- 匿名(userIdはあるが顔写真なし=ゆっくり顔)も満員感のため席に座れる現仕様は維持。

## 出力フォーマット

`結論 → 根拠 → 反論・リスク → 具体案(rankVenueParticipantsのソート/分枠ロジックを擬似コードで)` の4ブロックで。
