# 結論：4 枚の地図を「1 つの動的な『再発防止シミュレーター』」に統合する

「4 種類のグラフを並列して表示する」のは、情報過多で「誰も見ない地図」を量産する過剰実装です。
**「エラー再発防止」に特化する場合、最も効くのは「①コミット履歴（修正系譜）」を軸とし、そこに「②依存関係」と「③データフロー」を「影響範囲」として重ね合わせる「3 層構造の動的グラフ」**です。

「GitHub 風の枝分かれ」を単なる可視化にするのではなく、**「もし今、このバグを直そうとしたら、どこが壊れるか（②）」「その直しが、過去のどの失敗（①）を踏まえたものか」を直感的に繋ぐ「故障予測マップ」**として再定義します。

---

# 根拠：なぜ「4 枚並列」ではなく「1 枚の動的統合」なのか

1.  **再発防止の本質は「文脈の紐付け」**:
    過去のバグ（①）を「なぜ直したか」だけでなく、「その修正が現在のコード（②③）にどう影響するか」を同時に見なければ、再発防止は形骸化します。例えば「記録件数系（①）」を直す際、それが「配信者除外（①）」と共通の依存モジュール（②）を共有しているなら、そこを触れば両方のバグが再発するリスクがある、という**横断的な知見**が得られます。
2.  **星野ロミ式（既存データ活用・過剰回避）の極致**:
    *   **①コミット**: `changelog` の JSON 構造は既に「修正内容」の宝庫。これを Git の生ログ（生々しく重い）に変換せず、**「バグの系統（タグ）」でグループ化した「修正ツリー」**として再構築します。
    *   **②依存**: `impact-map.json` が空なのは、静的解析の結果を「全ファイル」で出力し、ノイズが多すぎて意味をなさないからです。「変更時に影響大（3 機能以上波及）」というフィルタを適用し、**「危険な変更点」だけをノード化**すれば、ノード数は 500→50 に減り、視認性が劇的に向上します。
    *   **③④**: これらは「地図の背景（地形）」として機能します。これらを独立した地図にするのではなく、**「修正系譜（①）が通るルート」**として描画します。

3.  **腐り検知の最適化**:
    4 つのグラフを別々に生成・チェックすると、整合性が取れなくなります（例：changelog は更新されたが、impact-map は古い）。**「1 つの生成スクリプトで、4 つのデータを同時に読み込み、1 つの SVG/JSON として出力し、1 つのチェックパスで整合性検証」**を行うことで、腐りを即座に検知できます。

---

# 反論・リスク：批判役の視点（穴を突く）

*   **「情報過多で視認性が崩れる」**:
    4 種類のデータを 1 枚に詰め込むと、線が交差して「蜘蛛の巣」になり、何が何だか分からなくなるリスクがあります。特に SVG で 500 以上のノードを描くとブラウザが重くなる可能性があります。
    *   *対抗策*: **「デフォルトは最小セット（修正系譜のみ）」**とし、ユーザーが「依存関係を表示」や「データフローを表示」をオンオフできる**インタラクティブなフィルタリング**を必須とします。また、SVG ではなく、軽量な Canvas または CSS Grid を活用した「階層的な展開/折りたたみ」で描画し、重さを抑えます。
*   **「自动生成の精度（機械分類）が怪しい」**:
    `changelog` の `items` から「バグの系統」を機械的に分類するのは、自然言語処理なしでは難しいです。誤分類が起きれば、誤った「再発防止」を誘導します。
    *   *対抗策*: 機械分類は「候補」にし、**既存の `classifyFeatureCategory` の辞書（v0.1.840）を「正解ラベル」として流用**します。`items` に含まれるキーワード（例："記録", "DOM", "除外"）を辞書と照合し、一致しないものは「未分類（人手確認が必要）」として黄色くマークします。
*   **「生成コストと腐り検知の矛盾」**:
    複雑なグラフ生成は時間がかかり、CI/CD のフローを遅くします。
    *   *対抗策*: 生成スクリプトは**「差分生成」**に特化させます。変更されたファイルや `changelog` のみを読み込み、既存のグラフ構造を更新するアルゴリズムを実装します。完全再生成は「重大なリファクタリング時」のみとし、通常は高速な更新のみを行います。

# 具体案：『再発防止シミュレーター (Re-Prevent Simulator)』の設計

**目標**: `npm run map:simulate` で、**「過去のバグ系統」×「現在の依存リスク」×「データフロー経路」**を 1 枚のインタラクティブ SVG に統合し、腐り検知付きで出力する。

### 1. どのグラフを・どの既存データから・どう自動生成するか

**コア概念**: **「修正系譜マップ（Bug Lineage Map）」**をベースに、他のデータを「レイヤー」として重ねる。

*   **ベース（①コミット履歴グラフ）**:
    *   **データ源**: `src/lib/changelog.js` (177 版分)
    *   **生成ロジック**:
        1.  `items` のテキストを `classifyFeatureCategory` の辞書でスキャンし、**「バグタグ」**（例：`stale-DOM`, `record-zero`, `exclude-streamer`）を自動付与。
        2.  同じタグを持つバージョンを**「系統（Branch）」**として連結。
        3.  結果：「記録件数系」という一本の枝に、v0.1.792 → v0.1.804 → v0.1.838 が繋がる**「修正ツリー」**を生成。
        4.  *出力*: `docs/map/lineage-graph.json` (ノード：バージョン、エッジ：系統関係)

*   **レイヤー 1（②依存グラフ）**:
    *   **データ源**: `scripts/feature-map.mjs` (静的解析ロジック) + `impact-map.json` (空だが構造はあり)
    *   **生成ロジック**:
        1.  全ファイルの `import` 関係を解析するが、**「影響範囲（波及先）が 3 つ以上」**のファイルのみを「重要ノード」として抽出

### groq/llama-3.3-70b  [爆速の視点]  (1721ms)
========================================================================
## 結論
エラー再発防止に最も効くのは、コミット履歴グラフを changelog の系譜で引けるようにすることです。優先順位は、① コミット履歴グラフ、② 依存グラフ、③ データの流れ、④ カテゴリ折りたたみツリーの順です。

## 根拠
コミット履歴グラフは、過去に同様のエラーをどう修正したかを即座に辿ることができます。changelog の系譜を利用することで、バグ修正の系譜を枝で繋ぐことができます。依存グラフは、全ファイルの import を静的解析することで充実させることができます。データの流れとカテゴリ折りたたみツリーは既にあるため、強化する価値はあるか過剰か検討する必要があります。

## 反論・リスク
情報過多・腐り・メンテ不能になる過剰リスクがあります。4 枚も地図が増えると、誰も見ない・生成が重い・git log 複製は即腐る可能性があります。再発防止に本当に効く最小セットは何かを検討する必要があります。

## 具体案
1. コミット履歴グラフ: changelog の {version,summary,items} を「系統(タグ)」でグルーピングし、バグ修正の系譜を枝で繋ぐ「修正系譜マップ」を自動生成します。classifyFeatureCategory を流用して、changelog の items から系統を機械分類します。scripts/changelog-map.mjs で実装します。
2. 依存グラフ: 全ファイルの import を静的解析して「このファイルを変えると波及する先」を出すことを決定的生成で実装します。scripts/impact-map.mjs で既存の impact-check の発想を地図にします。
3. データの流れとカテゴリ折りたたみツリー: 既にあるため、強化する価値はあるか過剰か検討します。code-tree の details 折りたたみで足りる可能性があります。
4. 腐り検知: --check で腐り検知を全グラフに効かせます。scripts/tree-map-check.mjs と scripts/feature-map-check.mjs で実装します。

**具体案**  

### 1️⃣ 修正系譜マップ（①）
- **生成スクリプト**：`scripts/changelog‑map.mjs`
- **入力**：`src/lib/changelog.js`（177 版 JSON）  
- **処理フロー**  
  1. `changelog` をパースし、`items` 文字列を `classifyFeatureCategory` に流す（既存のカテゴリ辞書を拡張し、**「バグ系統」タグ** を 10 種類程度に追加）。  
  2. 同系統タグでバージョンを時系列にソートし、**「系統枝」** オブジェクト `{tag, versions: [{v, date, summary}]}` を作成。  
  3. 各系統ごとに **SVG `<path>`** で直線＋分岐を描く（ノードは `<circle>`、ツールチップは `title` 属性でバグ概要）。  
  4. 出力先：`docs/maps/repair‑lineage.svg`（決定的生成）。  
- **再発防止への効果**  
  - バグ系統をクリック → その系統の全修正履歴がポップアップ。  
  - 「同系統の過去修正が未適用」かどうかを CI で自動チェック（`scripts/check‑repair‑coverage.mjs` が `tree‑map:check` にフック）。  

### 2️⃣ インパクトサブグラフ（②）  
- **生成スクリプト**：`scripts/impact‑summary.mjs`（既存 `feature‑map.mjs` の拡張）  
- **入力**：全ファイルの `import` AST（`@babel/parser` でパース、外部ライブラリ禁止なので自前の軽量パーサを `scripts/utils/parseImports.mjs` に実装）。  
- **フィルタ**：  
  - 直接/間接インパクト数 **≥3** のノードだけ抽出。  
  - 影響先が **同系統タグ** と一致する場合はハイライト（`stroke: red`）。  
- **出力**：`docs/maps/impact‑summary.svg`（ノードはファイル名、エッジは矢印）。  
- **再発防止への効果**  
  - 変更前に「このファイルを触ると何系統のバグが波及するか」警告を CI で出す。  
  - `tree‑map:check` が生成した JSON と比較し、**新規インパクトが増えていないか** を検証。  

### 3️⃣ データフロー & カテゴリツリー（③・④）  
- **現状利用**：`repo-tree-map.mjs` の `SPINE_STAGES` と `feature‑sitemap` の HTML 折りたたみはそのまま残す。  
- **軽量装飾**：`docs/maps/spine‑flow.svg` と `docs/maps/category‑tree.svg` に **微小な接続線**（`<line>`）だけを追加し、**「どのステージがどのカテゴリに属すか」**
