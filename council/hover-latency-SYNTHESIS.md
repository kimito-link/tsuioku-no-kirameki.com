## 0. 会議の信頼度(先に書く)
- 統括役が落ち、統合を批判役が代行。批判役は「握手の来場者+1 が致命的リスク」を最重要に挙げたが、**司令塔の実測でこれは過大評価と判明**(下記)。統合表は鵜呑みにしない。
- 発散役(qwen3.8-27b)の「遅さの主犯はゼロから viewUri を取ること」という筋は正しい方向。ただし細部(クライアントが末尾IDを持っている前提)は /live/ の実装と食い違う(ページはコメントストリームを受信していない=件数集計はサーバの別ジョブ)。

## 1. 実測で判明した真の内訳(2026-09-15・司令塔が Node で計測)
初回3.5秒の内訳:
| 段 | 時間 | 備考 |
|---|---|---|
| watch HTML 取得 | 約370ms | |
| WS 握手→viewUri | 約190ms | 来場者+1 の副作用はここ |
| **NDGR 浅い遡り(12区画639KB)** | **約3秒** | ★遅さの主犯はここ |
2回目(キャッシュ有)=0.25秒。**握手は主犯ではない**(会議の批判役の前提は誤り)。主犯は NDGR の遡り。

## 2. 結論(1案・第1手)
**ページを開いたら、いま見えている上位N配信を先読みしてサーバのメモリキャッシュを温める(A-1)。** ただし会議の懸念を実測で裁定して以下に絞る:

| 論点 | 決定 | 根拠 |
|---|---|---|
| 先読みするか | **する**。ページ表示直後にバックグラウンドで上位 **3配信**だけ `POST /api/live-recent-comments` を投げてキャッシュを温める | 主犯は NDGR 遡り(3秒)なので、ユーザー操作前に済ませるのが唯一の実時間短縮 |
| 握手の来場者+1 | **許容(むしろ減る)**。先読みは1配信=1握手で上位10人ぶんの viewUri が1回で取れる。ホバーのたびに握手するより握手回数は減る | 実測: 握手は0.19秒・キャッシュ60秒で同配信の以後の握手ゼロ。ユーザー決定(2026-09-14「握手は残す」)とも整合 |
| 本文の置き場 | **現状維持(メモリ60秒・Redis に置かない)** | privacy §14。先読みも同じエンドポイントを叩くだけなので保存の性質は変わらない。会議の「先読み=保存扱いになる」は誤り(取得してメモリ60秒は現行と同じ) |
| Vercel の負荷 | **上位3件・逐次(並列1〜2)・ページ最初の1回だけ** | 会議3体とも「無差別先読みは Hobby の同時実行で危険」で一致。3件に絞る |
| スケルトン表示 | **併用する**。先読みが間に合わない配信(4位以下・深夜で視聴者0)はホバー時オンデマンド+スケルトンで待たせ感を消す | 批判役・ローカルの一致点。実時間短縮(先読み)と体感改善(スケルトン)の両輪 |
| tally で温める(A-2) | **やらない** | 本文を Redis に置くことになり privacy §14 改定+著作権リスク。先読み(A-1)で足りる(お題 F の自答どおり) |

## 3. 第1手の形(最小)
- `live-ranking-entry.js`: `render()` 後、**ページ最初の1回だけ**、上位3配信(`sortByEstimatedConcurrent` の先頭3・pin があればそれ優先)の代表 uid(rankers[0])で `POST /api/live-recent-comments` を投げる(逐次・失敗は握りつぶす)。応答は捨ててよい(サーバ側キャッシュが温まるのが目的)。60秒ごとの再読み込みでは**温め直さない**(握手を増やさない=最初の1回だけ)。
- カードのスケルトン: 既存の「取得中」状態を、骨格(名前行+グレーの帯)にして「待たされ感」を減らす(`liveRecentHoverCard.js` の取得中状態の見た目だけ)。
- ★本文を Redis に置かない・viewUri を保存しない・先読みは最初の1回だけ(60秒ごとに握手を増やさない)。

## 4. 反論・リスク(残す)
- **深夜・視聴者0の配信**: 先読みしても握手/NDGR が取れず遅いまま。→ スケルトンで受ける(実時間は縮まないと正直に)。
- **上位3件だけ**: 4位以下の配信をホバーすると初回は遅い。第2手で「ホバーしそうな配信を予測して広げる」は反応を見てから。
- **Vercel 冷起動**: メモリキャッシュは関数が寝ると消える。先読みの直後にホバーすれば温かいが、時間が空くと再取得。これは Redis を使わない限り構造的に残る(privacy とのトレードオフ)。

## 5. やらない(会議+司令塔一致)
本文を Redis/tally で温める(privacy §14・著作権) / viewUri 保存(却下済み) / 無差別全配信先読み(Vercel 負荷) / クライアントが末尾IDを送る案(ページはコメントストリームを受信していない=前提が崩れている)。
