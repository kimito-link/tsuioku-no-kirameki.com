お題: メインPOP・応援プレビュー・WEB版の3画面を「完全に同じ(フルコピー)」にする方法

# 製品の文脈
Chrome拡張「君斗りんくの追憶のきらめき」。ニコ生の応援コメントをこのPCに記録し可視化する。
3つの画面が「同一で完全(フルコピー)」であることが最重要の設計原則:
- ①POP = 拡張のポップアップ(popup.html)。本体。watch ページ内 iframe(embed_watch)で動く。
- ②応援プレビュー = 拡張内 live-view.html。popup.html を iframe で全面埋め込み(そっくりそのまま方式)。
- ③WEB版 = app.tsuioku-no-kirameki.com/live-view?v=token。拡張なしで見られる純Web公開コピー。

ユーザーは「①=②=③のフルコピー」を100回以上要求している。だが現実は揃わず、ユーザーは
「レーンが全然そろってない・コメントが0とかたくさんある・WEB版が全然ダメ」と言っている。

# データの流れ(実コードで確認済み)
- popup が各種「鏡(mirror)」を chrome.storage.local に publish する:
  - laneMirror(応援レーン: りんく/こん太/たぬ姉/ギフト/広告の5段。cap=各段48件、容量512KB超で半減)
  - northStarMirror(北極星: 貢献度/広告ランキング。cap=各10件=ニコ生本体の1-10位表示に合わせた頭打ち)
  - statCardsMirror(数字カード: 記録/同接/来場)
  - commentTimelineMirror(コメントの流れ。cap=最新60件、totalSeen=渡された配列長=記録総数ではない)
  - topSupporters(応援者ランキング上位10件)
- status ページ(status.html)が上記の鏡を storage から読み、jsonBlob に束ねて:
  - ②応援プレビューへ: KEY_LIVEVIEW_PUBLISH_PAYLOAD に jsonBlob を置く。②はそれを読んで本物の描画関数で描く。
  - ③WEBへ: /api/status に POST(手動ボタン or v0.1.1016で配信中は約2分ごと自動publish)。
- ②③とも「再構築せず status が組んだ jsonBlob をそのまま描く」= drift ゼロを狙った設計。

# いま判明している具体的な食い違い(状態速報の実データ)
ある配信(匿名主体・記録924件・本文コメント808件)の状態速報より:
- 応援レーン鏡: りんく4 / こん太0 / たぬ姉44 / ギフト1 / 広告7 計56 (cap48未満なので削られていない=①と③で件数一致のはず)
- コメント鏡: 30件しかない(記録は808件あるのに)。ラベルは「観測累計30件」だが実際は「今この鏡バッチの母数」で累計ではない
- 北極星: 拡張apiRows=38 だが 鏡=10 (cap10による頭打ち=仕様。11位以降はWEBに載らない)
- jsonBlob サイズ: 131KB / 512KB (26%)=まだ74%余裕がある(容量に余裕があるのに固定capで削っている)
- 純Web公開送信: 36秒前(自動publishは効いている)

# 状態速報の自己診断の穴(実コード確認済み)
- liveviewPublishSelfDiag.js の整合チェックは「北極星 貢献度/広告」しか突合していない。
  応援レーン各段(りんく/こん太/たぬ姉)とコメントは①POP vs ③WEB鏡で突合していない=食い違っても検知されない。
- numberConsistency.js の異常検知は「記録vs公式」「コメ者vs来場」等5項目だけ。レーンやコメント乖離は検知項目に無い。
- parityVerdict.js は「③WEBが別ドメインで実描画を読めない」ため、観測の天井は「publish済+新鮮+鏡が整合」まで。
  ③WEBが"実際に何件描画したか"は検証できていない。

# 問うこと(結論→根拠→反論・リスク→具体案 の型で)
1. 「①POP=②=③のフルコピー」を本当に実現するには、cap(60/48/10)による間引きをどうすべきか。
   容量に74%余裕があるのに固定capで削るのは正しいか。動的cap(容量が許す限り全件送る)にすべきか、
   それとも「WEBは軽量サマリで良い=フルコピーという要求自体を再定義」すべきか。
2. ①POPが画面に描いた実件数と、③WEB鏡に載った件数が食い違う経路はどこか(描画とpublishの非対称)。
   同じ鏡を読むはずの①②③がなぜズレるのか、考えられる原因を列挙し、切り分け手順を示せ。
3. 「コピペするだけで①=②=③が揃っているか一発で分かる」ための自己診断は、何をどう突合すべきか。
   具体的に、状態速報にどんな行を出せば、ユーザーが説明せずに食い違いを指摘できるか。
4. コメント鏡が30件しかない(記録808件)のは仕様か不具合か。純Webで「コメントの流れ」を出すのに
   最新60件で足りるのか、もっと要るのか。「観測累計」という誤解を招くラベルはどう直すか。

# 制約
- 記録(IndexedDB)・取得・描画ロジックは壊さない。新規storageキーは増やさない(既存jsonBlob相乗り優先)。
- popup-entry.js は max-lines 上限ギリギリ(コメント追加でlintが落ちる)。
- 送信payloadは512KB上限(サーバー側 api/status の制約)。
