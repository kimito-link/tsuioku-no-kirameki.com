========================================================================
## 結論
「popup を開かずに popup 固有の診断を取得することは技術的に不可能です。」
  
## 根拠
1. **描画結果の不可視性**: `avatarLoadDiag` と `northStarRenderProbe` は、ブラウザが実際にレンダリングを行い、画像を読み込む挙動に基づいて生成される値です。Offscreen 文書では、表示領域がないため、レンダリングエンジンの最適化によりこれらの値が正しく取得できない可能性があります。
2. **MV3 の制限**: 拡張機能はユーザーがアイコンをクリックした場合しか popup を開けません。offscreen document での診断ロジック実行も、.popup 環境と完全に同じではないため、誤诊のリスクがあります。

## 反論・リスク
- **過剰なリソース消費**: offscreen document を頻繁に起動し続けることで、CPU とバッテリーの消耗が発生する可能性があります。
- **ユーザー体験悪化**: 裏で重い処理を実行している場合、ユーザーにとっては不快感を与えます。

## 具体案
1. **ボタン押下での診断**: status ページに「popup 診断取得」のボタンを追加します。
2. **Offscreen 使用**: ボタンが押された際に、offscreen document を起動し、.popup ロジックを実行します。
3. **結果保存と反映**: 診断結果を storage に保存し、status ページで表示します。

**MVP 実現手順**:
- `extension/offscreen-entry.js` を編集して、offscreen 文書での診断ロジック実行を可能にする。
- `status.html` にボタンを追加し、クリックイベントリスナーを設定する。
- 診断結果を storage から読み取り、UI 上で表示するためのコードを追加する。

### nvidia/qwen3.5-122b  [発散アイデア（推論強）]  (105262ms)
========================================================================
## 結論
「popup を開かずに、かつユーザー操作なしで popup 固有の診断（画像ロード/描画結果）を取得する」ことは、**MV3 のセキュリティモデルと「描画結果」の性質上、原理的に完全自動化は不可能**です。したがって、正攻法（offscreen で常時走らせる）は誤診のリスクが高く採用できません。
代わりに、**「ユーザーが status ページを開いた瞬間に、裏で 1 回だけ offscreen を起動し、popup の DOM をシミュレートして診断を生成・保存する『自動補完』」**という、操作を 1 回に集約する折衷案を提案します。

## 根拠
1.  **描画結果の不可視性**: `avatarLoadDiag` や `northStarRenderProbe` は、単なるデータ計算ではなく、ブラウザのレンダリングエンジンが実際に DOM 要素をパースし、画像リクエストを発行し、レイアウト計算を行った「結果」です。Offscreen 文書は DOM は持てますが、デフォルトでは「表示領域サイズ 0」かつ「レンダリングの最適化（画像の非読み込みなど）が働く」ため、本物の popup（可視領域あり）と全く同じ挙動（特に画像のロード成功/失敗のタイミングや、描画完了の判定）を再現することは極めて困難です。
2.  **MV3 の「ユーザージェスチャ」制約**: 拡張機能から `popup.html` を強制的に開く API は存在しません。また、Offscreen を常時起動して「描画監視」を続ける行為は、ユーザーの意図しないリソース消費（バッテリー、CPU）を引き起こし、過去の「自動ダウンロード連発」の悪夢を再現する危険性があります。
3.  **ユーザーの真の痛み**: ユーザーは「popup を開く手間」を嫌っていますが、本質的には「status に情報が足らないこと」への不安です。status を開いた時点で「あ、まだ popup 診断がない」と気づく必要がなく、**「status を開いた瞬間に、すでに最新診断が埋まっている」**状態であれば、popup を開く必要は消失します。

## 反論・リスク
*   **誤診のリスク（最大の弱点）**: Offscreen 環境で画像ロードを試みても、ブラウザの「画像キャッシュ」や「レンダリング最適化（Lazy Load の無効化など）」の影響を受け、本物の popup でロード失敗する画像が Offscreen では成功してしまう（あるいはその逆）可能性があります。これにより「popup は正常だが、実際には描画が詰まっている」という誤った診断が status に反映され、ユーザーの信頼を損なう恐れがあります。
    *   *対策*: Offscreen で取得した値は「推定値」として扱い、本物の popup を開いた瞬間に上書きする仕組み（二重チェック）を必須とします。
*   **プライバシー/権限の懸念**: 裏で画像をロードして解析する行為に対し、ユーザーが「勝手に画像を見ているのか？」と疑念を持つ可能性があります。
    *   *対策*: status ページに「popup 診断を自動取得しました（更新日）」と明記し、透明性を担保します。
*   **技術的限界**: もし Offscreen 上で画像ロードが完全に無効化されるブラウザ仕様（セキュリティ miatt）であれば、この案自体が機能しません（この場合は「不可能」と断言し、C 案の切り捨てへ回帰します）。

## 具体案
「完全自動化（Q1-案 A）の危険性を排しつつ、操作回数を最小化（Q2, Q4）する**『Status 開拓型オフスクリーン診断』**」を実装します。

### 1. 核心ロジック：On-Status-Open Trigger
ユーザーが `status.html` を開いたタイミング（`DOMContentLoaded` または `window.onload`）で、以下のフローを非同期で実行します。
1.  **Offscreen 起動**: `chrome.offscreen.createDocument()` を呼び出し、裏で `offscreen-entry.js` をロード。
2.  **シミュレーション実行**: Offscreen 文書内で、`popup-entry.js` の「画像ロードテスト」と「レーン描画テスト」のロジックを**データだけ（画像 URL、描画データ）を渡して**実行する。
    *   *工夫*: Offscreen 側の CSS を `width: 100px; height: 100px;` に固定し、ブラウザの画像ロード機構を強制的に発火させる（サイズ 0 でのロードを防ぐ）。
3.  **結果の保存**: 生成された診断結果（`avatarLoadDiag` 等）を `chrome.storage.local` に `popup_diag_cache` キーで保存。有効期限（例：5 分）を付与。
4.  **Status 反映**: `status.html` のスクリプトが保存されたキャッシュを読み込み、UI に反映する。

### 2. ファイル構成と実装手順
*   **追加/修正ファイル**:
    *   `src/extension/offscreen-diag-runner.js` (新規): Offscreen 内で動く専用スクリプト。`popup-entry.js` の診断ロジックをインポートし、引数付きで実行するラッパー。
    *   `src/status/status.js` (修正): ページロード時に `chrome.runtime.sendMessage({action: 'fetchPopupDiag'})` を送信。
    *   `src/extension/offscreen-entry.js` (修正): メッセージを受け取り、`offscreen-diag-runner.js` を呼び出すロジックを追加。
    *   `manifest.json` (MV3): `offscreen` 権限の維持。

### 3. ユーザー体験フロー（MVP）
1.  ユーザーは「拡張アイコン」をクリックせず、直接「status ページ」を開く（またはタブを開く）。
2.  **裏側で自動処理**: 0.5 秒〜1 秒程度の間に、Offscreen で画像ロードテストが走り、結果が status に表示される。
3.  **結果**: 「popup 診断：取得済み（1 分前）」として表示され、ユーザーは**popup を開かずに**全ての情報を確認できる。
4.  **例外処理**: もし Offscreen での取得に失敗した場合（画像ロードエラー等）、status 上に「詳細診断が必要なため、拡張アイコンをクリックしてください」という**1 回限りの簡易ボタン**を表示する。

### 4. 後続ステップ（V2）
*   **Cache 戦略の強化**: 画像の ETag やキャッシュヘッダーを監視し、画像自体が変わっていない場合は Offscreen を起動せず、キャッシュ結果を返すようにし、負荷をさらに下げる。
*   **誤診の検知**: 本物の popup を開いた際の結果と Offscreen 結果が異なる場合、その差分をログに残し、将来的に「どの画像が Offscreen と本番で挙動が異なるか」を分析するデータとする。

この案は、「原理的に不可能な完全自動化」を避けつつ、「ユーザーが意識する操作（status 開く）」をトリガーに裏で処理を行うことで、**

## 結論
popup を開かずに popup 診断を取ることは、技術的には可能ですが、完全に自動化することは難しいです。代わりに、ユーザーの操作を最小限に抑える方法を検討する必要があります。

## 根拠
MV3 の制限により、popup を勝手に開くことができません。また、popup 固有の診断は、popup が描画されたときにのみ生成されます。ただし、offscreen document を使用して、popup の診断ロジックを別のコンテキストで実行することは可能です。

## 反論・リスク
offscreen で popup ロジックを動かす場合、サイズ0・ユーザー操作なし・ライフサイクルが異なるため、popup と完全に同じ環境ではありません。さらに、自動実行のトリガーとコスト、storage 書き込み頻度、電池/CPU への影響などを考慮する必要があります。

## 具体案
1. status ページに「popup 診断も取り込む」ボタンを追加します。
2. ボタンを押したときに、offscreen document を使用して popup の診断ロジックを実行します。
3. 診断結果を storage に保存し、status ページに反映します。
4. ユーザーの操作を最小限に抑えるために、ボタンを押したときにのみ診断を実行します。
5. MVP として、初期バージョンでは、ボタンを押したときにのみ診断を実行し、後続のバージョンでは、自動実行のトリガーとコストを最適化します。
