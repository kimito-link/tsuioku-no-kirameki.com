# お題: 「よく使うAI指示文テンプレ集」をどう仕上げるべきか

## 背景
ユーザー(Claude Codeのヘビーユーザー、複数の個人開発プロダクトを並行運用)が、自分自身がAIコーディングエージェント(Claude Code / Cursor等)に繰り返し打っている指示文（プロンプト）を洗い出した。実際に全プロジェクトのセッション履歴を横断検索して発掘した実例は以下の通り。

### 実際に発掘した繰り返しプロンプトの実例

**A. Fable用リファクタリング指示書生成プロンプト**(6セッション以上でほぼ一言一句同じ、最も作り込まれている)
「あなたは、このコードベースを深く分析し、実装担当モデルがリファクタリングを完遂するための指示書を作る役割です。あなた自身は、まだ実装しないでください。」から始まり、Objective/Project Understanding/Behaviors To Preserve/Non-Negotiables/Stop And Ask Conditions/Baseline Commands/Debt Map/Implementation Phases/Verification Requirements/Reporting Format/Out-of-scope Itemsを含むMarkdown指示書(`refactor-instructions.md`)をFableに作らせ、それを人間が別モデル(Codex/Opus)に「/goal refactor-instructions.md に書かれたことを完遂しろ」で渡す、という2段階運用。出典はX(Twitter)の他ユーザーの投稿を元にしている模様。

**B. レスポンシブ対応チェック**(15件以上のプロジェクトで頻出、言い回しは案件ごとにバラバラ)
例: 「どの画面サイズで見ても綺麗に見えるようにレスポンシブ化」「この地図レスポンシブでどのサイズでももうちょっと大きく見せたい」「いま見ると潜っています。レスポンシブでの見えからも全部チェックして修正して」

**C. 安全弁(大規模改修の暴走防止)**
「まずはコードを変更せず、現在のリポジトリを調査して、既存構成を最大限生かす案を提示してください。調査結果と実装計画を私が確認するまで、大規模なリファクタリングやファイル削除は行わないでください。」

**D. コンポーネント化＆ファクタリング(エラーの出にくい構造)**
「ファクタリング＆コンポーネント化すれば、ミスがなくなると思います。また、各ブロックが何が入るか全部コメントアウトをAIも人間もわかるようにすればいい」

**E. ノーコード変更バグチェック**
「ソースコード変更なしにバグ・エラーチェックして」「エラーバグチェック計画して」

**F. AI会議**
既に`council-fable`スキルとしてスキル化済み(このHOWTO自体)。

### 既存の関連資産(車輪の再発明を避けるための前提)
- `~/.claude/skills/audit-skills/SKILL.md` というスキルが**既に存在する**。これは「実際の使い方(繰り返し打つプロンプト・HOWTO・設計/引き継ぎmd・メモリ・プロジェクト構成)を監査し、何度も手で説明している定型ワークフローを抽出して、再利用可能な高品質Claude Skill(SKILL.md)に変換する」ことを目的にしており、まさに今回のお題(A〜Eのテンプレ化)を実行するために作られたスキルに見える。「Fable主役で回すと精度が高いがOpus 4.8でも動く」ともあり、今回ユーザーが指定した3段構え(会議→Fable→実装引き継ぎ)とほぼ同じ思想。
- `~/.claude/skills/council-fable/SKILL.md` という、まさに今回使っている「会議→Fable設計」の3段構えを型化したスキルも既に存在する。
- 運用の憲法として「正本1つ・コピー散らさない／fail-closed／既存資産を作り直さず薄く束ねる」が最上位ルールとして明記されている(`github/CLAUDE.md`)。

## 決めてほしいこと(会議の主題)

1. **今回のテンプレ化作業は、既存の`audit-skills`スキルをそのまま呼び出すべきか、それとも今回だけ独自に会議→Fableの3段構えを回すべきか。** 既存資産の重複作成にならないよう、判断してほしい。
2. A〜Eの5個のテンプレのうち、**SKILL.md化(スラッシュコマンド化)する価値が高い順に優先順位をつけてほしい**。判断基準は「頻度」「言い回しのブレの大きさ(=型が固まっていないほど価値が高い)」「間違えると実害が大きいか(Cが典型)」。
3. A(Fableリファクタリング指示書生成プロンプト)は既に非常に長く作り込まれているが、**そのままSKILL.md化してよいか、それとも短縮・調整すべき点があるか**を具体的に指摘してほしい。特に、このプロンプトはXの他ユーザー由来と見られる。汎用的すぎて逆に使いにくくなっていないか、このユーザーの環境(Windows/AutoHotkey/複数リポジトリ横断)に合わせた調整が要るか。
4. B・D・Eのようにまだ言い回しが定まっていないテンプレは、**どんな決定版の文言にすべきか**、具体的な文面の叩き台を出してほしい。
5. **1つのSkillに全部まとめるべきか、5個(またはそれ以上)に分割すべきか**の構成案。

## 出力フォーマット
結論 → 根拠 → 反論・リスク → 具体案、の4ブロックで。
