お題: 会場モード(venue)を、公開記事「データを作る人と見せる人を分ける設計」(星野ロミ氏由来)の思想に沿わせるべきか。そのとき popup の「アイコン列・グリッド・診断」を会場へどう扱うか(そのまま運ぶ/会場向けに作り替える/運ばない)。ユーザーは「popup のアイコン列・グリッド・診断をそのまま会場へ運ぶ全体は大丈夫か」「その分離思想は入っているか」を問うている。慎重に方針を決めたい。

# 記事の核心(この思想が判断軸・原文の言葉)
- 「作る人」=常に裏で動く側が集める・集計する(記録の心臓部)。「見せる人」=画面は「置いてあるものを貼るだけ」。
- 正本の置き場=chrome.storage 等の共通領域に「集計済みを最新の1枚(最小の鏡データ)」で保管。
- 防ぐ問題: ①開いた瞬間に重い(画面が全件読み込み・集計するから) ②画面を開かないとデータが出ない(生成が描画に紐づくから)。根は同じ=「1画面に集める・集計・描くを全部やらせる」こと。
- ルール: 記録側が定期保存時に「鏡」を置く/画面は storage.onChanged で受けて貼るだけ(全件読み込みなし)/派生状態は保存せず冪等な述語で都度計算。
- アンチパターン: 画面の読み取りをキャッシュで包む(読み取りは減らすべき)/画面全体を毎回コピー(最小の鏡だけ)/記録の心臓部に集計を足す(作る人は薄く保つ)。

# 実コードで裏取りした現状(前提・覆さない)
- 会場は「見せる側で集計」している: src/extension/venueBar.js renderSeats が毎フレーム buildVenueSeating(集約)→席割り→描画を全部やる。診断(seatsShown 等)も renderSeats が計算して venueSeatsDiag(鏡)を storage に置く=ここは分離できている。だが順位バッジ(rankVenueContributors)もアバター解決率(computeVenueParticipantAvatarCounts)も renderSeats/パネル(見せる側)で計算=分離できていない。
- popup も実は「見せる側で集計」している: popup-entry.js renderUserRooms が aggregateCommentsByUser / userLaneCandidatesFromStorage で描画時に集約(記事の理想=貼るだけ、には未到達)。ただし storage.onChanged 受動更新の方向(「書かずに映す」)は既にある。
- popup の「アイコン列」は "数値ユーザーID+個人サムネが揃った応援だけ" を上段に出し、匿名(a:)は上に出さず下段へ流す設計(りんくキャラの UI 契約)。
- 会場は逆に "匿名(a:)も全員が主役" で席に座らせる設計(venueSeats.js venueParticipantKey=userId あれば匿名も着席)。実機は 868人・匿名だらけ。
- 「見せる側の集計」を大きくすると hot path(renderSeats は毎フレーム)が重くなる=記事の①開いた瞬間に重い、を会場で再現しうる。

# 直近の失敗(繰り返し防止)
- Phase 2a(席に順位バッジ🥇🥈🥉)+ Phase 3(🩺会場の状態パネル)を実装・出荷(v0.1.1030)したが、実機868人密集会場でバッジが小さすぎて見えず、以前見えていた金色オーラも消したため「会場が変わっていない」とユーザー評価。= 見せ方(可視性)と、そもそも会場に集計ブロックを重ねる設計判断の両方が未決着。

# 問い(これに答えて)
1. 会場を記事の分離設計(作る人=裏で集計→最小の鏡を storage→会場は貼るだけ)に作り替えるべきか。それとも会場は「リアルタイム描画ループ(renderSeats)」の性質上、都度計算が本質で分離は過剰か。星野ロミ式(既存データ活かす・過剰実装回避・落とさない・恥をかかせない)で。作り替えるなら何を「鏡」として storage に置くか(席割り済み配列? 順位付き? アバター解決率の件数?)。
2. popup の「アイコン列・グリッド・診断」を会場へ「そのまま運ぶ」のは是か非か。popup は匿名を除外して数値ID+サムネ揃いだけ上段に出す UI 契約。会場は匿名も全員主役。この矛盾を踏まえ、(A)そのまま運ぶ (B)会場向けに"匿名も含む"版へ作り替える (C)運ばない(会場に別途グリッドは不要・席で足りる)。実機868人・匿名だらけを踏まえた線引き。
3. 「見せる側の集計」を会場でどこまで許すか。renderSeats は毎フレーム。順位/アバール解決率/グリッドを描画時に計算すると重い。記事の「鏡データ」を採るなら、誰が(どのタイミングで)集計して鏡を置くか(会場を開く前に別経路?content が定期で?)。会場は content inline と standalone(venue.html)の二経路がある=鏡を置く主体をどちらにするか。
4. 分離を採らない場合の最小の落とし所。作り替えが過剰なら、せめて「1回計算→sig 無変化 skip→3秒 min-gap」で hot path を守る現状方式で十分か。可視性(密集で上位が見えない)は分離とは別問題として、見せ方(バッジ拡大/静的オーラ復活/上部ランキングバー)で解けばよいか。
5. やってはいけない過剰実装/退化を1つ以上(批判役は必ず穴を指摘): 例=会場に独自集計を作って popup/status と drift/記録の心臓部(記録 SW)に会場専用集計を足して太らせる/毎フレーム全件走査で開いた瞬間に重い/匿名除外を会場へ持ち込み「全員主役」を壊す/鏡データを storage に増やして書込みを増やす/分離のために大改修して既存の安定(満席維持・eviction・吹き出し追従)を退化させる。

# 制約(星野ロミ式+記事)
記録本体不可侵・新storage書込みを増やさない(または最小の鏡だけ)・hot path 重くしない・落とさない(匿名も人として出す)・既存データ活かす・過剰実装回避・恥をかかせない・作る人と見せる人を分ける(見せる側で集計を増やさない)・検証ファースト。

出力は『結論 → 根拠 → 反論・リスク → 具体案』の4ブロックで。具体案は「まず実機/コードで何を確認するか」と「作り替えるなら最小のファイル:関数(誰が鏡を置き、会場は何を貼るだけにするか)」まで。
