【お題】Chrome拡張「君斗りんくの追憶のきらめき」の応援ライブビューを、①本物POP=②応援プレビュー=③WEB で完全同一にしたい。ただし順番が肝心で、ユーザーの指示は「まず①本物POPがちゃんと動くようにする → その上で全機能 → その上で①②③同一」。

【現状の症状(ユーザー実機・2026-07-02)】
①本物POP(ニコ生watchのツールバーから開く本物のpopup)で、次が「全部」同時に起きている:
- 重い/真っ白/固まる(過去 v1023 で②passiveがrefresh()全件を走らせ storageを奪う真因を1つ潰したが、①本体でもまだ重い場面がある。3配信同時+backfillで更新所要が11秒級に膨れた実績あり)
- 数字/件数がおかしい(記録件数・同接・来場が違う/0/古い。表示の正本 recordedCountForDisplay に一本化する途中)
- 応援レーン(りんく/こん太/たぬ姉/広告)や顔アイコンが 空/崩れる/出たり消えたり(広告列の明滅→高さ振動を個別に潰してきた)
- 「①=②=③同一」の緑パリティバッジが出るのに実際は数字/中身がズレる(=フルコピーは嘘。parity判定が中身を突合していなかった穴を段階的に塞いでいる最中)

【アーキテクチャ(実コードで確定)】
- 3画面すべて同一の popup-entry.js が描画する。
  ①POP=extension/popup.html(鏡を「書く」源泉=source of truth)
  ②応援プレビュー=extension/live-view.html の INLINE_PASSIVE(dock=liveview/status。①の鏡を「読むだけ」・storageに書かない・watchに注入しない受動ビュー)
  ③WEB=app/live-view.html(popup-entry を chromeシムで動かす純Web。サーバ経由で送られた鏡を読む)
- ②③は①の鏡(laneMirror / statCardsMirror / topSupporters / northStarMirror 等の JSON 鏡)を読んで再現する。だから①が不正確なら②③は構造的に正しくなり得ない。
- 単一 chrome.storage.local(LevelDB)を①の記録処理・②の受動描画・status診断・backfill が奪い合う→並行readでstall(単一DBの書込競合)。
- popup-entry.js は max-lines ラチェット上限ギリギリ(~21600行)。純関数は src/lib へ切り出す規律。

【過去に踏んだ地雷(捨てた案・繰り返し禁止)】
- refresh()/paint の read path は触らない(v0.1.948で2回却下=read cache/丸ごとHTML鏡が実機で退化)。
- DOM丸ごと鏡は重さで却下(.nl-main を毎paint sanitize=重い。業界もStreamElements型=全stateを1JSONで送るのが正攻法)。
- renderSeats/描画に「入力sig同一なら丸ごと早期return」を足したら、別surfaceのアイコン列がちらつく回帰(v1032撤回)。機序未特定の盲目的sig skip禁止。
- 「①=②=③✅」を ack{ready,ts,liveId} だけで判定すると嘘の緑が出る=②の実描画値を①と突合しないとダメ。
- 診断カウンタ(commentIngestBySource等)を表示に混ぜない。表示の正本は1本(recordedCountForDisplay)。
- 「1個ずつレーンを足して近づける」禁止=本物lib・本物state を丸ごと使う。似せて自作しない。
