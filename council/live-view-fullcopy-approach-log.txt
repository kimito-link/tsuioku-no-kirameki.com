## 結論  
案Aの「共有lib移植・漸進」は、popup側のモジュールレベルstate/ヘルパの依存関係を完全に切り離せないリスクがある。案Bの「丸ごとクローン」は、popup.jsのchrome.*依存をスタブ化する実装コストが見積もり不足。

## 根拠  
- 案Aでpopupの純関数をlive-viewに移動する際、`avatar load guard`や`identicon キャッシュ`などのstateは純関数外で管理されている。これらをoptsで注入するには、popup側のstate変更をlive-view側で再現する必要があり、実質「再現」に陥る可能性。過去に`paintNorthStarStripInto`で却下されたパターンと構造が一致。
- 案Bの問題は、popup-entry.jsが`DOMContentLoaded→initPopup`のライフサイクルに強く依存している点。live-viewでiframe外のDOMContentLoadedイベントを抑止するには、MV3のcontent_scriptsの実行タイミングとスコープ制限に依存するリスクが。実際にpopup.jsの`chrome.tabs.getCurrent()`などはタブが前面にある前提で書かれており、live-viewタブ単独では例外を吐く。

## 反論・リスク  
案Cのiframe埋め込み案は、MV3のcontent_security_policyでiframe.srcに同一オリジン制約が厳格化されており、拡張内でpopup.htmlをiframeに読み込むと「Not allowed to load local resource」エラーになる。また、popup側の`chrome.windows.getCurrent()`などはiframe内では実行不可で、iframeと親のlive-view.html間のポーティングコストが膨大になる。

## 具体案  
1. **案Aの改良案**: `popup-entry.js`内のstate/ヘルパを`src/lib/popup-runtime-context.js`として抽出し、`live-view-entry.js`で`createPopupContextStub()`を定義。例:  
   ```js
   // popup-runtime-context.js
   export const createPopupContext = () => {
     return {
       avatarCache: new Map(),
       identiconScheme: '#FF5733',
       // ...
     };
   };
   ```
   ```js
   // live-view-entry.js
   import { createPopupContext } from '../lib/popup-runtime-context';
   const popupContext = createPopupContext();
   renderTopSupportRankStripInto(popupContext);
   ```

2. **案Bの実装手順**:  
   - `popup.html`を`live-view.html`に複製後、`popup-entry.js`を`live-view-entry.js`にリネーム。  
   - `DOMContentLoaded`イベントハンドラを`initLiveView()`関数に変換し、`popup-entry.js`での`DOMContentLoaded`自動実行を抑止:  
     ```js
     // popup-entry.js
     if (typeof chrome !== 'undefined') {
       document.addEventListener('DOMContentLoaded', initPopup);
     }
     ```
     → `live-view-entry.js`では以下に変更:  
     ```js
     export const initLiveView = () => {
       // chrome.tabs依存はガード
       if (typeof chrome === 'undefined') {
         document.querySelectorAll('[data-admin]').forEach(el => el.remove());
       }
       // 他chrome.*依存のスタブ化
     };
     ```
   - `live-view.html`で`popup-entry.js`を外部スクリプトとして読み込み、`initLiveView()`を手動実行:  
     ```html
     <script type="module">
       import { initLiveView } from './live-view-entry.js';
       initLiveView();
     </script>
     ```

## 具体案
### CaseA(共有lib移植・漸進)
1. **popup-entry.js**: 描画関数を1枚ずつ src/lib の共有モジュールへ抽出し、依存する state/ヘルパは opts 引数で注入します。
2. **live-view.html / live-view-entry.js**: 共有モジュールから描画関数を import して同じ入力で呼ぶように修正します。popup 側にあって live-view にまだ無い/自作で残っているパネルを、本物の関数で順に置換していく。
3. **src/lib**: 共有モジュールとして描画関数を抽出し、popupとlive-viewで共通して使用できるようにします。

具体的なファイル操作例:
- `src/lib/paintStoryUserLaneDomFilled.js` (描画関数の抽出)
  ```javascript
  export function paintStoryUserLaneDomFilled(container, opts) {
    // 実装
  }
  ```
- `popup-entry.js`
  ```javascript
  import { paintStoryUserLaneDomFilled } from '../src/lib/paintStoryUserLaneDomFilled';

  function initPopup() {
    const container = document.getElementById('story-user-lane');
    paintStoryUserLaneDomFilled(container, { /* opts */ });
  }
  ```
- `live-view-entry.js`
  ```javascript
  import { paintStoryUserLaneDomFilled } from '../src/lib/paintStoryUserLaneDomFilled';

  function initLiveView() {
    const container = document.getElementById('story-user-lane');
    paintStoryUserLaneDomFilled(container, { /* opts */ });
  }
  ```

この案で、popupとlive-viewの両方が同じ描画関数を使用することで、「完全コピー」が確実に保証され、自作アレンジが混入する余地が最小限になります。また、将来サーバー公開版への移植も容易に対応できます。

## 結論
案B(丸ごとクローン)が最善の実装方式である。

## 根拠
「完全コピー(1px違わず)」を保証するためには、popup の描画関数や CSS クラスをそのまま使用する必要がある。案B は popup.html を丸ごと複製し、popup-entry.js の描画を live-view 単独で動かすため、自作アレンジが混入する余地が小さくなる。また、将来サーバー公開版への移植性も考慮され、chrome.* 依存の箇所をスタブ化する必要がある。
