【お題】公開ページ「追憶のきらめき ランキング」(https://tsuioku-no-kirameki.com/live/)の、コメント順位表の行にマウスを乗せると「その人の直近の発言」を出すホバー機能で、初回の待ち時間(「発言を取得中…」の表示)を消したい。ユーザーの言葉:「もっとスムーズに出したい　待ち時間ながい」。

回答は必ず「結論 → 根拠 → 反論・リスク → 具体案」の型で。観測(事実)と解釈(推測)を混ぜないこと。

================================================================
【観測】(実測・実コードで裏取り済み。ここは議論の材料であって結論ではない)
================================================================

■ 現状の仕組み(v0.1.1514・本番稼働中)
- ホバー→250ms debounce→ `POST /api/live-recent-comments {lv,uid}`。サーバが watch HTML を取り→視聴WSを握手して viewUri を取り→NDGR を浅く遡り(caps elapsedMs 4000/segments 12)→その配信の上位10人の直近5件を集めてレスポンスに載せる。
- ★本文は Redis に保存しない。サーバの温かい関数インスタンスのメモリ Map に 60 秒だけ保持する(同じ配信の別の人へのホバーは握手ゼロ)。
- 応答は `{ ok, lv, byUid, partial, cached }`。カードは body 直下 fixed 1個、純関数で6状態(取得中/成功/0件/失敗/未対応/空)。

■ 実測(2026-09-15・本番エンドポイントを curl)
- 初回(その配信で誰も直近ホバーしていない・キャッシュ空): 3.5秒。内訳=watch HTML 取得 + WS 握手(serverTime→seat→stream→schedule→messageServer) + NDGR 浅い遡り(12区画639KB)。
- 2回目以降(同じ配信・キャッシュ有): 0.25秒。
- つまり遅いのは「その配信で今日まだ誰もホバーしていない初回」だけ。1人がホバーすれば以後60秒はその配信の全員が速い。

■ 既に持っている材料(実コード・裏取り済み)
- 5分ごとに GitHub Actions の tally ジョブが全配信(最大20本)を巡回して「コメントで応援した人」の件数を集計している(`scripts/live-comment-tally.mjs`)。この巡回は既に watch HTML→WS 握手→viewUri→NDGR 遡りをやっている=上位者の直近5件も「ついでに」取れる位置にある。
- 増分集計(v0.1.1513)で tally は前回の続きから差分だけ取る(1配信0.6秒級)。
- `/live/` は 60 秒ごとに一覧を再取得している(`live-ranking-entry.js` の load)。ページを開いた時点で「いま見えている配信」は分かっている。
- サーバのメモリ Map キャッシュは「温かいインスタンス」限定=Vercel の関数が寝ていると消える(60秒 TTL より短く消えることもある・推測)。

■ 制約(privacy・規約・方針)
- ★privacy §14「コメントの本文は保存しません」。ホバーは「表示のためにその場で取得して返す・サーバに保存しない・メモリ60秒・どの人をホバーしたかをログ/解析に残さない」で §14 と両立させている(v0.1.1514 で追記済み)。本文を Redis に置くと §14 の改定と著作権リスクの再検討が要る。
- 視聴WSの握手は「来場者数 +1」の副作用がある(実測 9→10)。先読みや温めで握手回数が増えると、各配信の来場者数を自分で押し上げる。
- api/ は npm 依存ゼロ・Node 標準のみ・Vercel Hobby(関数実行時間の上限・同時実行数に限りがある・上限値は未確認)。
- コメント本文は投稿者の著作物になりうる。本人ローカル(拡張)への記録と違い、公開ページ経由の保存は質が変わる。

【問い】(それぞれ 結論→根拠→反論・リスク→具体案 で)
================================================================
(A) 初回3.5秒の待ちを消す最善の方向は? 候補: (1)ページを開いたらバックグラウンドで見えている配信の上位者を先読みしてキャッシュを温める (2)5分ごとの tally ジョブが本文も一緒に取って置き場に温める (3)取得は遅いままカードをスケルトン表示して届いたら差し替える。それ以外の案も歓迎。
(B) 「本文をサーバに置かない(privacy §14)」を守りつつ待ちを消せるか。メモリ60秒キャッシュしか置けないとき、どこで・いつ・誰の操作で温めるのが筋か。Redis に本文を置く案を採るなら、privacy 改定と著作権のどこをクリアすれば許容できるか。
(C) 握手が来場者数を +1 する副作用を、先読み/温めで増やしすぎない設計は? (先読みは1配信1握手で全員分の viewUri が取れる=ホバーのたびの握手より少ない、が正しいか)
(D) スケルトン表示だけでも体感は十分改善するか(3.5秒でも「待たされ感」を消せるか)。それとも実時間を縮めないと不満は残るか。
(E) 最小の第1手(いちばん小さく出して反応を見る形)。先読みを「ページを開いた最初の1回・上位N配信だけ」に絞る等。
(F) tally ジョブで温める場合、本文をどこに置くか(Redis 短TTL / メモリは Actions と Vercel で別プロセスなので不可)。privacy を守るなら「件数だけ Redis・本文はホバー時オンデマンド」の現状を変えずに、先読み(A-1)だけで足りるのでは?
