お題: 「kimito.link のページ表示を軽く（速く）する。特にLP(/)。外部SEOツールで表示速度10.06秒＝離脱リスク と出ている」

司令塔(Claude)が本番を実測した事実（推測でなく計測値・これを前提に議論せよ）:
- LP(/)の HTML 応答自体は速い: TTFB 1.1s / total 1.2s。how-to は TTFB 0.9s。
  → サーバ応答は遅くない。10秒の正体は「クライアント側のダウンロード＋描画」。
- LP の HTML が 350KB と巨大。中身は RSC ペイロード + 大量の画像マークアップ。
- LP に <img> が 56個。うち55個が Next.js の /_next/image 経由（全て loading=lazy・width/height 指定済み＝遅延と寸法は既に適切）。
- /_next/image のレスポンスは x-vercel-cache:HIT でキャッシュ済み（コールド最適化の遅延ではない）。だが返ってくるのは image/png のまま（vary:Accept はあるのに WebP/AVIF に変換されていない）。
- 同一ロゴPNGが w=128 / w=1080 / w=1200 など複数サイズで別々に要求されている。実質数体のマスコット/ロゴに対して55リクエストに膨らんでいる＝過剰フェッチ。
- JSチャンク14・CSSチャンク4。data-uri埋め込みは0。
- 既存の関連対策（メモリ）: 日本語フォントの preload は 244→0 に削減済み(PR#121)。twimgサムネは ?name=small 化済み。next/image 化はしない方針だった画像もある。

問い:
上記の実測を踏まえ、「LPの体感表示を10秒から大幅に短縮する」ための、具体的で実行可能な軽量化案を優先度つきで出してほしい。特に次を重視:
A) 56枚の画像をどう減らす/軽くするか（同一画像の多サイズ重複、png→webp/avif、本当に必要な枚数、ヒーロー以外の遅延徹底）。最大の効き目はどこか。
B) 350KBのHTML(RSCペイロード)を小さくする手（不要なクライアントコンポーネントのRSC化、Server Component化、コンテンツの分割/遅延）。
C) JS 14チャンクの削減・分割・遅延（LP初期表示に不要なものを後ろへ）。
D) やってはいけない/逆効果な施策（過去に next/image化を避けた事情、フォントpreload切りと矛盾しないか等）。
E) 最小工数で最大効果の「まず1個やるなら」これ、を1つ名指しで。

各メンバーは必ず: 結論 → 根拠 → 反論・リスク → 具体案（設定値・手順・対象ファイルまで落とす）。
推測でなく上の実測に紐づけて答えること。実測に無い犯人（例: サーバが遅い）を勝手に作らない。
