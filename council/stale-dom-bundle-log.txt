# 根拠
1.  **症状の正体は「心理的ノイズ」である**:
    実コード（`content-entry.js` 等）が示す通り、表示混乱の経路は皆無です。ユーザーが「混乱を感じている」という事実は、**「システムが何か不正なことを検知した（と誤解させる）警告テキスト」**が、ユーザーの安心感を破壊した結果です。したがって、storage の中身を物理的に整理する（案P）よりも、**「その状態が異常ではない」というファクトをユーザーに伝える（または警告を出さない）**方が、コスト対効果が高いです。

2.  **星野ロミ式の適用**:
    *   **落とさない**: 既存の `prune` ロジック（6h TTL/LRU）は健全に動作しており、データを破棄しません。
    *   **既存データ活かす**: `eventDomLvCount` のデータ自体は、過去に開いたタブの履歴として有用な場合があります（デバッグ用など）。無理に削除する必要はありません。
    *   **過剰実装回避**: 全タブを監視して即座に削除する（案P）などは、`storage.onChanged` の発火頻度を増やし、共有ストレージの競合（stall）を誘発するリスクがあります。
    *   **失敗体験=不穏な表示の除去**: 「31 件あるから危ない」という誤解を、「31 件あっても現在表示に使われているのは 1 件だけだから安全」という事実に置き換えるのが最適解です。

3.  **背景タブの非効率性**:
    `autopatrol` などの背景巡回は、ユーザーが視覚的に確認していないため、`persistOfficialEventDomBundleNow` を呼び出して DOM バンドルを保存する意味は薄いです。ここが「数値を膨らませる」元凶です。

# 反論・リスク
**反論 1: 「警告を隠すだけ（案T/M）で、本当に裏でデータが腐り、将来的に performance を落とすのではないか？」**
*   **批判**: 警告を消しただけでは、無限に古いデータが溜まり続け、Storage サイズが肥大化するリスクがある。
*   **反撃**: 既存の `pruneStaleEventDomLvs.js` が TTL 6h と LRU 30 件という強力なガードレールを既に持っています。これ以上の「即座の削除」は過剰です。データが溜まるのは「短期間に大量に開く」時だけですが、6 時間後には自然に消えます。ユーザーの「今の不安」を解消し、技術的な「将来のリスク」は既存のガードで管理すれば十分です。

**反論 2: 「背景タブでも書かないようにすると、もしユーザーがそのタブに戻った時にデータがないのでは？」**
*   **批判**: 巡回タブが突然前面化した場合、DOM バンドルがないと表示が崩れる？
*   **反撃**: 巡回タブは通常、`visibilitychange` または `tab` 切り替え時に再読み込み（または再読み込み相当の処理）が行われます。`content-entry.js` は `lastOfficialEventDomBundle=null` で初期化されるため、**「データがない＝初回ロード」として振る舞うだけで、表示崩れは起きません**。むしろ、不要なデータを書き込む方がメモリと Storage の無駄です。

**リスク: `storage.onChanged` の監視強化によるパフォーマンス劣化**
*   案P（高頻度 prune）のように `onChanged` を多用すると、マルチタブ環境でスロット競合が起き、`STORAGE_OP_TIMED_OUT` が頻発し、既存の「静かに諦める」方針を崩壊させる恐れがあります。これを避けるため、**「書込み側の抑制（案R）」**と**「診断側の再定義（案M）」**に絞ります。

## 案 1: 診断ロジックの文脈化（案 M の進化版）
**コンセプト**: 「数値の多さ」ではなく「現在の表示への影響」を基準にする。
**実装場所**: `diagWarnings.js` の `deriveStaleDomBundleSuspected` 関数。

**変更点**:
現在のロジック：
```javascript
// 現状（過剰警告の原因）
if (eventDomLvCount > 30 || currentLiveIdInEventDom === false) {
  return true;
}
```

**修正後**:
「現在アクティブなタブ（または直近の表示用）に、そのデータが影響していないなら、警告を出さない」とする。
```javascript
// 修正案：文脈的有用性の判定
// 1. 現在アクティブな liveId が eventDom に存在するか
const hasActiveBundle = eventDomLvs.some(bundle => bundle.liveId === currentLiveId);

// 2. 警告の閾値を「表示混乱のリスク」ではなく「異常な膨張」に修正
// 30 件という閾値は「表示混乱」の閾値ではないため、削除または大幅に引き上げる（例：1000 件）
// または、単に「現在アクティブな bundle が存在する限り、数値が多くても警告は出さない」とする
if (hasActiveBundle) {
  // 現在見ている配信のデータがあるなら、過去の蓄積（名残）は「正常な履歴」とみなす
  return false; 
}

// アクティブな bundle が無い場合（例：全タブ閉じた直後など）のみ、過剰な蓄積をチェック
if (!hasActiveBundle && eventDomLvCount > 100) { // 閾値を 30 -> 100 に緩和
  return true;
}

return false;
```
**効果**: 「31 件あるから危ない」という誤解を解き、「現在見ている配信のデータがあるなら、過去のデータがあっても安全」という事実をコード上で保証します。ユーザー側の「不穏な警告」が完全に消えます。
