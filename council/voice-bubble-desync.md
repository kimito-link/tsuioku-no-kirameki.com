# お題: 読み上げ(音声)とコメント(吹き出し)がずれるのを直す

## ユーザーの言葉
「読み上げとコメントがずれるときがあるのが気になる。(かなり頑張ってくれたけど)」

## 司令塔が実コードで特定した真因(確定・推測でない)

### 同期の仕組み(現状)
- 吹き出し(bubble)は TTS 再生イベントに連動する状態機械(src/lib/venueBubbleLifecycle.js):
  - `pending`(合成待ち)→ `audioStart` で `speaking`(再生中=消さない)→ `audioEnd` で `done`(余韻後消す)。
  - 鳴らなかった(stale/合成失敗/OFF)なら `resolved` で `unvoiced`(流速寿命で普通に消す)。
- `pending` の吹き出しは「最低これだけは残す床」= **BUBBLE_PENDING_VOICE_FLOOR_MS = 1800ms**
  (venueBubbleLifecycle.js:27)。合成→再生開始までの遅れで吹き出しが先に消えるのを塞ぐ床。

### ずれの核心(数値の不整合)
- 読み上げの鮮度ゲート **VOICE_STALE_MS_NORMAL = 8000ms**(voiceAgeGate.js:37・v0.1.782)。
  = コメントは音声キューで最大 ~8秒待ってから再生されうる(件数ゲート8件 × 再生1本 + 安全網8秒)。
- だが吹き出しの pending 床は **1800ms のまま**(v0.1.773 で鮮度ゲート 1800ms に追従した名残。
  その後 v0.1.781/782 で鮮度ゲートは 2500→8000ms に戻されたのに、床は 1800ms に取り残された)。
- → **コメントの吹き出しは ~1800ms で消えるのに、対応する音声は最大 ~8000ms 後に鳴る**。
  = 声が鳴り始めたとき吹き出しはとっくに消えている = 「読み上げとコメントがずれる」。
  pending のまま床(1800ms)を超えると流速寿命で消え、その後 audioStart が来ても
  nextBubbleVoiceState は done/unvoiced 終端で蘇らせない(=ずれが確定する)。

### 確認済みの事実(コード)
- venueBubbleLifecycle.js のコメントに「voiceAgeGate の通常しきい値に合わせる」と明記。
  だが実際の値が 1800ms(旧鮮度ゲート) vs 8000ms(現鮮度ゲート)で食い違っている=放置バグ。
- speaking になれば消えない(BUBBLE_VOICE_SPEAKING_CAP_MS=12000 まで)。問題は
  **speaking に【なる前(pending)】に消えてしまう**こと。

  manifest/package 同期。

### Q1: pending 床をどう決めるのが正しいか
- 単純に BUBBLE_PENDING_VOICE_FLOOR_MS を 1800→8000ms(鮮度ゲートと一致)に上げるのが筋か?
- それとも「音声キューでの実際の待ち時間(キュー位置 × 再生1本 + 合成遅延)」で動的に決めるべきか?
- 床を鮮度ゲートに【常に一致させる】単一の正本(定数を共有 or 一方が他方を参照)にして
  二度と食い違わせない設計は?(今回の放置バグの再発防止)

### Q2: 「鳴らない音声」を待ち続けて吹き出しが残りすぎないか
- 床を 8000ms に上げると、最終的に stale で鳴らなかった(unvoiced)コメントの吹き出しも
  8秒近く残る。これは「ずれ」とは逆方向の不自然さ(鳴らないのに残る)。
- resolved(=鳴らないと確定)が来た瞬間に unvoiced へ落として早く消す経路は既にある
  (nextBubbleVoiceState の resolved)。pending 床を上げても、resolved が来れば即 unvoiced に
  なるので「鳴らないのに8秒残る」は起きない、で合っているか? それとも resolved が
  来ない経路(合成パイプラインが item を黙って捨てる等)があって床だけが効く穴があるか?

### Q3: そもそも「ずれ」は床だけが原因か(他の desync 源)
- 吹き出しを出すタイミングと音声を enqueue するタイミングがズレている可能性は?
  (例: 吹き出しは DOM 観測即時・音声は別経路で遅れて enqueue → createdAt 基準がずれる)
- 速い配信で件数ゲート(8件)が古いコメントを drop したとき、その吹き出しは resolved を
  受け取って unvoiced になるか? それとも drop されたことが吹き出しに伝わらず pending のまま
  床まで残る(=別のずれ)か?
- venueBar(会場・inline/standalone)と comeview(コメビュ別窓)で同期経路が違うなら、
  片方だけずれる可能性は?

### Q4(批判役の核心): 最小修正で価値が出る MVP はどれか・上げすぎの害は
- 床を上げるだけの1行修正で「ずれ」は実際に消えるか、それとも見かけ上の対症療法で
  Q3 の別 desync が残るか。
- 床を鮮度ゲートに一致させる「単一正本」化が、将来また鮮度ゲートだけ変えたときの
  再発を本当に防ぐか(定数の物理的共有 vs コメントでの約束)。
