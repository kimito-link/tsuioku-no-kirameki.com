お題: Chrome拡張(MV3)の「応援ライブビュー」専用ページ(別タブで開く live-view.html / live-view-entry.js)を、拡張ポップアップ(popup.html / popup-entry.js)と【そっくりそのまま=骨格・パネル・並び・見た目を丸ごと一致】させたい。最善の実装方式を決める。

★前提の訂正(重要・実機で確認済み):
- 直前まで「案A=popup の描画関数を1枚ずつ live-view へ移植(漸進)」で進めていたが、実機(Playwright で popup.html と live-view.html を直接開いて目視)で「はじめから違う・そっくりそのままでない」とユーザーに却下された。
- 目視で判明した事実: live-view は独自の骨格(配信ヘッダ→盛り上がりメーター→応援者ランキングのグリッド→公式値レーン)で組まれている。一方 popup は全く別の骨格(操作ツールバー群=HTML/マーケ/メディアキット/スクショ/再読み込み/コメビュ/読み上げ → 顔アイコン付きの大きな統計カード3枚+小行 → 公式値レーン → 応援レーン段組み → …)。
- = パネルを1枚ずつ足す漸進(案A)では、骨格が別物なので永遠に一致しない。漸進方式は実機の事実とズレていた。

技術的な事実(実コードで計測):
- popup.html は 12,263 行の巨大で深くネストした DOM(初期ロードシェード/no-watch ヒント/配信者バナー/統計カード/録画ヒーロー/パネル幅凡例/表示ヘルプ/コメントティッカー/盛り上がり/応援レーン(成長ゲージ・詳細)/watch メタ/音声レベル/ストレージエラーバナー/ギフト各種マウント …)。
- popup-entry.js は DOMContentLoaded で initPopup を自動実行し、chrome.tabs / chrome.scripting / chrome.windows / chrome.runtime を 62 箇所で使う。watch タブが前面にいる前提のコードが多い。live-view は別タブ単独で chrome.storage しか実質持たない(tabs/scripting/windows を使うと例外やノーオペになる)。
- 既存ブランチ live-view-full-clone(WIP 1コミット e2a68029「popup 丸ごとクローン途中・描画配線は未完」)があるが master から 56 コミット遅れ。
- 描画の足場として、popup の本物の純関数・本物の人物タイル(buildPersonTileEl)・本物のレーン描画(paintStoryUserLaneDomFilled)・本物の統計/ランキング描画は既に src/lib に共有抽出済み(chrome 非依存=別ページから import 可)。chrome 依存なのは popup-entry.js の「初期化・タブ操作・ライフサイクル」部分。

ユーザーの絶対要件:
- 「そっくりそのまま」= popup.html の見た目・骨格・パネル・並びを丸ごと映す。実装者のアレンジ・取捨選択を入れない。
- 配信者操作(録画ON/OFF・コメビュ起動・読み上げ・スクショ等、watch タブを操作する系)は live-view では機能しない/不要なら、見た目は残すか隠すかは別途決めてよいが、勝手に「省く」のは NG(まず丸ごと映してから、いらない所をユーザーと相談)。
- 盛り上がりメーターは残してOK(popup にもあるので問題なし)。

問い: 「popup.html をそっくりそのまま live-view で出す」ための最善・最確実な実装方式はどれか。

  案B1(HTML丸ごとクローン + 共有描画関数で配線): popup.html の <body> を live-view.html に丸ごと複製(CSS も全部)。描画は popup-entry.js のうち chrome 非依存の「データ→DOM 描画」部分を共有モジュールに切り出して live-view から呼ぶ。chrome.tabs/scripting/windows を使う初期化・タブ操作・配信者操作は live-view では no-op スタブ or 非表示。DOMContentLoaded 自動実行は live-view 用エントリに置換。

  案B2(iframe で本物の popup.html を埋める): live-view.html に <iframe src="popup.html?embed=1"> を置き、popup をそのまま描画。popup-entry.js に「embed モード(chrome.tabs 等を触らない・storage 購読だけ)」分岐を足す。MV3 同一拡張ページ間 iframe の可否・操作透過・storage 共有・サーバー版移植性を必ず論じること。

  案B3(その他): 例=popup-entry.js を「ページ非依存の描画コア(chrome 非依存)」と「popup 専用ライフサイクル(chrome 依存)」に分割し、live-view は描画コア + live-view 用ライフサイクルで再構成。あるいは別案。

評価軸(優先順):
  ① 「そっくりそのまま(骨格・並び・見た目が丸ごと一致)」をどれだけ確実に保証できるか。popup を直したら live-view も自動で追従するか(乖離=drift が起きにくいか)。
  ② popup 側に回帰(挙動変化)を起こさないか。
  ③ MV3 制約(CSP・local-resource・iframe・chrome.* の有無)で詰まらないか。
  ④ 将来サーバー公開版(chrome.* 一切なし)への移植性。
  ⑤ 実装/保守コスト(12,263 行のクローン追従・62 箇所の chrome 依存の処理)。
