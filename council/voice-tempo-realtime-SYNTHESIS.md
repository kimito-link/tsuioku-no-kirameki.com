# 司令塔の統合(裏取り済み): 読み上げをコメントの滝でもテンポよくリアルタイムに

会議4体(groq系クラウドのみ・縮退運用)の発散素材を、実コード(voicePlayer.js / voiceReadQueue.js /
voiceAgeGate.js / voicevoxClient.js / voiceDiag.js)で全件裏取りした統合。

## 結論(先に全部)

**確定済みの設計判断(件数ゲート主軸・時間ゲートは保険のみ・上限8件・FIFO・決定論)は一切触らない。**
その上で、採用は次の3つだけ。他の会議案は全部却下または延期(理由は§5)。

1. **Phase 1: テンポ計器(E2Eレイテンシ)** — 「コメント到着→声が出る」までの実測msを voiceDiag に足す。
   今は合成時間(lastSynthMs)しか見えず、**テンポそのものを測る計器がゼロ**。憶測でパラメータを触る
   状態に戻らないため、これが全ての土台。ついでに `diag.lastDepth` が宣言のみで未設定のバグを直す。
2. **Phase 2: 再生時レート補正(playbackRate キャッチアップ)** — 先読み合成した WAV は「合成した瞬間の
   混雑度」の速度で焼き固められる。その後キューが膨らんでも遅いまま再生される構造穴を、再生直前に
   `audio.playbackRate`(preservesPitch=true・Chrome標準)で**合成なしゼロコスト**で埋める。決定論・有界。
3. **Phase 3: 同文統合の正規化強化(既定オフ)** — 完全一致 merge は実装済みで「ほか○件」も既に読んで
   いる(§2の発見)。「8888」「88888888」「ｗｗｗ」「www」が別文扱いで滝を素通りする穴だけを、
   類似度閾値でなく**正規化後の完全一致**(NFKC+同一文字3連以上を3に圧縮)で塞ぐ。既定オフの設定フラグ。

キュー拡張(8→12)・先読み深さ常時3・合成キャッシュ・手動ブーストUI・情報密度ドロップ・要約読み上げは
**全部却下**(§5)。

## §1 現状の構造(実コード裏取り・会議の前提より正確な地図)

読み上げのレイテンシ = ①キュー待ち + ②合成待ち + ③再生1本ずつの直列消化。

- ①は `pushVoiceQueue`(voiceReadQueue.js:9)の**上限8・最古drop**で有界。ラグ上限 ≒ 8件×再生1本。
- ②は `_startPrefetch`(voicePlayer.js:227)の**先読み深さ1〜3**(`resolveVoiceSynthDepth`)+
  v0.1.800 の `kickPrefetch` / enqueue 直後の即時 prefetch(voicePlayer.js:472)で、先頭の合成待ちは
  ほぼ隠蔽済み(実測 lastSynthMs は先読みヒット時ほぼ0)。
- ③が**残る唯一の構造的ボトルネック**。再生は1本ずつ(重ねない・重ねるべきでない)ので、テンポの
  実効レバーは「1本あたりの再生時間を混雑時に短くする」= `computeVoiceCongestion` の speedBoost
  (+0〜+0.8)と maxChars(60→30)。これは実装済みで設計として正しい。

**会議が見落とした構造穴(今回の主発見)**: `_ensurePrefetch`(voicePlayer.js:204-219)は
`computeVoiceCongestion(this.queue.length)` を**合成起動の瞬間**に評価して speedOffset を焼き込む。
つまり「待ち1件の平時に先読みした WAV」は boost 0 のゆっくり音声のまま、その後コメントの滝で
キューが8件に膨れても**遅い声で再生される**。混雑が立ち上がる瞬間=一番テンポが欲しい瞬間に、
一番遅い声が流れる。発散役の「Sliding Window Tempo Adjustment」が触りたかった「カクつき」の
正体はこれで、微分制御などしなくても再生時レート補正(Phase 2)で決定論的に埋まる。

## §2 事実訂正(お題の「要現状コード確認」への回答)

- **「○件」は読み上げに既に使っている**: `buildMergedVoiceText`(voicevoxClient.js:363-373)が
  count>1 のとき `「${本文}、ほか${count-1}件」` を合成テキストに含める。merge された同文は
  音声1回+件数読み上げで、投稿者の存在は既に「件数として」声に乗っている。
  → お題の検討2「統合でなく読み上げ側の演出で済ませられないか」は**既に実装済み**。Phase 3 は
  この既存演出の入口(一致判定)を広げるだけで、読み上げ文の生成は1行も変えない。
- **合成キューと再生キューの分離(会議の Dual-Queue 案)は既にある**: `this.prefetches`(Map・
  voicePlayer.js:40)が合成パイプライン、`this.queue` が再生FIFO。世代ガード(generation)と
  wanted-Set 掃除(voicePlayer.js:243)で「順序を保って再生キューに戻す」も解決済み。新規設計不要。
- **`diag.lastDepth` は初期化(voicePlayer.js:51)されるが、どこからも代入されていない**(comeview 側
  と違い voicePlayer 経路は未配線)。永遠に0を報告する化石計器。Phase 1 で直す。

## §3 Phase 設計

### Phase 1: テンポ計器(退行リスクゼロ・全ての土台)

「テンポが良い」を測れないまま Phase 2/3 に進まない(status-congestion の教訓と同じ:
計器→裏取り→実装の順)。

- voicePlayer.js: `onAudioStart` 発火箇所(voicePlayer.js:370 付近)で
  `E2E = Date.now() - item.enqueuedAt` を計測し、diag に追加:
  - `lastE2eMs`(直近1件の到着→発声ms)
  - `e2eAvgMs`(EMA・係数0.3 程度。窓バッファを持たない=メモリ有界・純粋)
  - `mergeTotal`(mergeRepeatedVoiceItem で吸収した累計。今は無計器で「統合が効いているか」不明)
- `_startPrefetch` 内で `this.diag.lastDepth = depth;` を代入(化石計器の修理)。
- voiceDiag.js: `buildVoiceDiagSnapshot` / `buildVoiceDiagLine` に上記3値を追加。
  行の例: `会場読み上げ: ON / 待機3(最大8) / 体感遅延1.8秒(平均2.4秒) / 統合5件 / 間引き2件 / 合成0ms`
- **間引き通知UIは新設しない**: `_showSkipped`→`onSkip`(voicePlayer.js:104)が既にスキップ件数を
  UI に出しており、状態速報の「間引き○件」も既にある。批判役の「手動ブーストは配信者負担」に同意、
  さらに言えば自動制御(speedBoost)が既に決定論で効いているので人間レバーは不要。
  会議の「間引き通知UI」への回答は「既存計器の露出を1行増やす(体感遅延)」で完結させる。

### Phase 2: 再生時レート補正(playbackRate キャッチアップ)

§1 の構造穴(合成時点の混雑で速度が固まる)への最小・決定論・合成コストゼロの解。

- 設計(擬似コードでなく実関数への対応づけ):
  - `_ensurePrefetch` で prefetch エントリに `boostAtSynth: congestion.speedBoost` を保存
    (Map の value は既に `{generation, promise}` オブジェクト=フィールド追加のみ)。
  - `_drainQueue` の再生直前(voicePlayer.js:334 の `new AudioCtor(objectUrl)` 直後)で:
    - `boostNow = computeVoiceCongestion(現在の this.queue.length).speedBoost`
    - `rate = clamp((1 + boostNow) / (1 + boostAtSynth), 1.0, 1.35)`
      (**上げるだけ・下げない**。遅くする方向は「間延び」退行になるので封印)
    - `audio.preservesPitch = true; audio.playbackRate = rate;`
  - 純関数 `computeVoicePlaybackRate(boostAtSynth, boostNow)` を voiceReadQueue.js に置き単体テスト。
- 決定論: 入力はキュー長2点のみ。確率要素なし。乱数なし。
- 有界: 上限1.35(VOICEVOX speedScale 側の最大 +0.8 と重ねても、実効 1.8×1.35≒2.4倍を超えない
  よう clamp。聴感限界は Phase 1 の計器を見ながら実機で調整=定数1個)。
- 退行安全: playbackRate は合成をやり直さない・キュー/FIFO/ゲートに一切触れない・ended イベントは
  レート倍速でも正しく発火する(watchdog 20秒も従来どおり保険で残る)。
  preservesPitch は Chrome 86+ 標準(この拡張は Chrome 専用)なのでピッチ崩れ(ゆっくり文化への
  違和感)は起きない。万一 false 環境でも「早口になる」だけで沈黙にはならない。
- 発散役の「3秒窓の微分で連続テンポ制御」は却下: 状態(履歴バッファ)が増え、テスト不能な時間依存が
  入る。上記の「2点比較」で同じ体感(混雑立ち上がりの遅い声を解消)が状態レスで得られる。

### Phase 3: 同文統合の正規化強化(既定オフ・安全側全振り)

- 目的: 「8888」「888888」「ｗｗｗ」「www」の応援連打が別文扱いで8枠を食い潰し、普通のコメントを
  最古dropさせるのを防ぐ。滝の主成分は実際この種の連打。
- 設計:
  - 純関数 `normalizeVoiceMergeKey(body)` を voiceReadQueue.js に新設。処理は**2つだけ**:
    1. Unicode NFKC 正規化(全角/半角ゆれ吸収: `ｗｗｗ`=`www`、`８８８`=`888`)
    2. 同一文字の3連続以上を3連に圧縮(`88888888`→`888`、`wwwww`→`www`。**2連は触らない**=
       「ああ」「いい」等の日本語を壊さない)
  - `mergeRepeatedVoiceItem`(voiceReadQueue.js:40)の一致判定を `body ===` から
    `normalizeVoiceMergeKey(body) ===` へ(candidate に key を持たせ、queue 走査時に比較)。
    読み上げる本文は**最初に来た原文のまま**(書き換えない)。件数は既存の「ほか○件」がそのまま乗る。
  - 設定フラグ `nls_voice_merge_normalize_v1`(既定 **false**=現行の完全一致のみ)。storageKeys.js に
    追加し、popup の音声設定に1トグル。オンでも一致判定が広がるだけで、オフなら現行と完全同一パス。
- 批判役の「草/草むしり誤統合」への回答: 類似度閾値・トークン頻度ヒューリスティックは**両方採用しない**。
  正規化後の完全一致のみなので「草」と「草むしり」は正規化しても別文字列=構造的に誤統合しない。
  批判役の提案した「1秒以内に3回」の頻度条件も不要: merge は現キュー(上限8件・数秒ぶん)しか
  走査しないため、**時間窓はキュー滞在時間で自然に限定**されている(古いコメントと誤統合しない)。
- ジャンル文化との整合: 本文は原文のまま読む(要約・書換なし)。連打の主は「888を8個」でなく
  「盛り上がり」を届けたいのであり、「888、ほか5件」は存在感を消さずむしろ束ねて届ける。
  それでも価値観判断が割れうるので**既定オフ**でユーザーに委ねる。

## §4 「テンポが良い」の体感評価基準と実機検証手段

- **定義(定量)**: `e2eAvgMs`(Phase 1)で測る。
  - 平時(待機0-1): 中央値 2.5秒以内(合成~1.5秒+再生開始まで)。
  - 滝(待機5+が続く): `e2eAvgMs` が 8秒(=時間ゲート保険値)を**恒常的に超えない**こと。
    構造上の上限は「8件×短縮後の再生1本」なので、Phase 2 が効けば上限自体が下がる。
  - ゼロ音声ゼロ: `spokenTotal` が増え続ける(最終発話○秒前が queueNow>0 で伸びない)。
- **実機検証手順**(feedback-trust-status-report の原則どおり、状態速報コピペで完結させる):
  1. 大型配信(またはテスト配信+コメント連投)で読み上げON。
  2. 状態速報の「会場読み上げ」行を配信前半/滝の最中/後半の3回コピペしてもらう。
  3. 見る値: 体感遅延(lastE2eMs/e2eAvgMs)・間引き・統合・再生TO・停止位置。
  4. Phase 2 の A/B は「同一配信の滝区間で e2eAvgMs と間引き件数が下がるか」で判定
    (ブラウザ目視のお願い往復はしない)。
- 単体テスト: `computeVoicePlaybackRate`(境界: boost同値→1.0/上限clamp/下げ方向は常に1.0)、
  `normalizeVoiceMergeKey`(8888系/www系/2連は不変/「草」≠「草むしり」)は全て純関数でテーブルテスト可。

## §6 退行ゼロの絶対条件

- **v0.1.773 の教訓は不可侵**: 時間ゲート(voiceAgeGate.js)は保険8秒/10秒のまま一切触らない。
  リアルタイム維持の主レバーは件数ゲート(上限8)のまま。Phase 1-3 のどれもゲートに触れない。
- FIFO 不変: enqueue 順=再生順。ギフト(priority:'high')の割込みも現行のまま。
- 決定論のみ: 乱数・確率要素は一切持ち込まない(パチンコ会議の却下判断を尊重)。
- コメント本文は書き換えない: 正規化はmerge**一致判定キー**にのみ使い、読み上げ原文はそのまま。
- ゼロ音声ゼロ: 「全stale でも最新1件は読む」(voicePlayer.js:261-279)・watchdog 20秒は不変。
- Phase 3 は既定オフ: オフ時のコードパスは現行とバイト単位で等価(フラグ分岐1箇所のみ)。
- 反映3手順(AGENTS.md §12.5): 各Phaseで version bump + `npm run verify:bump`、ユーザーは
  pull→拡張リロード→watch タブ F5 で初めて反映。

## §7 司令塔が会議を訂正した点

- 「Dual-Queue Pressure Valve」は新設計でなく**現行アーキテクチャの再発見**(prefetches Map+FIFO)。
- 「○件読み上げは未実装かも」→ **実装済み**(buildMergedVoiceText の「ほか○件」)。
- 会議の誰も、先読みWAVに**合成時点の混雑速度が焼き固まる**構造穴(§1)を指摘できなかった。
  微分制御・並列化・キャッシュはすべてこの穴の代償行為であり、playbackRate 補正1個で本丸が埋まる。
- 「テンポの体感評価基準の整備」(速い視点役)は正しい指摘だが、新基準の発明でなく
  **既存 voiceDiag に E2E 1系統を足すだけ**で足りる(車輪の再発明を回避)。
