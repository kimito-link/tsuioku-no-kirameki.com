# お題: 状態速報に「過去ログ取り込みの途中経過」が出ない断線を直す

## ユーザーの言葉
「早速一気に取れる前提とが出ていないので今回の機能をつかってなおしてほしい」
（今回の機能=v0.1.793 で作った機能マップ自動生成 `npm run feature-map`）

## 司令塔が機能マップ→実コード裏取りで特定した真因（確定・推測でない）

### 経路
- `KEY_BACKFILL_PROGRESS = 'nls_backfill_progress_v1'`（過去ログ取得の進捗）
- **書く人**: content-entry.js の `publishBackfillProgress`（backfill-sw-entry.js も）
- **読む人**: status-entry.js の `loadBackfillProgressSafe`（状態速報ページ）、popup-entry.js

### 断線の核心（content-entry.js:15384）
```js
// v0.1.657「ローディングなしで一気に取る」: 単一タブなら数秒で掘り切るので
//   途中経過を見せず完成だけドンと出す設計。
if (_backfillProgress.done !== 1) return;  // ← done=1(完走)まで storage を一切書かない
```

- この設計は **1タブ・短時間配信なら正しい**（数秒で完走→完成だけ出る）。
- だが今回の実機は **2配信同時記録 + 2時間46分の長時間配信**。
  - 完走まで何分もかかる/前面裏面切替で完走しない間、`done=0` のまま。
  - その間 `nls_backfill_progress_v1` が一度も書かれない → status は null を読む。
  - → 状態速報の進捗が出ない＝「一気に取れる前提が出ていない」とユーザーが感じる。

### popup は対策済み・status は未対策（非対称）
- popup は v0.1.764 で「キーが null でも recordingActive なら『取り込み中…』」と出す
  フォールバックを持つ（backfillRinkuNarration.js:359）。
- **status-entry.js は別経路で、このフォールバックを通らない**。null だと進捗ゼロ表示のまま。

### もう1つの構造的限界
- `nls_backfill_progress_v1` は**グローバル(直近1配信分のみ)**。今回のような2配信同時記録では
  片方の進捗しか入らない（配信ごとの進捗にならない）。

## 確認済みの事実（診断 JSON より）
- `romiDebug.backfill`: `running:true, rows:6113, done:0, stopReason:""` = 取得自体は正常進行中。
  **記録は壊れていない**（94%取得・5,825/6,229）。問題は「進捗が status に届かない表示の断線」。
- 過去にこの種の混同があった: v0.1.665「一気に取れる前提が崩れている」は別件
  (リトライ生涯予算切れで実際に停止)。**今回は停止していない=表示の断線**が新しい点。

## このプロジェクトの制約（必ず守る）

- 「1変更=patch 1つ」。changelog/manifest/package を同期。changelog summary は35字以内。

  （途中経過の実況過多に戻すのは退行）。

## 会議への質問（役割分担 + 結論→根拠→反論→具体案）
役割: 総合役=設計整合と退行防止 / 発散役=別の切り口 / 批判役=各案の穴を最低1つ /
実装役=具体的なファイル・関数・テスト名まで。

### Q1: どこを直すのが筋か
3つの候補。どれを主軸にするか（複数併用も可）:
- (A) content が走行中(done=0)も進捗を storage に書く。ただし v0.1.657 の「短時間は静かに」を
  壊さないため、**長時間/複数配信のときだけ**途中経過を書く条件をどう定義するか。
- (B) status 側で、キーが null でも「記録中の配信なら『取り込み中…』」と popup と同じ
  フォールバックを出す（content を触らず status だけ直す=最小・低リスク）。
- (C) 進捗キーを配信ごと(per-lv)にして2配信同時でも両方出す（構造改善だが大きい）。

### Q2: v0.1.657 の「短時間は一気に・静かに」を壊さずに途中経過を出す境界
- 「一気に取れた(数秒で完走)」と「長くて途中」をどう区別するか。
  経過時間? rows がしきい値超? 一定時間 done に至らなかったら? どれが純関数でテストでき、
  かつ短時間配信を巻き込まないか。

### Q3: 「一気に取れる前提が出ていない」という【表示の不安】をどう解消するか
- ユーザーは「壊れている?」と不安。実際は取得中で正常。
  v0.1.791 の学び（低%を🔴でなく⏳追いつき中にして不安解消）と同じ構図。
- status に何を出せば「ちゃんと取れている・途中なだけ」が伝わるか。

### Q4（批判役の核心）: 今回の機能マップは本当に役立ったか・次に何を機械化すべきか
- 図は `nls_backfill_progress_v1` を「読む人だけ(断線)」に出した。だが実は status が
  文字列直書き・書く側が定数名で**解析が別キー扱いした偽陽性**でもあった。
  → 図は「done=1 でしか書かれない条件付き断線」までは示せない（静的解析の限界）。
- このクラスの「キーは書かれるが条件付きでしか書かれない」断線を将来どう検出するか。
