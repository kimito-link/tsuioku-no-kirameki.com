# 会議 統合結論 — 「WEBサイトURLで見る」を応援ライブビューと同一画面に

> お題: `council/webview-equals-liveview.txt` / 会議: COUNCIL_QUALITY=1・design ルーティング
> メンバー: qwen3-32b(批判) / gemma4(統括lead) / llama-3.3-70b(速い) / gpt-oss-120b(批判2)
> 司令塔(Claude/Opus)が統合・裏取り。生データ: `council/webview-equals-liveview-answers.json`

## 会議の対立(割れた)

| メンバー | 推し | 理由 |
|---|---|---|
| gpt-oss-120b(批判) | **案A** | 拡張内 live-view は既に popup 完全埋め込み=「同一画面」を追加実装ゼロで最小・確実に満たす唯一手段 |
| gemma4(統括) + llama | **案C** | 単一ボタンで「本人リアルタイム」と「他人へ共有」の両立は不可能=用途で分離(ボタン2つ/文言) |
| qwen3-32b(批判) | A寄り | 案Cはボタン増でユーザーが取り違える。診断の用途は「本人がリアルタイム確認」が圧倒的多数 |

## 司令塔の裏取り(事実の確定)

- ユーザーが見せた `chrome-extension://.../live-view.html?lv=lv350824633` = **本物 popup.html を iframe 全面埋め込み**
  = 配信者カード・応援レーン・数字カード・ギフト貢献度まで完全にそっくり・リアルタイム・**ただし拡張がある本人だけ**。
- 純Web版(?v=)= laneMirror(応援レーン)だけ再描画・配信者カード/ギフト貢献度は出さない=popup 全体そっくりではない。
  共有可だがスナップショット。
- **ユーザーの実際の言葉=「WEBサイトURLで見るを押すと応援ライブビューと【同一画面】にしたい」**=見た目の完全一致が要件。

## 司令塔の判断(会議を1つに収束)

「同一画面」を**最小・確実**に満たす唯一手段は **案A**(gpt-oss-120b・qwen が支持)。
理由=拡張内 live-view は既に popup 完全埋め込みで存在する=**遷移先を変えるだけ・追加描画ゼロ・新規storage readゼロ**。
案B(純Web を popup 全体そっくりに)は実装が重く制約に抵触。案C(ボタン2分割)は「同一画面にしたい」という
単純な要望に対しボタンを増やすのは過剰(qwen 批判=取り違え誘発)。

**ただし会議が割れた本質=「共有機能(他人が拡張なしで見る)を捨ててよいか」=コードでは決められないプロダクト判断。**
ここはユーザーに1点だけ確認する(推測で共有を消さない)。

### 確定案(ユーザー確認後に実装)
- **既定: 案A** = status 配信カードの「🌐 WEBサイトURLで見る」を、押したら `live-view.html?lv=<lv>` を新規タブで開くに変更。
  - 文言も実態に合わせる(例「🪞 応援ライブビューで見る」)。送信(POST)は不要になるので外す。
  - 既存の「🔥 応援ライブビューを開く」ボタンと役割が重複するため、**重複を1つに統合**(死にボタンを作らない)。
- **共有(純Web ?v=)を残したい場合のみ**: 案A + 共有は別導線(=実質 案C)。だがユーザーが「同一画面」だけを望むなら案Aで十分。

## リスク(自己申告)
- storage read 増: 無し(遷移先URLを変えるだけ)。
- 共有不可: 案A単独だと「拡張なしの他人へ共有」はできなくなる(=要ユーザー確認)。
- リアルタイム vs スナップショット取り違え: 案Aはリアルタイムに寄るので、むしろ取り違えが減る。
- ブラスト半径: status-entry.js のボタン1〜2個。会場/popup/純Web 本体に不介入。
