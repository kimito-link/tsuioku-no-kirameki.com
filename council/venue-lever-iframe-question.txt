お題: Chrome拡張「君斗りんくの追憶のきらめき」(ニコ生コメント記録・応援可視化)の【会場モード】を、星野ロミ視点=【てこの原理=大工事でなく最小実装】で実現する設計を会議してほしい。星野ロミ(動いてるものはそのまま活かす・摩擦ゼロ・既存資産を最大活用・最短で機能する仕組み)ならどうするか。

== 会場モードの正本(ユーザーが100回以上伝えている絶対ルール) ==
会場モードを開いたら、popup の「アイコン列・グリッド・診断を表示」(りんく段・こん太段・広告段・たぬ姉段・全コメント者グリッド)が、そっくりそのまま会場に出る=本物の再利用(コピペ)。さらに(2)開くと「会場モードになるよー」と りんく・こん太・たぬ姉 が出てくる演出、(3)その演出中に VOICEVOX(読み上げ)を準備、(4)そのまま popup のアイコンに吹き出しを付けて読み上げる。

== ★てこの原理の発見(実コードで裏取り・前回の大工事案を覆す重大事実) ==
- watch ページには既に【inline パネル】が iframe で埋め込まれて【動いている】。`content-entry.js:3553` iframe を生成し、その src は【popup.html そのもの】(コメント多数「iframe(popup.html)」)。つまり popup の中身(りんく/こん太/たぬ姉/広告/グリッド)は watch ページ内に iframe として本物がそのまま存在し動いている。
- しかも iframe ローディング演出として【りんく・こん太・たぬ姉 が並んでぴょこぴょこ動きセリフを切り替える「読み込み中」表示】が既にある(content-entry.js:3181 付近 ensureInlineLoadingPlaceholder)=ユーザーの言う「会場モードになるよー」のキャラ演出が【既に実装済み】。
- inline host(`#nls-inline-popup-host`)は position:relative・width:100%・z-index 2147482000 で watch ページのレイアウトフロー内(コメント欄付近)に差し込まれている。display:none/opacity で出し入れ。
- 一方【現状の会場モード(venueBar.js)】は別物=独立 fixed ダイアログ(role=dialog)で【独自の席(buildVenueTiers/createSeatNode/ensureTierNodes の 3D ひな壇)】を組んでいる=popup の段組みでない=「出すべきでないメンバー(顔ぶれが popup と違う生候補)」を独自席に並べている=動いていても撤去すべき不良品。
- 既に正しく動いている再利用すべき部品: inline iframe(popup.html 本物)・キャラ ローディング演出・VOICEVOX クライアント(voicevoxClient.synthesizeVoice)・読み上げキュー(drainVoiceQueue)・吹き出し(venueBar の bubbleLayer・ただし座標が独自席 seatAnchorEl 基準)。

== 前回会議の結論(これを見直す) ==
前回会議は「会場ダイアログ内に popup と同じ段組み DOM を生成し paintStoryUserLaneDomFilled/bucketStoryUserLanePicks を会場が呼ぶ=独自席は撤去」と結論=しかしこれは【段組みを作り直す中〜大工事】で、星野ロミの「動いてるものは活かす・てこの原理」に反する。popup(=inline iframe)は既に完璧に動いているのに作り直すのは無駄。

== 問い(てこの原理=最小実装で) ==
1. 「会場 = 既に動いている inline パネル iframe(popup.html)を会場レイアウトで見せるだけ」を最小実装で実現する最良の方法は何か。候補(これに限らない): (a)会場モードを開いたら inline host(#nls-inline-popup-host)を fixed で全画面前面に出す(会場用クラスを足すだけ・iframe は同一・再ロードしない) (b)inline iframe を会場ダイアログ内へ移設(appendChild)し閉じたら戻す (c)会場ダイアログ自体をやめ「会場モード=inline パネルを大きく前面表示するモード」に再定義 (d)その他。iframe を再ロードせず動いてる状態を保つのが肝。
2. キャラ演出と VOICEVOX のタイミング。iframe ローディング演出(りんく/こん太/たぬ姉)は【既にある】。これを「会場モードになるよー」の演出として流用し、その演出中に VOICEVOX ウォームアップを走らせる最小実装は。演出は新規でなく既存流用。
3. 吹き出し。現状 venueBar の吹き出しは独自席 seatAnchorEl 基準。会場が iframe(popup.html)になると、読み上げ対象アイコンは iframe 内(別ドキュメント)。iframe 越しに吹き出しを出す方法(iframe 内に出すか・親側オーバーレイで iframe 内アイコン座標に重ねるか・postMessage で座標をやり取りか)。最小で破綻しない案は。
4. 独自席(venueBar の buildVenueTiers/createSeatNode/renderSeats)は撤去か温存か。星野ロミの「動いてても出すべきでないメンバーは捨てる」=撤去が筋だが、最小ブラスト半径なら一気に消さずフラグで止める段階案も。
5. 最小工数の段階リリース順。各段で実機確認。例: PR1=会場ボタンで inline パネルを全画面前面表示(iframe 流用・独自席はフラグで止める)→PR2=ローディング演出を会場演出に流用+VOICEVOX 準備→PR3=吹き出しを iframe アイコンに重ねる→PR4=独自席撤去。

評価軸: ①popup の中身がそっくり会場に出るか(iframe=popup.html 本物・作り直さない=コピペ) ②実装が最小か(てこの原理・動いてるものを活かす・新規コード極小) ③キャラ演出/VOICEVOX/吹き出しが成立するか ④iframe 越しの吹き出し座標が破綻しないか ⑤回帰リスク(inline パネルは記録の主要機能=壊すと致命的・独自席撤去は段階的に) ⑥星野ロミらしさ(摩擦ゼロ・既存最大活用・最短) ⑦content.js/venue.js 二重バンドル整合。

各メンバーは『結論 → 根拠 → 反論・リスク → 具体案(どの関数/DOM/CSS をどう変えるか・PR段階)』の4ブロックで。批判役は必ず穴を1つ指摘(特に『inline iframe を会場へ移設/前面化すると、記録の主要機能である inline パネル本来の表示を壊すリスク』『iframe(別ドキュメント・別オリジンでないが別 document)越しの吹き出し座標取得の難しさ』『会場ダイアログをやめると既存の会場演出資産=群衆/ヒート等を捨てることになる是非』)。司令塔(Claude)が最後に統合・裏取りして1案に収束させる。最優先は「動いてる inline パネル(popup.html iframe)を最小実装で会場として見せ、キャラ演出中に VOICEVOX を準備し、アイコンに吹き出しを付けて読み上げる(てこの原理)」。
