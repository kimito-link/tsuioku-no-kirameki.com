# 問い(これに答えて)
1. 診断の中身。会場固有(seatsShown/participantCount/otherCount/broadcasterInSeats/固着=lastUpdateAt の古さ)を出すか、popup と同じアバター解決率(participants から withAvatar/resolvedAvatar/withUid を数える)も足すか、両方か。星野ロミ式(既存データ活かす・過剰実装回避・恥をかかせない)で優先順位を。venueSeatsDiag は既にあるので新規集計を増やさない線引き。
2. 置き場と開閉。会場バー下部に折りたたみ「🩺 会場の状態」を新設する案の是非。会場はフルスクリーン没入 UI=常時見せると没入を削ぐ。既定は畳む?開く?モバイル(会場は横長想定)での収まり。既に status(健全度パネル)が同じ観測値を色セルで出しているなら、会場内にも二重で出すのは冗長か、むしろ「その場で見える」価値があるか。
3. 高さ振動を出さない設計。折りたたみは席(seatsHost)と別レイヤに置き、開いても席の高さを侵さない(position/overlay か、席エリアの外か)。空データ時に畳んで高さが変わるのを防ぐ設計。sig は何をキーにすべきか(seatsShown+participantCount+otherCount の件数集合、capturedAt は入れない)。
4. drift を出さない実装分担。venueAvatarDiagLine.js(新・src/lib)を storyAvatarDiagLine の流儀で作るべきか、それとも storyAvatarDiagLine を会場からも read-only 参照して会場固有だけ薄く足すか。会場の participants → 診断入力への変換純関数をどこに置くか(venueSeats.js? 新ファイル?)。テスト(vitest)で件数を固定検証。
5. やってはいけない過剰実装を1つ以上(批判役は必ず穴を指摘): 例=会場に独自集計を書いて status/popup と drift/診断を毎フレーム再計算して hot path を重く/折りたたみ開閉で席の高さを揺らす/没入 UI に常時デバッグ情報を出して興を削ぐ/新 storage キーを増やす/venueBar を太らせて max-lines 超過。

# 制約(星野ロミ式)
記録本体不可侵・新storage書込み増やさない(既存 KEY_VENUE_SEATS_DIAG を使う)・hot path(描画/席割り)重くしない・落とさない・既存データ活かす(venueSeatsDiag/collectVenueParticipants/storyAvatarDiagLine は既にある)・過剰実装回避・恥をかかせない(空バーの明滅・没入を削ぐ常時表示を作らない)。純関数は src/lib に集約し会場は read-only 参照(drift 防止)。検証ファースト。
