【お題】Chrome拡張の状態速報ページ(status.html)で「実際には視聴していない(watch タブがどこにも開いていない)配信が、いつまでも『視聴中の配信』として表示され続ける」問題を、どう直すのが最善か。設計方針を多角的に出してほしい。

【確定事実(実コードとユーザー実機で裏取り済み)】
1. status.html は2秒ごとに更新し、「視聴中の配信」セクションに表示する lv を enumerateActiveLives() で決める。判定は3経路の優先順:
   - 経路1: chrome.tabs.query({url:'live.nicovideo.jp/watch/*'}) で【今この瞬間に実際に開いている watch タブ】から lv 抽出 ← 最優先。1件でも取れたらこれを返す。
   - 経路2: fastDiag.lives(視聴中フラグ付き配列)。ただし実装上 fastDiag に lives 配列は無く、実質ヒットしない(死んでいる経路)。
   - 経路3: nls_last_watch_url(最後に視聴した URL の文字列・時刻情報なし)から lv を1件抽出。【どれだけ古くても無条件に1件返す】。
2. ユーザー実機で、watch タブをどこにも開いていない(最小化ウインドウも含め無い)のに、特定の配信(例 lv350811514)が「視聴中の配信」に出続ける。前回別の lv は F12 で nls_last_watch_url を手動削除したら消えた=経路3の last_watch_url 残骸が原因。
3. nls_last_watch_url は content script が watch ページにいる間 window.location.href を保存するだけ(時刻なし)。タブが死んでも誰もクリアしないので残る。次に別の配信を見れば上書きされるが、見なければ永遠に残る。
4. 配信ごとのデータ nls_panel_summary_<lv> は存在し、content がタブ生存中は定期更新する(タブが死ぬと更新が止まる)。最終更新時刻フィールドの有無/名前は未確認(調査中)。
5. 過去の設計判断(v0.1.630)=「経路1(実タブ)を最優先にしたのは、以前 panel_summary を全部列挙して400件が視聴中扱いになった実機問題への対策」。つまり「実際に開いているタブだけを視聴中にしたい」が設計意図。だが経路3のフォールバックが古い記録を拾って意図を裏切っている。

【設計上のジレンマ】
- last_watch_url フォールバック(経路3)は「watch タブを開いているのに status から tabs.query が一時的に取れない(権限/タイミング)」ケースの保険でもある。完全に消すと、本当に視聴中なのに表示されない退行がありうる。
- status.html は「軽さ最優先=2秒ごとの更新で storage read を増やすな」という強い鉄則がある(直近 voiceDiag/venueSeatsDiag の毎回 read が重さの原因と判明し12秒間引きに移したばかり)。鮮度判定で追加 read を増やすのは慎重に。ただし経路3は経路1/2が空のときだけ通るので稀。

【問い】
A. 「実際に視聴していない配信を『視聴中』と出さない」ために、経路3(last_watch_url フォールバック)をどう直すのが最善か。案を複数、それぞれ長所/短所/退行リスクつきで:
   - 案1: 経路3で拾った lv の panel_summary の最終更新時刻を見て、N分以上古ければ「視聴中」に出さない(鮮度ガード)。閾値 N は何分が妥当か。最終更新時刻フィールドが無い場合の代替は?
   - 案2: 経路3で拾った lv は「視聴中」ではなく「最後に見た配信」と見出しを変えて別扱いにする(消さずに正直な表示にする)。
   - 案3: nls_last_watch_url に保存時刻も持たせ、古い last_watch_url は経路3で使わない(content 側の書き込み変更が要る)。
   - 案4: その他(タブ消滅イベントで last_watch_url をクリアする等)。
B. status の「軽さ鉄則(毎回の storage read を増やすな)」を守りつつ実現するには、どの案が最小コストか。経路3でだけ追加 read 1回は許容範囲か。
C. ユーザーの方針は「余計なものを残さない(余計なのがあると人間もAIも間違える)」。死んだ配信が『視聴中』と居座るのは『余計な誤情報』。この価値観に最も合うのはどの案か。「正直な表示(最後に見た配信と明示)」と「消す(鮮度で出さない)」のどちらがユーザー体験として良いか。

技術前提: Chrome MV3 / chrome.storage.local / status.html は2秒ごと更新・軽さ最優先。推測と確証を分け、日本語で。実装の具体(どのフィールドを見て何分で切るか)まで踏み込んでほしい。
