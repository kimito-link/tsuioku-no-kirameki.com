お題: Chrome拡張「君斗りんくの追憶のきらめき」(ニコ生コメント記録・応援可視化)の【会場モード】で、配信に参加した【全員】を顔(サムネ)付きで会場に並べたい。ユーザー要望(確定)=「とにかく全員。もちろんサムネあり優先。サムネ付きで500人並べば理想。SHOWROOM感です」。実機では過去に【482人配信】があり「会場参加者482人と表示しているのに席に出るのは約96人、残りは点描に逃げて顔が出ない。全員を抜け漏れなく顔付きで入れたい」という同じ要望が出ている。星野ロミ(リスクを取って大胆・摩擦ゼロ・失敗体験の除去・既存資産を最大活用・見やすさ最優先)ならどう実現するかで会議してほしい。

== 現状(実コードで裏取り済み・src/extension/venueBar.js + src/lib/venueSeats.js + venueViewport.js) ==

[席に座る資格]
- 席に座るのは【アクティブユーザー】=コメント/ギフト/広告(貢献)でアクションし userId が観測できた人。匿名(a:xxx・184)か数値IDかは無関係=全員が会場の主役。資格の正本は venueParticipantKey。
- 配信者本人は除外済み(v0.1.901)。来場者数(PV・無言視聴者)は userId が取れない=席に出せない=背景の点描 Canvas で別表現。これは原理的制約(NDGRで無言視聴者一覧は取れない)。

[現在の描画=8段の3Dひな壇方式]
- 席プールは固定150ノード(VENUE_FULLSCREEN_MAX_SEATS=150)。seatNodes を起動時に150個作って使い回す。
- 同時表示数 = resolveVisibleArenaCount({ totalCount, perRow, rows:8 }) = Math.min(total, perRow×8段, hardCap)。hardCap は resolveDynamicArenaCap(total)= clamp(base60, floor(total×0.5), max150)。つまり同時表示は最大150席で頭打ち。
- 8段の「ひな壇」は buildVenueTiers が段ごとに depth を返し、CSS変数 --nlsb-tier-y(奥ほど上へ -18px×depth)/--nlsb-tier-z(-72px×depth)/--nlsb-tier-scale(奥ほど縮小)で【3D遠近=奥に縮んでいく】見た目を作る。縦スクロール会場ではなく、固定8段に詰めて奥行きで見せる方式。
- 入りきらない人(visibleSeats に入れなかったアクティブ参加者)は totalAnonymous=「ほか N人」として【点描 Canvas(crowdCanvas)】に逃がす。タイトルは「会場参加者 96人 ・ ほか 386人」のように出る。←【これが「482人なのに96人しか顔が出ない」の正体】。
- 席タイル本体は popup の本物 buildPersonTileEl で描画(v0.1.900・独自実装は撤廃済)。演出(VIP拡大/常連オーラ/発話/streak)はラッパー .nlsb-seat に被せる。
- サムネ優先は部分実装済: partitionThumbnailFirst で実サムネ(http顔写真 or 数値ID由来アイコン)持ちを visibleSeats の先頭へ寄せ、手前段(tier0=大)から埋める。実サムネ持ちは .nlsb-seat-vip で少し大きく明るく。
- 会場の最大高さは人数連動(resolveVenueMaxHeightVh): ~16人=48vh / ~64人=56vh / ~150人=64vh / それ超=72vh。中央の配信映像セーフエリアは grid で空けて素通し(スモーク禁止の過去方針)。
- レイアウトは全幅化済(v0.1.899): .nlsb-stage-layout を width:100% にして perRow が実画面幅に追従するようにした。だが同時表示の頭打ち(150)と8段ひな壇は変えていない。

[診断の土台]
- lastRosterInput = { allSeats, visibleSeats, audienceCount } を毎描画で保持済(誰が顔付き席/点描かを data 化できる土台はある)。ただし「メンバー一覧」ボタンの画面表示はまだ無い。

[性能の世界定石(過去調査・出典付き・council/venue-fill-canvas 等)]
- 482人程度なら DOM で十分(Canvas点描は数千人〜で初めて検討)。ボトルネックはノード数より「画像同時デコード」と「画面外レイアウト計算」。
- 最優先策= content-visibility:auto; contain-intrinsic-size:auto <h>; を高さ固定のアバターセルに付ける=ブラウザが画面外をスキップ(実測 583ms→6ms)。自前仮想スクロール不要。
- 罠(過去 v0.1.648 で踏んだ): 高さ可変だと placeholder とズレて白化する→セルは高さ固定・入れ子二重指定しない。
- 顔画像は IntersectionObserver で遅延ロード(500枚同時デコード回避)。grid-auto-flow:dense は席順を壊すので避ける。LOD=前列は実サムネ顔/奥はゆっくり顔やシルエットでも顔は出す。

== 設計の核心(会議で解くべき緊張関係) ==
A. 現在の【8段3Dひな壇(奥に縮む)】と【全員500人を縦スクロールで顔付き表示】は設計が衝突する。8段固定で奥に縮める方式は、500人を入れると奥が潰れて顔が読めない。全員出すなら(a)段数を大幅に増やして縦スクロール会場に作り替える(3D遠近は捨てるか弱める)か、(b)3Dひな壇の世界観を保ったまま段数可変+縦スクロールにするか、の判断が要る。
B. サムネ持ち優先=「サムネ付き500人が理想」。実サムネ(顔写真)持ちを必ず手前・大きく、サムネ無し(匿名のゆっくり顔)は奥・小さくても顔は出す、というLOD階層をどう全員規模で破綻なく出すか。
C. 「会場参加者N人・ほかM人(点描)」の二層を、全員顔付きにしたら点描は要らなくなるのか? それとも点描は「無言視聴者(PV・席資格なし)」専用に残すのか(席資格ありの人は全員顔、PVだけ点描背景、の整理)。
D. 性能=500セルでも軽く保つ(content-visibility + 遅延ロード)。映像セーフエリア(中央の配信映像)は潰さない(スモーク禁止の過去方針厳守)。

== 重要な過去の失敗(前提として必ず踏まえる) ==
- 「会場モードで配信画面以外を壁で覆う」案を、実機を見ずに大きく作って実装したら、配信映像とコメント欄まで黒く覆って却下された。会議4体も誤った前提(壁で覆う)に引きずられ全員その方向で一致した=【会議は前提が誤ると全員で同じ方向に間違える】。だから今回も、各メンバーは前提自体を疑い、実機で確認すべき点を明示すること。
- 「縦8段にしたのに DOM のひな壇ノードが5個固定で5段に詰め込み窮屈化」した過去がある=【純関数だけ変えて DOM/CSS を実機で確認しないと壊れる】。段数・席プール数を変えるなら DOM(seatNodes/tierNodes)と CSS の整合を必ず指摘すること。

== 問い ==
1. 500人(理想)・全員サムネ付き・SHOWROOM感を最良で実現するレイアウトは何か。候補(これに限らない):
   (a) 縦スクロール会場に作り替え=3Dひな壇を捨て、全員を段組みで並べ overflow-y:auto で下まで見れば全員。content-visibility:auto で軽さ確保。サムネ持ちを前列予約・LODでサイズ階層。
   (b) 3Dひな壇の世界観を保ったまま段数可変(8固定をやめる)+縦パン/スクロール。奥行きは手前数段だけにし、それ以降はフラットに全員。
   (c) その他の星野ロミ的アイデア(大胆だが見やすい・没入感最大・既存資産=buildPersonTileEl/吹き出し/3キャラ/ヒートを活かす)。
2. 同時表示の頭打ち(現 hardCap=150)をどう外すか。500人をDOM化して軽さを保つ具体策(content-visibility の付け方・高さ固定・遅延ロード・席プールを150固定からどう増やすか=全員ぶんプールするか可変生成か)。回帰リスク(白化・席churn・吹き出し座標)。
3. サムネ持ち優先のLOD階層を全員規模でどう破綻なく出すか。実サムネ→数値ID由来アイコン→ゆっくり顔→(最奥)シルエット、の優先と席配置。手前段=大・奥段=小でも顔は出す方針との両立。
4. 「会場参加者N人・ほか(点描)M人」の二層を全員顔付き化したらどう整理するか。点描 Canvas は無言視聴者(PV・席資格なし)専用に残すか、廃止か。
5. 最小ブラスト半径で段階リリースするなら、どの順でPRを切るか(例: PR1=診断ボタンで現状の「N人中何人席か」を可視化→PR2=cap撤廃+content-visibility で全員→PR3=サムネ優先LOD強化→PR4=画像遅延ロード)。各段で実機確認を挟む前提。

評価軸: ①全員(理想500)が顔付きで出るか(抜け漏れゼロ) ②サムネ持ちが優先・手前で目立つか(SHOWROOM感) ③配信映像セーフエリアを潰さない(スモーク禁止厳守) ④500セルでも軽い(content-visibility/遅延ロード) ⑤実装/保守コストと回帰リスク(最小ブラスト半径・DOM/CSSとの整合) ⑥段階リリースで各段に実機確認の検証ポイントがあるか ⑦星野ロミらしさ(大胆・摩擦ゼロ・既存資産活用)。

各メンバーは『結論 → 根拠 → 反論・リスク → 具体案(どの関数/CSS/DOMをどう変えるか・PR段階)』の4ブロックで。批判役は必ず穴を1つ指摘し、前提(3Dひな壇を捨ててよいか・点描を残すか)自体も疑うこと。司令塔(Claude)が最後に統合・裏取りして1案に収束させる。最優先は「配信映像を隠さず、全員(理想500)をサムネ優先で顔付きに並べ、軽さを保つ」設計。
