お題: Chrome拡張(MV3・ニコ生コメント記録)で、過去ログ取得(backfill)が「走っている表示(running:true)なのに1セグメントも1件も進まない(seg:0・rows:0)」配信がある。ユーザーは「一気に全部取れる前提が崩れている」と訴えている。この真因究明と、安全(BAN回避)な範囲での対策を設計したい。

== 実コードで裏取り済みの事実 ==

[アーキテクチャ]
- backfill は SW(service worker)で走る。crawlNdgrBackward(src/lib/ndgrBackfillCrawl.js)という純ジェネレータが、NDGR(mpn.live.nicovideo.jp・watchと別オリジン)の view エンドポイントを叩き、ChunkedEntry の `backward` URI を辿って過去へ遡り、各 `segment` URI を fetch して実コメントを yield する。
- backfill-sw-entry.js の for(;;) ループが gen.next() を回し、ev.segmentsFetched で state.seg を、ndgrChatsToMergeRows(ev.chats) の長さで state.rows を更新する。
- fetch は credentials:'omit' 必須・CORS *・SW の特権 fetch。throttle は backward hop 間 15ms(NDGR_BACKFILL_MIN_GAP)。cap は segments:20000 / elapsedMs:900000(15分) / bytes:60MB / rows:100000。これらは「BAN回避のため意図的に保守的」と設計コメントに明記。並列度は1(直列)。
- 「雑に並列増強/throttle緩和すると BAN リスク」が過去の引き継ぎ警告。backfill は既に慎重設計。

[実機の動かぬ証拠(状態速報 romiDebug.backfill)]
配信 lv350804432(6:55開始を経過2:06で途中参加・公式761コメント・記録153=20%):
  running: true, rows: 0, seg: 0, done: 0
  fullSweepForced: true, ndgrViewBaseObserved: true, resumeFromVpos: null, gapRearmCount: 1
  triedLiveId: ""  ← 空(注目)
- NDGR はリアルタイム接続は生きている(ndgrLastReceivedAgo: 13930ms・networkErrorProbe.ndgrConnectStatus: "connected")。
- 記録153件の内訳(commentIngestBySource): backfill:0 / deep:131 / mutation:147 / ndgr:2 / visible:307。→ backfill 由来は0件。deep harvest と mutation/visible(画面スクロール由来)だけで153件。
- つまり「過去ログ遡り(backfill)」が実質1件も寄与していない。20%は NDGR接続後の新規分 + deep harvest(画面に見えている範囲)だけ。

[注目点]
- seg:0 = crawlNdgrBackward が【最初のセグメントを yield する前】で止まっている(view fetch か decode か backward 取得の初手で詰まっている)。
- triedLiveId:"" が空 = backfill が「どの配信を遡るか」を確定できていない可能性。fullSweepForced:true・ndgrViewBaseObserved:true なのに triedLiveId が空なのは不整合の疑い。
- running:true のまま seg:0 が続く = ループに入る前(viewBase 解決待ち/初回fetch待ち)で pending、または毎回 backward_exhausted で即終了して再起動を繰り返している、のどちらか。

== 問い ==
1. backfill が running:true・seg:0・rows:0・triedLiveId:"" で進まない最有力の真因は何か。候補:
   (a) viewBase は ndgrViewBaseObserved:true だが、それを crawlNdgrBackward に渡す経路が途中参加配信で欠落し初回 view fetch が走らない
   (b) 初回 view fetch(?at={unixtime})は走るが ChunkedEntry の backward URI が空/decode 失敗で即 done(backward_exhausted)になり seg:0 のまま完走扱い→再起動ループ
   (c) SW の keepalive(20秒)で初回 fetch 完了前に SW が落ち、毎回ゼロからやり直して進まない
   (d) その他
2. それぞれの仮説を「次にどの計器(状態速報に出す値)を足せば実データで確定できるか」。コードを推測で直す前に、seg:0 で止まる箇所を一発で切り分ける観測値を設計せよ(stopReason・初回fetchの成否/ステータス・viewBase の有無・gen が yield した回数・done に至った理由)。
3. 安全(BAN ゼロ)に直せる範囲はどこまでか。throttle緩和や並列増強は禁止(BANリスク)。計器で真因が「初手で詰まる」と分かった場合、初手だけを堅牢化する(viewBase 受け渡し修正・初回fetchリトライ・SW keepalive 延命)のは安全か。

評価軸: ①ユーザーの「一気に取れる/100%」体感に効くか ②MV3 SW・ニコ生サーバ負荷・BANリスクの安全性 ③実装/保守コストと回帰リスク ④self-verifying(嘘で緑にしない・推測でコアをいじらない=まず計器で真因確定)との整合。
