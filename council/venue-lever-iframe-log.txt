## 結論  
iframeを会場へ移設せず、既存の`#nls-inline-popup-host`をCSSで全画面表示し、`venueBar`の座標系をiframe内DOMと連動させる案が最小実装。ただしiframe越しなので吹き出し座標取得の破綻リスクがある。

## 根拠  
1. **iframe再利用**：`#nls-inline-popup-host`は既存で動いているiframeホストで、CSSの`position: fixed`+`width:100vw;height:100vh`で全画面表示可能。iframe本体は再ロードせず、`display:none→block`で即表示できる。  
2. **キャラ演出流用**：`ensureInlineLoadingPlaceholder`の既存演出を`venueMode`フラグで条件分岐し、`voicevoxClient.synthesizeVoice`のウォームアップを`requestAnimationFrame`で演出終了後に走らせることで最小コスト。  
3. **吹き出し実装**：iframe内DOMの座標を`getBoundingClientRect()`で取得し、親ドキュメントの`bubbleLayer`にポジションを`postMessage`で連携。iframeの`sandbox`属性が制限するが、現状は`allow-same-origin`が設定されているため可能。  

## 反論・リスク  
1. **iframe越し座標破綻**：`getBoundingClientRect()`で取得したiframe内座標が、親ドキュメントの`bubbleLayer`で正確に重ねられない可能性。特にズームやスケーリング時にズレが発生する。  
2. **回帰リスク**：`#nls-inline-popup-host`を全画面表示すると、通常のpopup表示時に「会場モードが強制的に開く」などの競合が発生する。`#nls-inline-popup-host`はiframeホストであり、通常モードと会場モードの切り替えロジックをフラグで分離する必要がある。  
3. **演出資産の捨てる是非**：会場ダイアログ廃止で「群衆/ヒート」などの演出資産を捨てることになり、UIの温かみが失われる。  

## 具体案  
### PR1: iframe全画面表示  
- `venueBar.js`に`toggleVenueMode()`を追加し、`#nls-inline-popup-host`に`class="venue-mode"`を付与。  
```js
document.querySelector('#nls-inline-popup-host').classList.add('venue-mode');
document.querySelector('#nls-inline-popup-host').style = 'position:fixed;left:0;top:0;width:100vw;height:100vh;z-index:2147483000';
```  
- `venueBar`の`buildVenueTiers()`を`if (!venueMode) return;`で無効化（段階的撤去）。  

### PR2: 演出とVOICEVOX同期  
- `ensureInlineLoadingPlaceholder`の終了イベントに`postMessage`で`VOICEVOX`ウォームアップをトリガー。  
```js
// content-entry.js:3181付近
ensureInlineLoadingPlaceholder().then(() => {
  window.postMessage({ type: 'VOICEVOX_WARMUP' }, '*');
});
```

## 結論（この問いへの答えを1〜2文で）
「会場モード」を新しいUIを作るのではなく、**「既存の inline iframe（popup.html）を CSS 変換（Transform）で全画面拡大・前面化し、親ドキュメントにオーバーレイ吹き出しを貼り付ける」**という、DOM 移動や再描画を一切行わない「視覚的トリック」で実現する。
これにより、中身のロジック（段組み、キャラクター、VOICEVOX 準備）は 1 行も変更せず、`venueBar.js` の独自席は「表示制御用フラグ」で無効化する最小実装（てこの原理）を実現する。

## 根拠（なぜそう言えるか）
1.  **DOM 移動のコストとリスク**: `appendChild` で iframe を移動させると、ブラウザは「別のドキュメントコンテキスト」への移動を強制され、内部状態（VOICEVOX のキュー、キャラクターのアニメーション状態、スクロール位置）がリセットされ、最悪の場合は `popup.html` の再ロードが発生する。これは「動いてるものはそのまま活かす」に反し、ロミの哲学を破壊する。
2.  **CSS Transform の「摩擦ゼロ」**: `transform: scale()` と `position: fixed` を親要素（`#nls-inline-popup-host`）に適用するだけで、視覚的には「全画面会場」になるが、DOM ツリー上の親子関係は維持されるため、内部の状態は完全に保持される。
3.  **吹き出しの座標計算**: iframe 内の座標を親ドキュメントで取得するのは `getBoundingClientRect` を跨ぐため煩雑だが、**「吹き出しを iframe 内部（popup.html）に描画する」**のではなく、**「親ドキュメント側のオーバーレイ層に、iframe の座標を基準にして吹き出しを固定する」**方が、iframe 内部の CSS 変更（既存資産）を触らずに済む。
4.  **独自席の撤去**: `venueBar.js` が生成する独自席は、会場モードが起動した瞬間に `display: none` または `visibility: hidden` で隠すだけでよく、DOM 削除（大工事）は不要。

## 反論・リスク（自分の案の弱点や、別の正解の可能性を1つ）
**リスク: iframe 内部の要素（アイコン）と親ドキュメントのオーバーレイ（吹き出し）の座標同期が、ページスクロールやウィンドウリサイズでズレる可能性。**
*   **批判視点**: 「iframe を拡大するだけなら、スクロール時に吹き出しがアイコンから剥がれるのではないか？また、自作の会場演出（群衆やヒートマップ）を放棄するのはもったいないのではないか？」
*   **対抗策**: iframe 自体をスクロールさせない（`overflow: hidden` で固定）設計にするか、吹き出しの座標更新を `requestAnimationFrame` で常に同期させる（ただし、ロミの「最小実装」なら「スクロール不可の固定表示」が正解）。また、群衆演出は「popup.html 内部のグリッド表示」が既にその役割を果たしているため、捨てる必要はない。

## 具体案（実際に動く/作れる形で具体的に）

**【基本方針】**
会場モード = **inline iframe の視覚的拡大モード**。
独自席 = **フラグで非表示**。
吹き出し = **親ドキュメントのオーバーレイ（iframe 上）**。
演出 = **既存ローディング演出の流用**。
