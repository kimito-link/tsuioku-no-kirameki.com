# お題: 会場の「吹き出し」と「読み上げ」を設計レベルで同時化する(根本再設計)

## ユーザーの言葉
「会場モードを見たけど、吹き出しが出たドンピシャのタイミングで読み上げが走っていない。
**何か根本的な設計を変えれば一気に解決する**ので、それも含めて会議。」
(実機 v0.1.799・会場参加131人・記録1,060・読み上げON)

## 司令塔が実コードで特定した現状設計(確定・推測でない)

### 今は「吹き出し」と「読み上げ」が【意図的に切り離されている】
- 吹き出し: コメントを観測した【その瞬間】に即出す。venueBar.js:2836 のコメント:
  「吹き出しは『しゃべった瞬間』に必ず出す。音声(VOICEVOX)とは切り離す。」
- 読み上げ: VoicePlayer の合成キュー(件数ゲート8件・先読み合成・1本ずつ再生)を経て、
  数百ms〜数秒後に鳴る。voicePlayer.js。
- なぜ切り離したか(v0.1.757): 旧実装は「声の再生開始(onPlayStart)で吹き出す」だったが、
  VOICEVOX が無い/未起動だと声が鳴らず onPlayStart が来ない→吹き出しが永久に出ないバグ。
  そこで「吹き出しは視覚要素なので音声の成否に依存させない」= 即時表示に。

### 結果として起きていること(ずれの構造)
- 吹き出しは t=0 に出る。読み上げは t=Δ(合成+キュー待ち)に鳴る。**この Δ が可視化されない**。
- v0.1.799 で「吹き出しの pending 床 = 読み上げ鮮度ゲート(8秒)」に合わせ、
  さらに onDropped(鳴らず破棄)で unvoiced に落とす同期を入れた(ずれの寿命は改善)。
- だが「ドンピシャで同時」ではない: 吹き出しが先に出て、声は後から鳴る(または鳴らない)。
  ユーザーが見ているのは「吹き出しと声が同じ瞬間に立ち上がらない」体験。

### 既存の部分同期(v0.1.771〜799)
- onAudioStart で吹き出しを speaking に(声が鳴り始めたら強調 class nlsb-bubble-voiced)。
- onAudioEnd で done(余韻)。onDropped で unvoiced(流速寿命)。
- = 「声に合わせて吹き出しの寿命を伸ばす」後追い同期はある。「声の開始に吹き出しの出現を
  合わせる」前段同期は無い(吹き出しは常に先行)。

## 設計の選択肢(会議で詰める・どれが根本解か)

- 案A【声起点に寄せる(全面同期)】: 吹き出しを「声が鳴り始めた瞬間(onAudioStart)」に出す。
  → ドンピシャになるが、VOICEVOX 無し/OFF/stale で「鳴らないコメントの吹き出しが出ない」
    =v0.1.757 が直したバグの再来。どう両立するか(読み上げ ON かつ VOICEVOX alive のときだけ
    声起点・それ以外は即時、の二刀流?)。
- 案B【即時表示のまま、声を吹き出しに追いつかせる】: 吹き出しは即時(現状)。ただし
  「その吹き出しのコメントを最優先で今すぐ合成・再生」して Δ を最小化する(キュー先頭割込み)。
  → 速い配信で全部割込むと破綻。"今見えている吹き出し"だけ優先する設計は?
- 案C【吹き出しを2段階に】: コメント観測時は「淡い/小さい」仮表示→声が鳴り始めたら
  「本表示(強調)」に昇格。声が来なければ仮のまま流速で消える。
  → 視覚的に「声と同時に立ち上がる」感を出しつつ、鳴らないコメントも見える(v0.1.757 両立)。
- 案D【読み上げ無しを既定にして"見せる同期"に振る】等、別の発想も歓迎。

## このプロジェクトの制約(必ず守る)
- Windows + PowerShell。`npm run verify:cc`。「1変更=patch 1つ」。changelog 35字以内。
- 純ロジックは src/lib(venueBubbleLifecycle.js / voiceAgeGate.js / voicePlayer.js)に切り出して
  単体テスト。chrome.* 非依存の純関数で。
- 退行ゼロの絶対条件:
  - v0.1.757: VOICEVOX 無し/未起動/読み上げOFF でも【吹き出しは必ず出る】(声に依存させない)。
  - v0.1.773 ゼロ音声回帰を再発させない(時間ゲートで全部 stale にしない)。
  - v0.1.782: リアルタイム維持は件数ゲート主軸・速い配信で画面を埋めない
    (selectBubblesToEvict + BUBBLE_MAX で頭打ち)。
  - comeview(別窓)は TTS 連動の吹き出しを持たない別経路=会場(venueBar)だけの話。
- 多タブ/storage stall を増やさない(記録停止の再発回避=最重要)。

## 会議への質問(役割分担 + 結論→根拠→反論→具体案 の4ブロックで答えよ)
役割: 総合役=設計整合と退行防止 / 発散役=別の切り口 / 批判役=各案の穴を最低1つ /
実装役=具体的なファイル・関数・状態遷移・テスト名まで。

### Q1: 「ドンピシャ同時」を v0.1.757(声非依存で必ず吹き出す)と両立する根本設計はどれか
- 案A〜D を評価し主軸を1つ。声が鳴る経路と鳴らない経路を【同じ状態機械】で破綻なく扱うには?
  (現状 venueBubbleLifecycle の pending/speaking/done/unvoiced を拡張するか・作り替えるか)

### Q2: 「声と同時に立ち上がる」体感を最小コストで出す
- 案C(2段階表示)なら、仮表示→本表示の昇格を onAudioStart で行うだけで Δ が見えなくなるか。
- 案B(割込み合成)なら「今見えている吹き出しのコメント」をどう特定し優先合成するか。
  速い配信での暴走をどう防ぐか(可視吹き出し数 ≤ BUBBLE_MAX なので有界?)。

### Q3: Δ(合成+キュー待ち)そのものを縮められるか
- 先読み合成(_startPrefetch)は既にある。吹き出しを出した瞬間にそのコメントの合成を
  最優先 prefetch すれば、再生開始までの Δ が縮む。件数ゲート(8件)との関係は?
- 「鳴る順 = 吹き出しが出た順」を保証する設計(FIFO 厳守)で"どの声がどの吹き出しか"の
  対応を崩さないか。

### Q4(批判役の核心): 根本再設計のリスクと、まず出す MVP
- 案A(声起点)は v0.1.757 バグ再来リスク最大。案C(2段階)は状態機械が複雑化。
  「一気に解決」を狙って大改造して、ゼロ音声/吹き出し消失/画面溢れのどれかを再発させないか。
- 最小で「ドンピシャ感」が出て退行ゼロな MVP は具体的に何か(案C の仮→本昇格 + 可視コメント
  優先 prefetch の合わせ技?等)。
