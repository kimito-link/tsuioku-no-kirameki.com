# 議題: LINE導線の配線図を「任せたほうがいい」と伝わる図にする

## 前提（すべて実測済みの事実）

顧客のLINE公式アカウント導線を可視化するページを作っている。
パスワード保護付きで、タレント事務所などの見込み客に見せる。

実データ:
- 22のサイト・アプリから、5つのLINE公式アカウントへ、32本の結線
- 最大の窓口には12サイトから7本のURLが向いている
- 結線の重みに49倍の差がある（最大49箇所で使用 / 最小1箇所）
- 8サイトが複数の窓口に分岐している
- 22×5=110通りありうる組み合わせを、32本に整理してある状態

さらに、この仕組みには以下が実装済み:
- 会話ログが往復とも messages_db に貯まる
- 間が空いた相手へ、履歴を踏まえた一言を自動送信する機能
- 関連する特許が3件出願済み（文脈OS / 感情影響可視化型意思決定支援 / AI返信秘書）

## 世界事例の調査で判明していること（確認済み）

- Sankey図の定石は「1カラム8〜12ノードが上限」→ 左22件は超えている
- force-directed レイアウトは「hairball（毛玉）」になり厳禁
- chord diagram は二部グラフに公式非推奨
- Hierarchical Edge Bundling（Holten）の比喩:
  「電線を束ねて雑然さを減らし、末端で扇状に開いて挿し込むように」
- iPaaS業界は n(n-1)/2 の数式で複雑さを説得している
- 研究では「読み解ける情報が多い」のは信頼を上げ、
  「読み解けない絵の複雑さ」は信頼を下げる（両論あり）

## 問い

**この図を見た見込み客が「自分でやるより任せたほうがいい」と感じ、
かつ「管理できていない」とは思わないために、何を足し、何を削るべきか。**

特に答えてほしい点:

1. 左22件をどう扱うか。カテゴリで束ねるべきか、そのまま並べるべきか。
   束ねるとしたら、何を基準にグループ分けするのが自然か。

2. 「110通り → 32本に整理済み」という対比を出すべきか。
   出すとしたら、どういう見せ方なら押し付けがましくならないか。

3. 特許3件をどう扱うか。名称だけ出すか、何をしているかまで説明するか。
   ★出願書類には「3件の関係性は内部記録のみ」という方針が明記されている。

4. この図で「やりすぎ」になる要素は何か。逆効果になるものを指摘してほしい。

## 制約

- 実データから来ない複雑さは足さない（装飾で盛らない）
- 確かめていないことを断定しない（3色: 確認済み/切れている/未確認 を使っている）
- パスワードは共有相手を限るためのもので、本気の鍵ではない

## 追加の問い（特許をフルに活かす）

出願済みの3件は、実は一続きの構造になっている（内部整理）:

```
① 文脈OS       — 表示された情報から文脈を自動取得し、保存する
                  ★「AI返信ツールではなく、表示された文脈そのものを
                    資産化するOSレイヤー」と出願書類に明記
                  ★返信生成は意図的に含めない設計
      ↓
③ AI返信秘書   — 省略された指示を、貯めた文脈から解決して返信を作る
      ↓
② 意思決定支援 — 送信前に、受信者がどう感じるかを可視化する
```

つまり「貯める→使う→送る前に確かめる」の全段が権利化されている。

5. **この3件を、事業上の強みとしてどう見せるのが最も効くか。**
   - 単に「特許3件出願済み」と書くのは弱いか
   - 「文脈を資産化する」という思想を前面に出すべきか
   - 導線の配線図と特許を、同じ画面でどう繋げると腹落ちするか

6. **★制約との両立をどう考えるか。**
   出願書類の内部方針では「①②の出願番号は願書に記載しない」
   「①②③の関係説明は本内部記録のみ」とされている。
   一方で、事業説明としては3件が繋がっていることこそが強みに見える。
   この矛盾を、法務リスクを増やさずに解く方法はあるか。
   （名称だけ出す／機能として説明し特許とは紐づけない／
     関係性は語らず3件を並置するだけ、など）

7. **競合が真似しにくいことをどう伝えるか。**
   「システムがある」だけなら他社も言える。
   「文脈が貯まり続けている」「その使い方まで出願済み」を、
   誇張せず、しかし弱くなく伝える言い方は何か。
