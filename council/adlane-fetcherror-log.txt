### 結論
「fetch_error」という単一のラベルで「通信失敗」と「データ不在」を混ぜる現在の設計は、**「状態の混同（State Conflation）」**という根本的な欠陥です。
これを解消するための発散的な2つのアプローチを提案します。

1.  **「空の成功（Empty Success）」という新ステータスの導入（Semantic Shift）**
    *   `fetch_error` を「通信エラー」に限定し、API 成功かつ 0 件を `no_data`（または `empty`）という独立したステータスとして定義する。
    *   既存の `na`（Not Applicable）と `no_data` を明確に区別する（前者は「対象外」、後者は「対象だが存在しない」）。
2.  **「レコードの存在性」を引数として明示する型安全なインターフェース（Type-Safe Signature）**
    *   現状の「null = 未取得/0 件の曖昧な状態」を破棄し、`rows` 引数を `null | [] | [data]` の明確な区別が可能にする形式（例：`{ rows: any[], isFetched: boolean }` オブジェクト）に変更する。
    *   これにより、`northStarLaneReason.js` 内部で「0 件かどうか」を判断するロジックが、外部の「通信結果」に依存せず、純粋なデータ検証ロジックとして独立する。

---

### 根拠
1.  **現行の致命的な欠陥**:
    現状、`nicoadApiRows` が `null` になる条件が「取得失敗」か「取得成功だが 0 件」の両方を網羅しています。この「情報の圧縮（Lossy Compression）」が、`return 'fetch_error'` という誤った判定を招いています。ユーザー（および AI）にとって、「赤（エラー）」は「システムが壊れた/通信できない」という意味で、「オレンジ/グレー（該当無し）」は「システムは正常だが、その瞬間にデータがない」という意味で、心理的・機能的に全く異なります。
2.  **星野ロミ式・自己検証ループの要請**:
    「該当データが無いだけのものを赤にしない」という方針は、単なる色の変更ではなく、**「状態の定義そのもの」**を変える必要があります。`fetch_error` という名前自体が「失敗」を暗示しているため、この名前を「成功して 0 件」のケースに使うこと自体が「嘘の診断」です。
3.  **3 年後楽の構造ガード**:
    現在のコードは、`rows` の値だけで状態を推測しようとしていますが、これは「API の仕様変更（0 件をどう返すか）」に脆弱です。`isFetched` や `status` を引数に含めることで、API の振る舞いが変わっても（例：0 件を空配列ではなく null で返すようになった場合でも）、ロジックの分岐点は「通信成功フラグ」に固定され、保守性が向上します。

---

### 反論・リスク
*   **反論**: 「`no_data` という新しいステータス値を増やすと、`healthCells.js` や UI 側のマッピングロジックが増大し、バグの温床になるのではないか？」
    *   **回答**: 逆に、現在の `fetch_error` が「二つの意味」を持っていることがバグの温床です。ステータスを増やすことは「状態の分解（Decomposition）」であり、`if (state === 'error')` で全て処理する曖昧なロジックを `if (state === 'error') { ... } else if (state === 'empty') { ... }` と明確に分けることで、将来の拡張（例：「データが古すぎる」など）に対応しやすくなります。
*   **反論**: 「引数に `{ ok, status, rows }` を渡すと、既存の関数シグネチャが変わり、`northStarLaneReason.js` を触らざるを得なくなる（DO_NOT_REWRITE 違反ではないか？）」
    *   **回答**: `DO_NOT_REWRITE` は「意図（優先度テーブル）を壊すな」という意味です。引数の型を「より正確な情報源」に変えることは、意図の強化であり、破壊ではありません。むしろ、`rows` だけを見て推測する現在のロジックの方が「脆弱な推測」であり、修正すべき対象です。
*   **リスク**: 既存の `characterization test` が、`fetch_error` を期待するケース（0 件のケース）で失敗する可能性が高い。
    *   **対策**: テストケースを「通信成功 0 件」のケースと「通信失敗」のケースに分割し、それぞれ期待値を `no_data` と `fetch_error` に書き換える必要があります。これは「テストの品質向上」であり、移行コストです。

// northStarLaneReason.js
export function determineNorthStarLaneState({ ok, status, rows }) {
  if (!ok) return 'fetch_error';
  if (rows.length === 0) return 'no_ad_ranking';
  return 'ok';
}

// healthCells.js
export function northStarLevel(state) {
  switch (state) {
    case 'fetch_error':
      return 'bad';
    case 'no_ad_ranking':
      return 'na';
    case 'ok':
      return 'good';
    default:
      return 'unknown';
  }
}
