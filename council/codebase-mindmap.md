# お題: コードベースの「機能ごとマインドマップ」を自動生成する仕組みをどう作るか

## 背景・動機

ニコニコ生放送 Chrome 拡張のコードベース。規模が大きい:
- `src/extension/content-entry.js` … 16000行超のメインエンジン(記録・バックフィル・broadcaster検出・パネル描画)
- `src/extension/venueBar.js` … 2800行超の会場モードUI
- `src/extension/*-entry.js` … popup / comeview / status / venue の各エントリ
- `src/lib/*.js` … 数百個の純関数モジュール(各機能の核ロジック)

直近、こういうバグが出た:
> 会場モード(venueBar.js)に配信者本人のサムネが「匿名」として混入する。
> 真因は content-entry.js が持つ broadcasterUid/IconUrl が venueBar.js に
> 「届く経路がない」こと。データの流れが途切れていたのに、それが誰の目にも見えていなかった。

ユーザーの言葉:
> 「全てのコードがAIも人間も理解できるマインドマップみたいなのがあればミスがなくなるとおもう」

## 確定した方針(ユーザー選択済み・変更不可の前提)

1. **機能ごとのマップ**にする(記録・会場・読み上げ・ギフト・パネル描画 等の機能単位で、
   関わるファイルとデータの流れをまとめる)。ファイル全体の俯瞰図ではなく機能軸。
2. **コードから自動生成**する(import 解析・storage キー解析などで機械的に作り、
   コードが変わったら再生成すれば最新になる=手書きでズレない)。

## このプロジェクトの制約(必ず守る)

- Windows + PowerShell 環境。Unix 専用構文は避ける(AGENTS.md / ~/.claude/CLAUDE.md)。
- 既存の npm スクリプト・Node ランナーを優先。重い新規依存は入れない。
- 検証は `npm run verify:cc`(test/lint/typecheck/build/bump)で通すこと。
- ビルドは esbuild。テストは vitest。型は JSDoc + tsc(@ts-check / @ts-nocheck 混在)。
- 「1変更=patch 1つ」の version bump 文化。生成物が大きいと dist 差分が膨らむ点に注意。

## 会議への質問(役割分担 + 『結論→根拠→反論→具体案』で答える)

役割: 総合役=全体設計の整合と実現可能性 / 発散役=既存と違う切り口・他OSSの先行事例 /
批判役=各案の穴を最低1つ / 実装役=具体的なファイル名・コマンド・出力形式まで。

### Q1: 「機能ごと」の機能境界をどう機械的に決めるか

人間が機能名(記録/会場/読み上げ…)を決め打ちで定義ファイルに書くべきか、
それともコードから自動でクラスタリング(import グラフのコミュニティ検出など)すべきか。
このコードベースは entry ごとにバンドルが分かれている(content/popup/comeview/status/venue)。
entry を機能の起点にするのは妥当か。

### Q2: 何を解析して図にするか(データソース)

候補:
- ES import グラフ(誰が誰を import するか)
- chrome.storage キーの read/write(誰が書き誰が読むか=今回のバグの核)
- 関数のexport/呼び出し関係
- JSDoc コメント / ファイル冒頭コメント(設計意図)
今回のバグは「storage キーの read/write が片側しかない(書く人はいるが渡す経路がない)」型。
storage キーの producer/consumer マップは特に効きそうか。優先順位をつけて。

### Q3: 出力形式は何が最適か(AIも人間も読める)

候補:
- Mermaid (flowchart/graph) を Markdown に埋める … GitHub/エディタでそのまま図に
- 自前 HTML + SVG のインタラクティブ図 … ズーム・クリックで該当ファイルへ
- DOT/Graphviz … 別ツール必要
- JSON + 既存の可視化
「AIも人間も理解できる」が要件。AIはテキスト(Mermaid/JSONなど)を直接読める方が良い。
人間はクリックできる図が良い。両立する形は何か。dist に焼かず docs/ に置く前提。

### Q4: 「ミスがなくなる」を本当に実現するには図の生成だけで足りるか

批判的に: マインドマップを生成しても、それを「見ない」「古いまま放置」では今回のミスは防げない。
- CI/verify に「storage キーに producer はあるが consumer がない(またはその逆)を検出して警告」を
  入れる方が、図より直接「ミス検出」に効くのでは?
- 図(理解の補助)と lint(機械的検出)の役割分担はどうあるべきか。
- 今回の「broadcaster 情報が venueBar に届かない」は、図で気づけたか? lint なら検出できたか?

## 期待する最終成果(司令塔がまとめる1案)

「何を・どの順で・どのコマンドで作るか」が分かる1案。
最小で価値が出る第一歩(MVP)と、その後の拡張を分けて。
