【お題】ニコ生配信記録ツール(Chrome拡張)の「状態速報(自己診断)」を、PageSpeed Insights のような
「全項目を網羅し、各項目に合否を出し、全部✅で初めて『完全』と言える」網羅的な完全性診断にしたい。

# 背景(ユーザーの正本要求・何度も言われている)
- ユーザー要求: 「PageSpeed Insights みたいに、診断項目をこれぐらい全部網羅して、これが全部できたら完全、
  という診断にしてほしい」。今は症状を1個ずつ拾って出すだけで『網羅した合格表』になっていない。
- 個別の症状(例: スクロール白化=スクロールすると重く一瞬白くなって遅れて描画)を報告するたびに
  「診断に入れてくれ」と言われ、私(Claude)が1個ずつ手で診断に足している。これは「網羅」になっていない=
  抜けが永遠に出る。ユーザーは「最初から全部の観点を出し切る合格基準」を求めている。

# いま実コードに既にあるもの(調査済の事実・ここは作り直さない)
- src/lib/healthCells.js: buildHealthCells() が約23項目の健全度セルを生成。各セルは
  { id, label, level: 'ok'|'warn'|'bad'|'na'|'processing', value, text }。
  項目例: 取得率/userId付き保存/NDGR接続/リアルタイム取込/過去ログ(backfill)/アバター解決/描画/
  多タブ名残/北極星6レーン/コンソールエラー/storage安定/NDGRコメント/記録↔公式一致/
  会場読み上げ(タイミング・漏れ)/会場座席(配信者混入・固着)/応援レーン人数整合。
- summarizeHealthVerdict(cells): 「異常(warn/bad)ゼロなら満点=異常なし✓」を出す総合判定。
  processing(取得中=正常な途中)・na(対象外/構造的限界=匿名や該当無しで100%不可能)は『正常』扱い。
- src/lib/aiShareFullText.js: 状態速報(テキスト)本体。冒頭に「3画面パリティ総合判定」「この診断の信頼性」、
  続いて「検知された対処候補(症状→原因→次の一手)」カード、配信ごと、各種自己診断、fastDiag JSON。
  健全度セル(23項目)は『総合判定: 🔴 異常あり: 〇〇』の【1行】に圧縮されているだけで、
  PageSpeed のような『全項目を一覧で合否表示する合格表』にはなっていない。
- 個別 probe は fastDiag に観測値があるのに「読める所」に昇格していないものがある(例: scrollWhiteoutDiag=
  白化は fastDiag に回数/最終時刻/要素が入っているが、状態速報の読める本文には最近まで出ていなかった)。

# 設計の正本(守る制約)
- 星野ロミ型 role-separation-design: 「集める/集計/置く(鏡)/見せる」。見せる側(状態速報)は集計済みの
  置き場から貼るだけ・重い読み込み(storage全件read)を持たない。
- 新規 storage read を増やさない。純関数(chrome非依存)+characterization test。
- 嘘をつかない: 取得不能(匿名/構造的限界/未取得)を赤(不合格)にしない=必ず『対象外(na)/保留』にする。
  正常な配信を赤だらけにしない(失敗体験の除去)。進行中(backfill中など)は青(processing)。
- 3画面(①拡張POP/②応援ライブビュー/③純Web)で同じ状態速報を出す(共有lib経由・既に土台あり)。

# 問いたいこと(結論→根拠→反論→具体案 の型で)
1. PageSpeed 型の「網羅的完全性診断」を、既存の healthCells(23項目)+summarizeHealthVerdict を土台に
   どう構成すべきか。具体的には:
   (a) カテゴリ分け(PageSpeed の Performance/Accessibility/… に相当)はどう切るべきか。
       この製品の関心は「①コメント記録の完全性 ②取得スピード ③描画/UI健全性(白化・重さ) ④3画面パリティ
       ⑤会場/読み上げ ⑥外部値レーン(北極星)」あたり。カテゴリは何個・どう命名すべきか。
   (b) 「全部✅で完全」をどう定義するか。全セル ok か? processing/na をどう扱うか(完全の定義から外すか・
       『達成可能な項目だけで100%』とするか)。誤検知(構造的限界を不合格にする)を絶対に出さないには?
   (c) 抜け漏れを構造的に無くす方法。今は私が症状を1個ずつ足している=PageSpeed のように「観点リストを
       先に定義し、各観点に必ず1セルを割り当てる」べきか。観点の網羅リストはどう維持する(レジストリ化)?
2. 表示形式: テキストの状態速報に PageSpeed 風の『カテゴリ別スコア + 各項目✅/⚠/🔴 一覧 + 完全まであと何項目』を
   どう出すか。既存の『総合判定1行』『対処候補カード』との重複/整理は?
3. これは1回の大改修でやるべきか、小さいPRに割るべきか。割るならどう割る(最初の1本は何)。
4. 地雷: この設計で踏みやすい失敗は何か(例: na/processing の扱いを誤って『永遠に100%にならない』or
   『取れてないのに緑』になる、観点の二重カウント、テキストが長くなりすぎる 等)。
