## 結論
「軽さ最優先」かつ「既存ロジックを壊さない」最小リスクで解決するには、**案1（status 専用軽量ダイジェストの導入）に、案3（初回レンダリングの遅延ロード）を組み合わせる**のが最適解です。
特に、40KB の巨大 JSON を 2 秒ごとに `read` して `parse` している行為自体が、MV3 のストレージ I/O 特性上、最大のボトルネックであり、これを「全データ読み込み」から「必要な最小フィールドの読み込み」に切り替えることで、I/O 負荷を 90% 以上削減しつつ、表示速度を劇的に向上させます。

## 根拠
1. **I/O ボトルネックの明確化**: 実機データで 40KB の JSON が 2 秒ごとに読み込まれています。Chrome Extension の `chrome.storage.local` は単一 LevelDB で、並列読み込みが禁じられている（直列化）ため、この 40KB の読み込み＋解析（JSON.parse）が、2 秒ループの全時間を占有し、他の必須データ（lives/summaries）の取得をブロックしています。
2. **データ粒度のミスマッチ**: `status.html` が表示すべき「診断結果の要約」と、`fastDiag` が持つ「AI 共有用の生ログ（interceptFetchLog やコメント観測データなど）」は目的が異なります。現状は「巨大な生データを毎回丸ごと読み込んで、一部だけ表示し、残りを捨てている」ため、I/O と CPU の無駄が極大化しています。
3. **最小ブラスト半径の確保**: 既存の `fastDiag` キー（AI 共有用）を削除したり構造を変えたりせず、**「新しいキー（例: `status_fast_diag_lite`）」**として別物を追加するだけなら、既存の `content` 側のロジックや `AI 共有ボタン` の動作を一切壊しません。これは過去に「並列化で timeout した」失敗を繰り返さない、最も安全なアプローチです。
4. **初回表示の改善**: 初回ロード時に 40KB の読み込みを待たず、必須データ（lives/summaries）だけを先に描画し、軽量ダイジェストは後から差し替える「スプラッシュスクリーン的」な挙動（案3の応用）にすることで、「開くのが重い」という体感を即座に消せます。

## 結論
案1(fastDiag を status 用に軽量化)が最も確度が高い原因に対処する方法です。

## 根拠
fastDiag は約 40KB の巨大 JSON であり、2 秒ごとに read して JSON.parse していることが重さの原因です。案 1 は content が status 向けに軽量ダイジェストを書くことで、status が必要とする最小フィールドだけを read することができます。フル fastDiag は「AI 共有ボタンを押した時だけ」読むことで、初回ロードと 2 秒ループの両方で重さを軽減できます。

## 反論・リスク
- content 側で軽量ダイジェストを書く処理が追加されることで、content 側の負荷が増える可能性があります。
- 並行化を試みた場合、LevelDB の競合により timeout が発生する可能性があります。
- 計測せずに直すと、他の部分で重さが発生する可能性があります。
- adopt する場合は、_stepMs 計器でどの read が律速かを実測する必要があります。

## 具体案
1. content 側で status 用の軽量ダイジェストを書く処理を追加します。
2. status 側で軽量ダイジェストを read するように変更します。
3. フル fastDiag は「AI 共有ボタンを押した時だけ」読むように変更します。
4. _stepMs 計器でどの read が律速かを実測し、必要に応じて最適化します。
