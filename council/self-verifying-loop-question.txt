お題: X投稿で話題の「self-verifying loop(300体のエージェントが並列で出力を生成し、別モデルがソースと突き合わせて検証・間違いが残る限りループを止めない)」の思想を、この個人開発のChrome拡張プロジェクトの開発フローに、過剰でなく実効ある形で取り入れる。

# 元ネタ(要点)
- 300並列エージェント+別モデルがソース照合で全出力を検証・12失敗→3→0と間違いゼロまでループ。「人が1行読む前に自分のミスを捕まえる」。バズ投稿で宣伝色あり=鵜呑み禁止。
- 本質は「規模(300体)」でなく「①出力をソースに突き合わせて検証 ②間違いが残る限り直しループ」。

# このプロジェクトの現状(実コードで棚卸し済み・これが前提)
既に自己検証ゲートが厚い:
- 機械照合ゲート(ループの核心と同種): tree-map:check(地図がコードとズレたら落ちる)/ site-health:check(内部リンク先のディスク実在照合)/ feature-map:check(機能依存図の腐り検知)/ verify:bump(manifest/package/changelog の版同期)。drift があれば verify:cc が落ちる=ソース照合で自分のミスを捕まえている。
- 正しさゲート: test(vitest)/lint/typecheck/build/e2e(playwright)。
- impact-check(3機能以上波及を警告)。
- 司令塔運用(AGENTS.md §T): 会議(マルチLLM並列)→Claudeが実コードで裏取り→1案→verify:cc 緑まで通さない。今日2回、会議のハルシネ/不足をgrepで訂正し誤実装を防いだ実績(ナビ・stale-DOM)。
- 制約: 個人開発・Claude Max のクレジット温存(無闇に大量エージェントを常用しない)。Windows/PowerShell。記録本体不可侵。verify:cc はローカル手動。

# 問い(これに答えて)
1. 元ネタの「①ソース照合 ②間違い残る限りループ」のうち、本プロジェクトに【既にある】のはどれで、【足りない/弱い】のはどれか。実態(上記ゲート群)を踏まえ具体的に。規模(並列数)を増やすのは本質か、罠か。
2. 「検証可能なもの(機械照合できる事実)」と「検証不能なもの(UI/UX・設計判断=正解が一つでない)」の線引き。self-verifying loop を適用すべきは前者だけ、という理解で正しいか。後者(今日のナビ設計=死にリンク可否をロミ思想+ユーザー確認で決めた)に自動ループを適用するのは何が危険か。
3. 「間違いが残る限り止めないループ」を本プロジェクトで具体化するなら、何を自動ループ化するのが費用対効果が高いか。候補: (a)/code-review を指摘ゼロまで自動反復 (b)新規の機械照合 :check を増やす(例: changelog文言とコードの整合・診断文言の事実性照合のような“嘘検出”) (c)会議→裏取りのループ自体を構造化。それぞれの効果と、Claude Max クレジット浪費/hot path/storageを重くする等の罠。
4. 今日の stale-DOM 事件(診断が「公式値レーンが混乱」と嘘をつき、ソース照合(Explore+grep)で嘘を捕まえて訂正)は、まさに self-verifying loop の縮小実例。これを“仕組み”に昇華するなら何を足すか。例: 「ユーザー向け診断文言が主張する因果が、実コードの経路と一致するか」を機械 or 半自動で照合する仕掛けは現実的か。過剰か。
5. やってはいけない過剰実装を1つ以上(批判役は必ず穴を指摘): 例=300体を真似て常時大量エージェント(クレジット枯渇)/正解が一つでないUI判断を自動ループに乗せて暴走/検証のための検証を増やしてメンテ不能。

# 星野ロミ式(判断軸)
落とさない・既存データ(既にあるゲート)を活かす・過剰実装回避(完成優先)・失敗体験の除去(今日の“嘘の診断”はまさに失敗体験)。

出力は『結論 → 根拠 → 反論・リスク → 具体案』の4ブロックで。具体案は「明日から/次の1コミットで何を足すか」まで具体に。架空のツール名を作らない。
