【お題】Chrome拡張①POPの「画面まるごと」を純Web③(app/live-view)に丸写しにする仕組みを設計せよ。ユーザー要望は明快「①に出てるものは全部③に丸うつしでいい」。1パネルずつ手作業で追いかける現方式では『次々これも無い』が無限に続く。1回の登録で①の全パネルが③に漏れなく出る根本アーキが要る。

## ユーザーの言葉(重要)
- 「まるうつしでいいのに」= 中身を理解して③用に作り直すのでなく、①が描いたものをそのまま③に映したい。
- 実配信中に③を見て「応援タイムラインが無い」「投げ一覧(14件)が無い」「これも無い問題ありまくり」と次々報告。1個直すと次が出る状態。
- 最終ゴール: ③が①の完全丸写しになれば、それをCapacitor/TWAで包んでスマホアプリ化できる。

## ★実測で裏取りした正確な現状(2026-07-07・本番③の生jsonBlobを実際にfetchして確認)
jsonBlob に実在するキー: generatedAt / snapshotMeta / overview / lives / fastDiag / laneMirror / statCardsMirror / northStarMirror / topSupporters / commentTimelineMirror / parityVerdict / statusReport

③に「本当に届いて描けている」もの(鏡データが jsonBlob に実在):
- laneMirror(応援レーン) / statCardsMirror(数字カード) / northStarMirror(但し lanes は adRanking と contributionRanking の2本だけ) / topSupporters(応援者ランキング) / commentTimelineMirror(コメント鏡) / lives[0](配信者カード) / statusReport(①の状態速報テキスト全文をバイト一致同梱)

③に「①では出るが鏡データが来ていない=出しようがない」もの(実測で欠落を確認):
- **投げ一覧(giftHistory・koken API・14件のギフト投げ詳細テーブル)**: northStarMirror.lanes に giftHistory が【無い】(adRanking/contributionRanking のみ)。ホストDOM northStarLaneThrows-giftHistory は③htmlに存在するが innerLen:0=空。
- **配信採点パネル(broadcastScoreDetails)**: ③htmlにホストDOMすら無い。jsonBlobに broadcastScore 鏡無し。
- **セッション比較(sessionSummaryCompareMount)**: 同上。
- **ギフトサイドバー履歴(giftSubAppHistoryMount)**: ③htmlにホスト有りだが innerLen:0=空・鏡無し。
- **室温/ルーム熱度(roomHeatSummary)**: ③htmlにホスト有り・何か557字描画されているが「+0件/0人」=laneMirror由来の別物で、①のroomHeat鏡は来ていない疑い。
- **応援タイムライン(第1号で実装済・未デプロイ)**: commentTimelineMirror は届いているが、③の描画が最新1件ティッカーのみだった→鏡→本物paint配線を足す実装をローカル実証済み(feat/web-mirror-timeline-parity・未マージ)。

## 現方式の構造(なぜ次々抜けるか・実コード)
- ①各パネルは popup-entry.js の refresh/render 関数が storage 生データから描く。
- ③に出すには「①で鏡(最小データ)を作り publish → status-entry.js:1555-1595 の jsonBlob 組立に1フィールド追加 → mirrorBundle SECTION_KEYS 追加 → ③ app/live-view.js の paintAllMirrors に paint 関数追加 → ③htmlにホストDOM → selfDiag突合」の【手作業5〜6箇所】。どれか忘れてもコンパイルもテストも通る(safeSection try/catch が握りつぶす)。だから1パネルずつ抜ける。
- 前段の設計(reference_web_mirror_parity_SYNTHESIS.md)は「セクションレジストリ(1箇所登録→機械展開+CI赤で忘れ検知)」を提案し、第1号(応援タイムライン)は実装・ローカル実証済み。だが【各パネルの鏡データ生成は依然パネルごとに要る】。

## 核心の問い(ユーザーの「まるうつしでいい」に本気で応える)
Q1. 「①の画面を丸ごと③に映す」最善アーキは何か。選択肢:
  (a) セクションレジストリで残りパネルを1つずつ機械的に埋める(前段設計の継続。鏡データ生成は各パネル分要る)
  (b) ①が statusReport のように【描画済みHTMLor構造化データを丸ごと1つ送る】方式に寄せ、③は貼るだけにする(パネル追加で③の作業ゼロに近づく)。前段会議ではDOMシリアライズを容量/ライブ性/CSP/資産破棄で却下したが、ユーザーの「まるうつしでいい」を最優先に再評価せよ。却下は妥当か? 部分的に(重いパネルだけHTML同梱)は成立するか?
  (c) ハイブリッド: 軽い構造データは鏡(既存資産流用)、複雑パネル(採点/投げ一覧/セッション比較)は①の描画済みHTMLスニペットを sanitize して同梱し③は貼るだけ。
  容量上限448KB(prune はしご既存)・ちらつきdiff-skip・referrer露出回避・③のchrome非依存・スマホWebViewで落ちない、を満たしつつ「①のパネル追加で③が自動追従」に最も近いのはどれか。1案を明確に推せ。
Q2. 投げ一覧(giftHistory)を今すぐ③に出すなら、Q1の選んだ方式でどう実装するか(触るファイル:行)。
Q3. 「①にパネルを足したら③にも自動で出る/出てなければCIが赤」を、どこまで自動化できるか。人間が絶対忘れない最小の規律は何か。
Q4. スマホ化(Capacitor/TWA)まで見据えたとき、丸ごと方式が審査(WebViewラップ)・容量・オフラインで不利にならないか。

## 制約・地雷
容量448KB上限(pruneはしご)・diff-skip機構触らない・voice触らない・referrer露出回避・publish経路に新規storage read足さない・既存の勝ちパターン(laneMirror等)作り直さない・fail-closed・③はVercel/拡張はcopy:ext。
