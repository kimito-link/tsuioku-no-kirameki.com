**結論**  
真因は**(A)refreshGen レース(heavy 完了前に次 refresh が追い越し 14532 で return→settled されない)**。**直し方は**(A)「最後に成功した全件 arr」を保持して次 refresh で settled=true にできるようにする**が最適。overlay 畳み漏れは同根で、正しい条件は**settled=true**。検証は**storyUserLaneRenderProbe**で settled 状態と reachedStep を観測。過剰実装のリスクは**heavy read を full 化する**こと。

---

**根拠**  
1. **refreshGenレースの証拠**  
   - 実機値から「更新所要5.2秒」「refreshGen が ++ されるたびに heavy が再読」が判明。  
   - 14532の「refreshGen !== watchPopupRefreshGeneration」は、heavy読了前のrefreshで早期returnの直接証。  
   - 7,262件のheavy readが5秒かかるが、配信中継は高速refreshが頻発するため、必然的にレースが発生。  

2. **(A)選定の理由**  
   - 「最後に成功した全件arr」を保持することで、heavy読了前のrefreshでも既存データを再利用可能。  
   - 既存の**provisional値を上書きせず、全件データの再利用**がロミ式「既存データ活かす」に合致。  
   - (B)settledをper-live持ち越すは、配信終了後のclean-upが難しく、配信途中の再利用に不適。  

3. **overlay畳み漏れは同根**  
   - 描画完了≠ローディング終了。**settled=false**のままprovisional表示→ローディングoverlayが残る。  
   - 正しい条件は**settled=true OR heavy読了後**。entries>0は10件でも成り立つが、プロダクションでは「全件未読了」が原因。  

4. **検証計器の有効性**  
   - **storyUserLaneRenderProbe**は既存でsettled/reachedStepを記録しており、14530-14542のreturn経路の観測が可能。  
   - 軽配信では14542の「arrCoversTotal」が成立し、重配信ではrefreshGenレースが支配的。

### groq/llama-3.3-70b  [爆速の視点]  (2396ms)

### 結論
真因は、**(A)refreshGen レース(heavy 完了前に次 refresh が追い越し 14532 で return→settled されない)** であると考えられる。実機の状態速報で「更新所要 5.2秒」という遅延のある更新と、重い配信の場合に heavy read が遅く、次の refresh が来て refreshGen が進む前に heavy が完了しないという状況が、この仮説を裏付ける。

### 根拠
- 実機の負荷と更新所要時間が長いことから、heavy read が遅いことが推測され、次の refresh が来る前に heavy が完了しない可能性が高い。
- 14532 の早期 return 条件が refreshGen の進みに応じて発生し、watchPopupHeavyCommentsSettled が true になる前に return されることが考えられる。

### 反論・リスク
- 他の条件 (B, C, D) も考えられるが、 refreshGen の進みと heavy read の遅れが最も実機の状況と一致する。
- refreshGen の進みを止めるなどの対策を講じないと、settled が true になる前に次の refresh が発生し、heavy が詰まる可能性がある。

### 具体案
1. **まず実機/計器で何を確認するか**: storyUserLaneRenderProbe に settled/reachedStep があるということから、このプローブを使用して、実機で watchPopupHeavyCommentsSettled が true になるか、ならないなら 14530-14542 のどれで return しているかを観測する。
2. **直すなら最小のファイル:関数**: `popup-entry.js` の `selectLaneFeedCommentRows` 関数内で、heavy が追い越されても「最後に成功した全件 arr」を保持して次の refresh で settled=true にできるようにする。
   - 例えば、`watchPopupHeavyCommentsSettled` を refresh ローカルでなく、per-live で持ち越すことで、heavy の読み込み完了を待つことができる。
   - または、refresh を throttle して heavy 完了を待つようにする。

### groq/gpt-oss-120b  [批判・詰め（推論特化）]  (4102ms)
========================================================================
**結論**  
1. **最有力の真因は (A) 「refreshGen レース」** ― heavy コメントの取得が完了する前に次の refresh が走り、`refreshGen` が進んでしまうため `watchPopupHeavyCommentsSettled` が `false` のまま early‑return（14532）され、全件集約がレーンに渡らない。  
2. **最小で確実に効く修正は (A)「heavy が追い越されても最後に成功した全件配列を保持し、次の refresh で `settled=true` にできるようにする」**。これにより、レーンは過去に取得した完全データを再利用でき、`entriesLen` が 10 に固定される事態を防げる。  
3. 「描画済みなのにローディングが終わらない」 overlay は **settled が立たないことと同根** である。ローディングは `settled === true && entries.length > 0` を条件に畳む実装なので、settled が false のまま描画が走ると overlay が永遠に残る。正しい条件は **「全件 heavy 取得が完了（settled）かつ描画対象エントリが 1 件以上」** とすべき。  
4. **検証で見るべき指標** は `storyUserLaneRenderProbe.settled` と `reachedStep`、および `watchPopupHeavyCommentsSettled` が true になるかどうか。軽い配信では 14530‑14542 のどれもヒットせず true になるが、重い配信では 14532 が頻発するはず。これらをコンソール/telemetry に出力すれば原因が確定できる。  
5. **やってはいけない過剰実装**：`settled` を安易に `true` に固定して別配信の heavy データを混入させること。これにより匿名応援が不正確に増え、他ライブのデータ漏洩・UI ちらつきが再発する。
