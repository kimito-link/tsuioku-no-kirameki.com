# お題: 星野ロミ式でソースコードのコンポーネント化・ファクタリングを最大化する

## 背景(司令塔が実コードで確認済みの事実)

ニコ生視聴を盛り上げる Chrome 拡張(MV3)。**巨大な entry ファイルに機能が集中**している:
- `src/extension/content-entry.js` … 約 **17,000 行**(記録エンジン・NDGR デコード配線・backfill・
  プロフィール解決・avatar/nickname enrich・storage 読み書き・診断…が全部入り)。max-lines ラチェット **17,297**。
- `src/extension/popup-entry.js` … 約 **21,217 行**(popup UI・応援レーン描画・HTML/マーケ/メディアキット
  エクスポート・吹き出し・各種ボタン…)。max-lines ラチェット **21,217**(『増やす禁止』と明記)。
- 既に `src/lib/*.js`(純関数)へ抽出する文化はある(monotonicCommentCount / ndgrDecode / ndgrChatRows /
  commentRecord / statusFormat / commentChunkStore / blobDownload / exportWaitNarration / reportCompleteVoice 等)。
  しかし entry 本体は依然巨大で、1 機能直すたびに巨大ファイルを読む必要があり【クラッシュ・事故の温床】。
- バンドルは esbuild(entry=機能境界)。`scripts/feature-map.mjs` で import グラフ+storage バス図を自動生成済み。
- ⚠️ 制約: **記録の永続(IndexedDB/chunk/テール)の不変条件を壊さない**・**新しい storage 書き込みを増やさない**
  (過去に storage 飽和事故)・**挙動完全不変のリファクタのみ**(機能追加でなく構造改善)・純関数化してテスト可能に。

## 星野ロミ式の原則(司令塔が deep-research で裏取り済み・本お題の評価軸)
1. 既にあるデータ/資産を最大限活かす(車輪の再発明をしない・既存の純関数/抽出文化に乗る)。
2. 重くしない・有界・割り切る(過剰な抽象化・レイヤリングはしない。動く最短の構造)。
3. 失敗体験の除去・体感最優先(リファクタで挙動やパフォーマンスを劣化させない)。
4. 完成させるために必要な最短の仕組みを選ぶ(理想の DDD より、今の規模で壊れにくくなる粒度)。
5. 計測志向(どこから手を付けると最も効くか=効果の大きい順に)。

## 問い(これに答えてほしい)

1. **巨大 entry(content-entry.js 17k / popup-entry.js 21k)を、どの粒度・どの境界で分割すべきか**。
   星野ロミ式『重くしすぎない・割り切る』を踏まえ、過剰レイヤリング(route/service/repository の3層など)に
   走らず、**今の規模で壊れにくくなる最小の分割軸**は何か。機能(feature)単位か、関心事(I/O・純ロジック・
   DOM 描画)単位か、その混合か。

2. **抽出の優先順位(効果の大きい順)**。content-entry.js / popup-entry.js の中で、まず src/lib(純関数)へ
   出すべき塊はどれか。判断基準(行数・変更頻度・テスト不在・他機能との結合度)を示し、上位 5 つ程度を挙げよ。
   ※実コードの具体名は司令塔が裏取りするので、ここでは『どんな性質の塊を優先するか』の原則と型でよい。

3. **挙動完全不変を保証するリファクタ手順**。巨大ファイルから純関数を抜くとき、デグレを出さない安全手順
   (characterization test 先行・1 関数ずつ・import 差し替えのみ・esbuild バンドル同梱確認・feature-map の
   断線チェック)を、星野ロミ式『失敗体験の除去』の観点で具体化せよ。

4. **やりすぎ防止ライン(割り切り)**。星野ロミ式では『過剰な抽象化はしない』。どこで抽出を止めるべきか
   (例: entry に残してよいのは何か=DOM 配線/Chrome API 直叩き/イベント登録 等)。コンポーネント化が
   かえって体感や保守を悪くする境界を示せ。

5. **批判役**: このリファクタの最大の罠を1つ必ず指摘せよ。例えば『純関数に抜いたつもりが entry の
   モジュール変数(broadcasterUidCache 等)に依存していて挙動が変わる』『抽出で import が循環する』
   『max-lines ラチェットを satisfy するための見せかけ分割で逆に可読性が落ちる』等。最も危険なものは?

## 出力フォーマット(厳守)
`結論 → 根拠 → 反論・リスク → 具体案(どの粒度で・どの順で・どう安全に)` の4ブロックで。
役割(統括/発散/批判/実装レビュー)に応じて視点を変えること。
