# 結論：「観測値の一本化」ではなく「IDB 集計の非同期化」と「表示層の完全分離」による双極設計

従来の「観測値（observed）をいかに安定させるか」という発想を捨て、**「表示値は IDB 実数を非同期で取得する（厳密解）」とし、「観測値（observed）は完全な診断用（内部状態）に格下げする」**という設計へ転換します。

「記録数」という概念を「画面に表示する数字」と「システム内部の推定値」に物理的に分離し、**表示層には一切の「単調化」「床」「除外」などのゲートロジックを置かず、IDB の実数をそのまま（ただし非同期で）表示する**のが正解です。これにより、ユーザー批判の根源である「数字の揺らぎ」を、システム側の推定誤差ではなく「データベースの正確な反映」として解消します。

---

# 根拠：なぜ「観測値の修正」ではダメなのか

1.  **「推定」は本質的に揺らぐ**: `observedRecordedCommentCount` は、ネットワーク遅延（gap）、ストリーミングの断絶（stall）、バックフィルの順序など、外部要因に依存して算出されます。これに「単調化」や「床」などのゲートを重ねることは、**「間違っている値を無理やり正しいように見せるパッチ」**であり、バグの蓄積（v0.1.645〜838の経緯）の根源です。
2.  **IDB は唯一の真実**: `IDB`（IndexedDB）に保存されたレコードこそが、ユーザーが実際に手元に残したコメントの「唯一の真実」です。`savedCommentsUidStats` が古いのはバグではなく、**「全件カウントの負荷を避けた結果」**です。これを「重いからやめよう」とするのではなく、「非同期で計算して表示する」ことで解決可能です。
3.  **ゲート撤去のリスクは「正しさ」で補える**: 単調化や床のようなゲートは、「不正解な値」が「正しい値」に上書きされるのを防ぐための安全網でした。しかし、**「IDB 実数」をソースにすれば、値は常に増える（または一定）であり、減ることもない**ため、単調化ロジック自体が不要になります。
4.  **星野ロミ式の実践**: 「落とさない」ためには、複雑な推定ロジックを維持するのではなく、**「重い計算を非同期化し、メインスレッドをブロックせず、結果が返るまで『読み込み中』や『前回の値』を表示する」**という、UX 的には「待機」を許容する設計が最も安全です。

---

# 反論・リスク：「IDB 全件カウント」は重すぎるのではないか？

**反論:**
「IDB の全件を数えるのは重い。特に chunk 数が膨大な場合、UI がフリーズする。」

**リスクへの回答:**
1.  **非同期実行**: カウント処理を `requestIdleCallback` や Web Worker へ移し、メインスレッド（描画・入力）をブロックしません。
2.  **段階的表示**: 最初の表示時は `observed`（推定値）を暫定的に表示し、バックグラウンドで IDB カウントが完了したら「正確な値」に更新（Replace）します。ユーザーは「数字が少し遅れて更新される」だけで、**「数字が跳ねたり減ったりする」**というストレスは消えます。
3.  **キャッシュ戦略**: カウント結果を `storage`（簡易キー）に保存するのではなく、**「lastCountedTimestamp + count」**を保存し、一定時間内（例：10 秒）はキャッシュを返し、それを超えたら再計算します。これにより、頻繁な再計算を防ぎます。
4.  **Chunk 対応**: `chunk index.total` は既に IDB にインデックスとして存在するはずです。これを直接参照するだけで、全件スキャンなしに概数（または正確数）を得るロジックが構築可能です。

**さらに、ユーザー批判への回答:**
「公式とズレる」のは、配信者除外などのフィルタリングロジックを「表示用」に持ってきたからです。これを「表示用」から外し、**「全記録数」**を表示し、フィルタリングは「詳細画面」や「別ボタン」で切り替える形にすれば、公式との比較対象が明確になります（※ただし、今回は「記録件数」の定義を「IDB 実数」に固定し、配信者除外は UI レベルのフィルタとして扱うのが最適解です）。

---

### groq/llama-3.3-70b  [爆速の視点]  (2317ms)

### 結論
ニコ生コメント記録Chrome拡張の記録件数の数字がソース/画面ごとにバラバラで正確さが崩れている問題を解決するために、根治的なアプローチが必要である。正本一本化を目指し、現状の複雑化したゲート群を整理統合する必要がある。

### 根拠
1. 現状の実装では「コメント記録の件数」という単一概念が6つの数字に分裂しており、各数字が異なるロジックで更新されるため、表示数値の正確性が崩れている。
2. ゲートの対症的経緯は、問題を解決するのではなく、複雑性を増してしまっている。
3. 正本を1つに定め、全画面がそれを見るようにすることで、複雑性を減らし、正確性を高めることができる。

### 反論・リスク
1. ゲートの撤去によって、元の病（4経路の上書き合戦・enumerate揺れ・OFF/ON max飛び）が再発する可能性がある。
2. 正本一本化によって、実際の記録数と表示数が一致しない可能性がある。
3.段階導入の順序や、表示正本の選択、各ゲートの存廃判定によって、問題の解決度が変化する可能性がある。

### 具体案
1. **段階導入の順序**：まず、診断用の数字（savedCommentsUidStats、commentIngestBySource）と表示用の数字（recordedCountForDisplay）を明確に分離する。
2. **表示正本の選択**：observedRecordedCommentCountを表示の正本に選択し、chunk index.total + tailを補助的な情報として使用する。
3. **各ゲートの存廃判定**：単調化（v0.1.645/792）と床（v0.1.804）は、正本が安定なら不要であるが、配信者除外（v0.1.774）は「記録N（うち配信者M）」と並記することで、正確性を高めることができる。
4. **第1段階で何を整理するか**：まず、表示用の数字のロジックを簡素化し、正本一本化を目指す。
5. **ゲートの整理統合**：段階的にゲートを整理統合し、安全網として残すべきゲートを判断する。
6. **characterization test**：各段階で「増えて減る/0潰れ」回帰を固定し、問題の解決度を確認する。

### groq/gpt-oss-120b  [批判・詰め（推論特化）]  (7291ms)
========================================================================
**結論**  
→ **正本は `IDB 実レコード数（集計は軽量サマリ）` を唯一の真実とし、全画面がそれだけを見る**。  
→ 表示ロジックは **「観測‐推定」** から **「DB‑サマリ」** へ完全に切り替える。  
→ 既存の 6 つのカウントは **「診断用」** と **「表示用」** に二分し、**表示用は 1 本だけ（DB‑サマリ）**、**診断用はそのまま残す**（ただし名前とドキュメントを整備）。  
→ ゲートは **「正本が安定すれば全て撤去できる」** とみなすが、**安全網として最小限の「単調化」だけは残す**（増減防止だけに限定）。  

---

### 根拠  

| 項目 | 理由 |
|------|------|
| **正本の選択** | *IDB の実レコード数* は **唯一の真実** であり、ネットワーク遅延・バックフィルの揺らぎに左右されない。`observedRecordedCommentCount` は「推定」＝副作用が多く、**根本的に揺れる**。`chunk index.total` は **モード依存**（chunk / main）で不完全。 |
| **診断用と表示用の分離** | 現行コードは 6 つの数値が混在し、**「診断」＝「表示」** が不明確。分離すれば **テスト容易性** と **ユーザー向け説明責任** が向上。 |
| **ゲート撤去の効果** | すべての揺らぎは **正本が不安定** であることが根本原因。正本が安定すれば **「増えて減る」**、**「0 に潰れる」**、**「床」** といった対症は自然に消滅する。 |
| **最小限の単調化だけ残す** | 正本が DB‑サマリであれば **増減は起きない** が、**UI の再描画タイミング** で同一フレームに二度更新が走る可能性がある。**単調化（前回表示値 > 現在値なら保持）** は UI フリッカー防止だけに留め、ロジックは除外する。 |
| **段階的導入の必要性** | 既存データ・ユーザー体験を壊さずに移行するため **「一括撤去」ではなく段階的リファクタ」** が必須。テスト自動化とキャッシュのロールバックが可能になる。 |

---

### 反論・リスク  

| リスク | 内容 | 緩和策 |
|--------|------|--------|
| **IDB 集計が重い** | フルスキャンは I/O コストが高い。 | → **軽量サマリテーブル**（`commentCountSummary`）を **インクリメンタルに更新**（`persistCommentRows` が走るたびに `+1`／`-1`）。フラッシュごとにサマリだけ読むので O(1)。 |
| **非同期取得遅延** | DB‑サマリ取得が UI スレッドに乗ると遅延が顕在化。 | → **Web Worker** でサマリ取得 → **Promise** で UI に渡す。表示は **「取得中」** 状態を出すだけでユーザーに不安を与えない。 |
| **既存診断ロジックが壊れる** | `savedCommentsUidStats` などは内部デバッグに使われている。 | → **名前空間を分離**（`diagnostic.savedCommentsUidStats`）し、**表示ロジックから完全に排除**。テストはそのまま残す。 |
| **単調化残存で不必要にロジック残る** | 残すと「あとでまた増える」恐れ。 | → **フラグ `ENABLE_MONOTONIC_FALLBACK`** をデフォルト `false` にし、**回帰テストで増減が無いことが確認できたら削除**。 |
| **ユーザーが「配信者除外」情報を期待** | 現在 UI に「配信者コメント数」も表示している。 | → **別カラム `recordedCountForDisplayWithStreamer`** を作り、**表示はオプション** として提供。根本ロジックは変えない。 |
