# 会議正本: 会場の席が「時間で減る」問題 — 誰を残し誰を入れ替えるか (2026-06-17)

お題ファイル: `council/venue-seat-eviction.md`(並列分割+星野ロミ観点を追記した版)
生応答: `.artifacts/venue-seat-eviction-answers.json` / ログ `.artifacts/venue-seat-eviction-meeting.log`
実装: v0.1.790・fbc46f3e・master push 済

## 症状(ユーザー観察)

レーン鏡映(v0.1.789)で会場とレーンを一致させた後も「最初はレーンが鏡のように映って増えるのに、
時間が経つと減ってしまう気がする」。

## 司令塔が実コードで特定した真因

集約(誰が応援したか)は累積で増え続ける(`mergeUserLaneAggregates`・`userLaneCandidatesFromStorage`)=減らない。
減るのは**席割りの段階だけ**。`rankVenueParticipants(participants, maxSeats=150)` が
「①サムネ → ②ギフト → ③**最終発言が新しい順(lastAt降順)** → ④発言数」でソートして `slice(0,150)`。
満席後にしゃべった人が来る度、③のせいで**最も長く黙っている人がランキングから押し出されて席を失う**。
一度落ちた人は `assignVenueSeats` の sticky 維持にすら届かない(ランキングで先に消えるため)。
= ユーザーの「時間で減る」= 最近しゃべった順の入れ替え制。

## ユーザーの要望と気づき(対話で確定)

- 「せっかく満席にしないといけないのに減らす意味がわからない」= 一度入った人は残す(満席維持)。
- 「サムネあり優先で」「発言数多い人優先で」= 顔出し・常連を残す。
- 「さむねありや発言数多い人で150こえるのはなかなかない」= 実機でも顔出し・常連は150に届かない。
- 「あーそうか、最近喋った人も重要」= 今盛り上げてる人も入れたい(3要素のバランス)。
- 「並列という発想つかえないか」+「星野ロミならどうするか」を会議で必ず検討するよう指示。

## 会議の収束(6/12応答: groq×2/nvidia qwen3.5/gemini/openrouter/deepseek-r1。ローカル大型はVRAM競合abort)

**6体が一致**:
1. **単一ソートでなく並列プール分割**(観点Aを全員支持)。常連が新着に押し出される二者択一は枠を分ければ消える。
2. **固定配分は罠 → 優先度順の充填(Fill & Merge)**(nvidia/openrouter が明確に指摘=最重要裏取り)。
   枠を固定席数(60/30/60等)にすると実機(顔出し5人)で顔出し枠が空いて無駄。各層を未選択者だけ
   フィルタ→ソート→連結し先頭から150取れば、顔出しが少なければ常連が、常連が少なければ新着が
   自動で席を埋める「流動的満員」。星野ロミ思想(軽い・有界・O(N log N)・割り切り)とも完全一致。
3. **prevSeatByKey で sticky**=一度入った人を優先再配置。
4. **空席は "+N人応援中" で吸収**=「減った」を感じさせない(本拡張は既に anonymousCount/観客席で実装済)。

## 司令塔の裏取り(会議の擬似コードをこのコードベースに合わせて訂正)

- 会議は `Date.now()`/「30秒以内」絶対時刻を使うが、`rankVenueParticipants` は**純関数で時刻を持たない**
  (テスト不可になる)→ `lastAt` の**相対順序**だけ使う。
- 会議の `hasAvatar` は本コードでは `hasRealThumbnail(avatar)`。
- ギフトは発言数スコアに既に効く(giftCount>0=preHasGift)ので独立層は設けない(層を減らして単純化)。
- "+N人応援中" 表示は既存(匿名のにぎやかし)で足りる。今回はソート層だけ直せば席が減らなくなる。

## 最終1案(実装した)

`rankVenueParticipants(participants, maxSeats, prevSeatByKey)` を**優先度順の充填**に作り替え:
  ① 既に座っていた人(prevSeatByKey にいる・cap内) — 降ろさない(満席維持の核)
  ② 実サムネ持ち(hasRealThumbnail) — 発言数多い順
  ③ 発言数が多い人(count>=2・常連) — 黙っても残る
  ④ 最近しゃべった人(lastAt 降順) — 今の盛り上げ
各層は未選択者だけ filter→sort→push(cap まで)。固定枠なし=流動的満員。純関数・O(N log N)。
`buildVenueSeating` が `opts.prevSeatByKey` をランキングにも渡すよう接続。

## 自己批判(deepseek-r1役を司令塔が代行)と棄却

- 懸念「sticky① が150を食い尽くすと新規が永久に入れない」→ ユーザーが明示的に望んだ挙動
  (「一度入った人は残す」)。かつ実機では顔出し+常連で150は埋まらない。満席に達するのは匿名の
  にぎやかし大量来場時で、そのとき「先に来た人が残り新規は+N側」=満員ライブとして自然。棄却。

## 学び

- 「並列(枠分割)」はユーザーの「両方重要」を構造的に解く=単一ソートの奪い合いを消す。だが
  **固定配分は実データで逆効果**(顔出し5人で枠が空く)→「優先度順の充填」が正解=枠の良さ(奪い合い回避)と
  単純さ(O(N) concat+1 slice)を両取り。会議の nvidia/openrouter の裏取りが決定打。
- 会議の擬似コードは Date.now 依存でテスト不可だった→司令塔が「純関数=相対順序」に訂正。会議は素材。
- ユーザーの設計直感(「最近喋った人も重要」)が3要素バランスの会議を呼び、単純な発言数一本ソートを回避できた。
