## 会議の合意点
1. **「ズレ」は構造的**: 吹き出し=即時 / 音声=合成+再生で遅延。v0.1.771 で吹き出しを声に連動させた結果、その定常ラグが【見える】ようになった(nvidia/qwen3.5-122b・deepseek-r1 が明確に指摘=会議の核心)。
2. **2つの方向**:
   - (A) **吹き出しを音声に同期**(onAudioStart で出す)= ズレ0だが即時性を失う(nvidia最強・gemini・deepseek・groq120b)。
   - (B) **定常ラグを詰めてゼロへ寄せる**(鮮度ゲートを早く効かせ捨てる・先読み深く・速度up)= 即時性を保つ(openrouter・llama・qwen-coder)。
3. **長時間ドリフトの原因候補**: VOICEVOX内部キュー飽和・タブのバックグラウンドスロットリング・定常ラグが解消されない蓄積感。

## 司令塔の裏取りで確定した事実(会議の前提を訂正)
- **ラグは無限増殖しない=鮮度ゲートで有界**: 通常2500ms / バックログ(queue>=3)1200ms / 高優先6000ms を超えた項目は捨てる(voiceAgeGate.js)。pushVoiceQueue max=12。よって会議の一部が言う「だんだん溜まって無限に遅れる」は誤り。
- **真因=『定常ラグ』が見えるようになった**: コメントレートが合成+再生をやや上回ると queue が【1〜2件】で安定する。この帯は backlog しきい値(3件)に届かないので鮮度ゲートが【2500ms のまま】=音声が常に約1.5〜2秒遅れて流れ続ける(捨てられないが追いつきもしない定常状態)。**v0.1.771 で吹き出しがその遅れた声を待つ→「吹き出しが先・声が後」が長時間ずっと見える**。これが「だんだんズレる」の正体(時間で悪化というより、定常ラグが常時可視化)。
- **会議の (A) 全面同期は即時性を殺す**: showSpeechBubble は onLiveComments で即時に出る(会場の生命線)。これを onAudioStart まで遅らせると、声が1.5s遅れている今の状態では【吹き出しも1.5s遅れる】=ユーザーが同時に求める「リアルタイム(即時)」を失う。だから (A) 単独は不採用。
- **VOICEVOX並行合成は可・再生は1本ずつ**: 先読み深さ(resolveVoiceSynthDepth)は queue>=5 で3・>=3 で2・他1。合成リクエスト並行はできるが再生は逐次=再生時間そのものは縮められない(速度upと本文短縮でしか縮まらない)。

## 司令塔の収束案(1案・(B)主軸 + 軽い同期 + 長時間保険)
**核心=定常ラグそのものを潰す((B))。ラグが sub-second になれば、吹き出し即時のままでも声がほぼ同時に追いつき「ズレ」が体感で消える。(A)の全面同期(即時性犠牲)には倒さない。**

### 1. 定常ラグを潰す: 鮮度ゲートを「もっと早く・もっと短く」(voiceAgeGate)
- backlog しきい値を queue>=3 → **queue>=2** に下げる(1〜2件で安定する定常ラグ帯にこそ効かせる=ここが真因)。
- backlog 時のしきい値 1200ms → **800ms** 程度へ。通常 2500ms も **1500〜1800ms** へ短縮(古い声を早く捨て「今」に追従)。
- → 効果: 遅れた声は早めに捨てられ、queue が常に薄く保たれ、音声が実時間に張り付く。捨てた分は「読まれない」が、会場の主目的は“今の盛り上がり”なので最新優先が正しい(既存方針 v0.1.755 と一致)。

### 2. 実ラグ計測 → 連続超過でキューを最新へフラッシュ(長時間保険・新規)
- enqueue 時刻からの実ラグ(now - enqueuedAt)を再生開始時に測る。
- ラグが上限(例 2000ms)を【連続N回】超えたら、キュー先頭側の古い項目を一括破棄して最新だけ残す(リセット)。
- → VOICEVOX 内部飽和・タブスロットリングで“じわっと遅くなる”ケースを定期リセット。鮮度ゲートの受動ドロップに加えた能動リセット。

### 3. 軽い同期(全面でなく「もう出ている吹き出しに声を寄せる」)
- 吹き出しは即時のまま(変更しない=即時性維持)。
- v0.1.771 の保持はそのまま。**追加で**: 声が来た時に既存吹き出しを軽く強調(onAudioStart で吹き出しに pulse クラス)。声と吹き出しが「結びついている」ことを視覚で示し、多少の残差を“同時”と感じさせる(人間は視聴覚が結びついていれば同時と認識=nvidiaの根拠を即時性を殺さない形で採用)。
- 全面 (A)(onAudioStart まで吹き出しを遅延)は不採用=即時性を失うため。

### 4. 長時間スロットリング対策
- タブが裏に回ると setTimeout がスロットリングされ合成/ドレインが遅延。可視時(visibilitychange)に復帰したらキューを最新へフラッシュ(2と同経路)。
- 既存の先読み深さ・混雑速度upは維持(害なし)。

## 会議のハルシネ/不採用(裏取りで除外)
- 「だんだん溜まって無限に遅れる」(複数)→ 鮮度ゲートで有界。真因は定常ラグの可視化。
- (A)全面同期=onAudioStart まで吹き出しを遅延(nvidia/gemini/deepseek)→ 即時性を殺す。軽い同期(3)に留める。
- 再生 playbackRate を 1.8 まで上げる(openrouter/groq)→ 速度ブーストは既存 speedScale(VOICEVOX合成側)で実装済。HTMLAudio playbackRate 1.8 は聞き取り難で過剰=既存の合成speedScaleブースト(最大+0.8)に委ねる。
- 「捨てたコメントをタイムラインに残す」(openrouter)→ 会場は別途コメビュがある・過剰。
- VOICEVOX 複数インスタンス起動(llama)→ 制約違反(1インスタンス・拡張は別ポート起こせない)。
