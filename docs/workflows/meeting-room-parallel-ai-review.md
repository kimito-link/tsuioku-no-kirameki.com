# 会議室プロンプト + 並列 AI レビュー（運用テンプレ）

人間が司令塔になり、**先に論点整理 → 複数 AI にレビューだけ並列依頼 → 司会が統合 → 最小差分で実装**するためのコピペ用テンプレです。  
（「複数 AI に同時にファイル修正させない」前提の **爆速レビュー会議室** 向け。）

汎用の長文ワークフローはリポジトリ外の `AI汎用ルール/` も参照してください（`.cursor/rules/from-ai-generic-rules.mdc` の表参照）。

---

## 1. 推奨フロー（5 ステップ）

1. **会議室**（下記ブロック）で論点・案・リスク・次の一手をテキスト化する。  
2. **並列レビュー**：同一コンテキストを各 AI に渡し、**レビュー結果だけ**返させる（コード編集はさせない）。  
3. **司会**（Cursor / Claude Code のメイン）が矛盾を解消し、**採用 1 案 + 捨てた理由**を短く書く。  
4. **実装チャット**は「採用案 + 触ってよいパス」だけ指示し、**最小差分**で進める。  
5. 契約まわり（`chrome.storage` / `NLS_*` / `frameId` 等）を触ったら **ルール記載の単体 or E2E** を回す。

---

## 2. 会議室プロンプト（そのままコピペ）

次の `<<<...>>>` を埋めて、**1 チャットの最初のメッセージ**として送る。

```text
あなたはこのスレッドの「司会」です。複数の視点を順に出し、最後に統合してください。
コードの自動編集は不要です（設計・論点整理のみ）。

## 背景・制約
<<<プロジェクト名、技術スタック、触ってはいけない領域（例: manifest キー契約）>>>

## 目的
<<<何を達成したいか（ユーザー価値）>>>

## 現状・問題
<<<再現手順、ログ、既知の事実>>>

## 司会の依頼（順番に出力）
以下の 4 ブロックを、見出し付きで必ず出力してください。

### A. 実装案 AI（Codex 想定）
- 実装方針を 2〜3 案に分け、それぞれ長所・短所・工数感（S/M/L）
- 推奨案を 1 つに絞り、理由を 5 行以内

### B. レビュー AI（抜け漏れ）
- 仕様の曖昧さ、エッジケース、テストで押さえるべき点を列挙

### C. 設計・仕様整理 AI（Claude 想定）
- 用語の定義、データの正本（どの値を「正」と呼ぶか）、境界（popup / content / background）

### D. 批判 AI（やらない方がいいこと）
- 失敗パターン、過剰設計、巻き戻しコストが高い選択
- 「今やらない」ことの提案

## 司会の統合（必須）
- 採用する方針を 1 つ（箇条書き 5 行以内）
- 捨てた案と理由（各行 1 案）
- 次に人間が「実装チャット」に貼るべき指示文を 1 ブロック（コピペ用）

以上です。
```

## 3. 並列レビュー用：各 AI への依頼（コピペ）

会議室の出力と、**同じ差分・同じファイル抜粋**を全員に渡す。  
（`ai-cli-mcp` 等でファンアウトする場合も、中身はこの形に揃えると比較しやすい。）

### 3.1 Codex / 実装寄り（コードは書かせない版）

```text
次のコンテキストだけを前提に、レビューしてください。ファイルの直接編集は不要です。

【目的】<<<1 行>>>
【会議室の結論サマリ】<<<貼り付け>>>
【関連コード・差分】<<<貼り付け>>>

出力してほしいもの:
1. 実装上のリスク（優先度つき 最大 5）
2. 推奨する実装順序（ステップ列挙）
3. 追加で見るべきファイル・関数名の候補
```

### 3.2 Gemini / 別視点（抜け漏れ）

```text
次の内容を、初見のレビュアとして読み、見落としを指摘してください。編集は不要です。

【会議室の結論】<<<貼り付け>>>
【コード抜粋】<<<貼り付け>>>

出力:
- 前提がズレている箇所があれば指摘
- ユーザー体験・エラー表示・パフォーマンスの観点で気になる点
- 確認したい質問を最大 5 個
```

### 3.3 Claude / 仕様・設計

```text
次の内容から「仕様として固定すべきこと」を整理してください。コード編集は不要です。

【会議室の結論】<<<貼り付け>>>
【既存の制約・ルール】<<<AGENTS やチーム規約の該当箇所を貼る>>>

出力:
- 用語集（用語 → 意味）
- データの正本（どの層が authoritative か）
- popup / content / storage の責務分界
```

### 3.4 批判 AI（やらない理由）

```text
次の採用案について、「やってはいけないこと」「後から痛いこと」を徹底的に列挙してください。編集は不要です。

【採用案】<<<貼り付け>>>

出力:
- なぜ失敗しうるか（最大 5）
- 代替の小さな一手（MVP）があれば提示
- ロールバックが難しい変更があれば警告
```

## 4. 司会（統合）用プロンプト

並列レビュー結果が揃ったら、**メインの Cursor / Claude Code** に渡す。

```text
以下は同一論点に対する複数 AI のレビュー結果です。司会として統合してください。

【会議室の結論】<<<貼り付け>>>
【Codex レビュー】<<<貼り付け>>>
【Gemini レビュー】<<<貼り付け>>>
【仕様整理】<<<貼り付け>>>
【批判】<<<貼り付け>>>

やってほしいこと:
1. 矛盾点の整理と、採用する解釈（短く）
2. 最終的な「実装タスク一覧」（チェックリスト、最大 10 項）
3. 実装チャットに渡す一段の指示文（触るファイルの上限を明示）
コード変更はこのメッセージでは不要です。
```

## 6. `ai-cli-mcp` を使うときのコツ

- 各ワーカーに渡す **入力を同一構造**にする（差分・結論・制約）。  
- ワーカーからは **diff ではなく箇条書き**で返させ、**司会が 1 つの実装指示**にマージする。  
- このリポジトリでは **`src/` が正本、`npm run build` で `extension/dist/`**（`dist` 手編集禁止）を会議室の「制約」に毎回含めると安全です。

## 7. 更新方針

運用で詰まったら、**このファイルに「うまくいった依頼の実例」だけ短く追記**する程度に留める（長文化は避ける）。

### 実例（2026-05-15）

論点: watch ポップアップの公式数値「—」、診断の `rank_tab_not_found` / 北極星 `iframe_unrendered`。  
会議の結論: (1) スナップショットの `liveId` 欠けと採用ゲートをコードで是正、(2) ギフトサイドバー内のランキングタブ検出は **インライン複製をやめ `findGiftSidebarRankTabElement` に統一**してテキスト長・aria のズレを解消。  
並列レビューは別モデル無しでも、上記の役割ブロックをこのチャット内で順に出してから最小差分に落とした。
