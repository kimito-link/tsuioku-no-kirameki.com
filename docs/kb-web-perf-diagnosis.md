# KB: 「重い/固まる/黒くなる」の測り方（世界の標準手順）

> 正本。**推測でコードを読み始める前にこれを読む**。
> 初出: 2026-08-18（サイドパネル黒画面+「診断が重い」。3回誤診してから標準手順に切り替えて真因到達）
> 対象: Chrome拡張・Webアプリ全般（このリポ固有ではない＝他リポへ横展開可）

---

## 0. 掟

**症状を聞いたら、自分のコードを読む前に「世界はこの症状をどう測るか」を先に調べる。**

理由: コードを読んでの推測は当たっているように見えて外れる。2026-08-18 は
**3回続けて外した**（①CSSの max-width で頭打ち ②デバウンス無しの resize ③リサイズで壊れる）。
標準手順で測ったら**数十分で真因が数字になった**。

## 1. 症状別・最初に使う道具

| 症状 | 使う道具 | 何が分かるか |
|---|---|---|
| 時間とともに重くなる | **Performance Monitor**（DOMノード数/リスナー数/JS Heap の時間軸） | 増え続ける型か、頭打ちする型か |
| メモリが増える | **ヒープスナップショット比較**（2点間の Delta） | 本当にリークか、GCが効いているか |
| 一瞬固まる | **Performance パネルの longtask** | どの関数が何ms止めたか |
| 画面が黒い/白い | **画面録画のフレーム解析** | settled state では絶対に見えない |
| 描画が遅い | **要素数**（`document.querySelectorAll('*').length`） | 作りすぎか |

★このリポは MCP から **CDP `Performance.getMetrics`** を直接叩ける（下記§3）。

## 2. ★数字の読み方（ここを間違えると誤診する）

### 2-1. 「増えた」だけでは【リークと言えない】

```
t=0s   Heap  4.3MB   DOM  7,108
t=27s  Heap 126.8MB  DOM 13,682
t=57s  Heap 112.7MB  DOM 13,682   ← Heap が【減っている】＝GCが効いている
```

**判定**: 27秒で増えて以後**横ばい**、Heap は**減る** ＝ **リークではない**。
これは「最初に一気に作って居座る」型。

★**リーク型との見分け方**: リークなら t が進むほど**単調に増え続ける**。
**最低3点**（開始・負荷後・放置後）取らないと区別できない。2点では必ず誤診する。

### 2-2. 業界の相場を持っておく（これが無いと「多い」が判断できない）

> ★**2026-08-31 更新**: 下の「DOM総数1,500以下」は**古い基準**だった。
> Lighthouse の `dom-size` 監査は **13.0(2025-10)で廃止**され、`dom-size-insight` に置換された。
> - 新基準は**静的な要素数を見ない**:
>   「recalc が **300要素超** / layout が **100 objects超**、**かつ 40ms 超**」のときだけ失格
>   （<https://developer.chrome.com/docs/performance/insights/dom-size>）
> - 「800警告 / 1400エラー」は**スコア曲線のパラメータ**であって閾値ではなく、当時から**非スコア**
> - ★**このリポでの実測(2026-08-31・Chrome で popup.html を計測)**:
>   タイル0枚/1,053要素 → **0.4ms** ／ 600枚/4,053要素 → 14.6ms ／
>   **1,200枚/7,053要素 → 15.6ms**（＝新基準40msの**半分以下**）
> - ⟹ ★**要素数だけで「重い」と判断しない。** 実際に recalc/layout が何ms かを測る。
>   （★この製品には recalc を測る計器がまだ無い。作るまでは判定しない）

| 指標 | 目安 | 出典の考え方 |
|---|---|---|
| **DOM総数** | ★**判定に使わない（参考値）** | 旧: Lighthouse 1,500。★廃止済み。上の注記参照 |
| **実際に重いか** | **単一の recalc/layout が 40ms 超** | ★新 `dom-size-insight` の基準。これが本命 |
| ★この製品で実際に凍った水準 | **3,984個で29.3秒** | 自リポの実測（changelog v0.1.1470 相当） |
| 1親要素の子 | 60以下 | 旧 Lighthouse |
| DOM深さ | 32以下 | 旧 Lighthouse |

★チャットUI（Slack/Twitch/YouTube/Discord）は**全て仮想化**を採用し、
50,000件のデータでも DOM は数十ノードに保つ。

### 2-3. 「見た目を縮める」は【DOM数を1つも減らさない】

`display:none` / サイズ縮小 / `visibility:hidden` は**要素数に効かない**。
密度の問題と要素数の問題は**別**。混同すると「LODを入れたのに軽くならない」になる。

## 3. このリポでの実行手順（CDP経由・操作ゼロ）

```js
// mcp__chrome-devtools__evaluate_script で拡張ページ側に対して
() => ({ nodes: document.querySelectorAll('*').length })
```

時間軸で取るなら **同じ測定を t=0 / 負荷後 / 放置後 の3点**で繰り返す。
★**1点だけ取って「多い/少ない」を語らない**。

Node 側で要素数の増減を見積もるだけなら happy-dom で足りる
（実ブラウザを起こさずに「適用前/適用後」を比較できる。2026-08-18 はこれで 77.1%減を確認した）。

## 4. 直し方の選択（DOMが多すぎるとき）

| 方式 | DOMが減るか | 向き/不向き |
|---|---|---|
| **世界標準の仮想化**（画面外をDOMから削除） | ◎ 劇的に減る | ★「一度出たものを消さない」価値がある製品には**合わない**。0件の瞬間を作りうる |
| **中身LOD（枠は残す・中身だけ空に）** | ○ 大幅に減る | 「消さない」を守れる。★このリポの採用形（v0.1.1426・**77.1%減**） |
| `content-visibility:auto` | × 減らない | ★このリポで**2回撤去済み**（白い隙間／クリック不能） |
| `loading="lazy"` | × 減らない | ★3D変形下で画像が出ない事故あり（会場で撤回済み） |
| CSSで隠す | × 減らない | §2-3 |

### ★「枠は残す。中身だけ空にする」の要点（再利用可能な型）

1. **枠（親要素）は全件作る** → 件数を数えるガード（幕の解除条件など）が無傷
2. **子要素を最初から作らない**（「作ってから消す」ではない。`img.src` は**DOM未接続でもフェッチが始まる**）
3. **一方通行**（空→中身 のみ。中身→空 に戻さない）→ 画像の破棄/再生成 churn を作らない
4. 可視判定は **IntersectionObserver**。root は実際のスクロール容器に合わせる
5. ★**寸法を先に確定**する。枠と中身で高さが違うとスクロール位置が飛ぶ
6. ★**枠に地色を塗る**。透明のままだと「中身は在るのに地が無い」＝黒く見える

## 4.5. 測ったあとの直し方カタログ（横展開・実績つき）

★出典: `dns-osint-pro-ver2.0/docs/POPUP-PERF-2026-06-05.md`（**同じMV3・ビルド無しのChrome拡張**。
実location付きで真因A〜Iを並べ、Phase1/3/5 が実際に出荷済み）。
**測り方はこの文書（§1〜§3）／直し方はあちら**、と役割が分かれる。

| 症状 | 直し方 | 効き |
|---|---|---|
| 初回描画が固まる | **非表示のリストまで初回に作っていないか**。`display:none` の分を遅延生成（`data-built="0"` → タブclickで1回だけ作る） | 大（ノード数が半減しうる） |
| 同上 | **同じものを2回描いていないか**（構築直後に再ソートで作り直す等）。1回にする | 大・削除だけなので低リスク |
| 連続 append でカクつく | `appendChild` を1件ずつやめ、**DocumentFragment に貯めて1回 flush**。親に `contain: layout style` | 中〜大 |
| アニメ中ずっと重い | **rAF で毎フレーム走らせていないか**。実際の変化が0.3〜3秒周期なら interval か時間差分で間引く | 大 |
| 同上 | **`prefers-reduced-motion` がJSで無視されていないか**（CSSだけ対応は片手落ち）。reduce なら**最終状態を即表示**してループを起動しない | 大（a11yも同時に直る） |
| 停止処理が重い | `querySelectorAll('*')` で全子要素を止める → **ルートに1クラス付けてCSSで止める** | 中 |
| スクロールがもたつく | `box-shadow` の infinite アニメは**合成層に乗らずペイントを誘発**する。`transform`/`opacity` に置換し回数を有限に | 中 |
| 行ごとの再計算 | 行を作るたびに配列 `.some()` 等で判定していないか。**判定済みの値を持ち回る**（判定そのものは変えない） | 中 |

### ★`content-visibility: auto` は「条件つきで有効」（このリポでは2回撤去した）

- **あちらで効いた条件**: **高さの揃った行**（40px）が `max-height` + `overflow-y:auto` の
  **スクロール枠の中**に縦1列に並ぶ。`contain-intrinsic-size` で寸法を先に教えている。
- **このリポで失敗した条件**: 応援レーンは **flex-wrap で折り返す・幅も高さも可変のタイル**。
  → **白い隙間**／**クリックが効かない**（ヒットテストから外れる）で**2回撤去**。
- ★**「他所で効いた」は「ここで効く」ではない**。**寸法が固定で縦1列**なら候補、
  **可変サイズで折り返す**なら候補にしない。

## 5. ★やってはいけない

- **1点しか測っていないのに「増え続けている」と言う**（3点取る）
- **Heapが増えた＝リーク、と決める**（減っていればGCは効いている）
- **効かなかった修正を残す**（撤回する。足し続けると版だけ増えて症状は消えない）
- **測る前にコードを読んで犯人を決める**（3回外した実績）
