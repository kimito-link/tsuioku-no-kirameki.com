# 定型文マネージャーのClibor並み拡張 — 会議ハーネス素材の統合(司令塔による裏取り済み)

## 会議で出た、司令塔が却下した危険な提案(採用しないこと)

**groq/gpt-oss-20bが「列ソートはUI上のソートアイコンだけ非表示にして、実際には列ソートを使う(実データの並び順は右クリックでのみ書き換える)」という妥協案を出した。これは却下する。**

理由: 既存の設計書(`SNIPPET-MANAGER-DESIGN.md`のG-1節)は「`NoSort NoSortHdr`は必須オプションであり省略不可。実装者への最重要申し送り」と明記している。ソート機能そのものを有効にしたまま「アイコンだけ隠す」というのは、ユーザーが列ヘッダをクリックすればソートは実際に発火してしまう(アイコン表示とソート機能自体は別物)可能性が高く、地雷マップの趣旨(行番号↔ListView表示順↔ini行番号の3者対応が壊れると、別の定型文を誤って上書き・削除する)を回避できていない。**列ソートは機能自体を無効化(`NoSort NoSortHdr`)したまま、UIの並び替えは行番号ベースの明示的な操作(右クリックの「↑へ移動」「↓へ移動」)のみで実現すること**。

## 会議で出た、構造的に妥当な論点(採用可)

1. **番号キー参照とランチャー側のホットキーの役割分離**は、複数メンバー(groq/gpt-oss-120b, groq/gpt-oss-20b)が指摘しており、AutoHotkeyのホットキー解決順序を踏まえると妥当な懸念。「管理画面での番号キーは実行時のショートカットではなく、管理画面がフォーカスを持つ間だけ有効な選択キー」という役割分離案(`HotIf WinActive(...)`でスコープを絞る)は、既存のランチャー側の`HotIf`パターン(数字キー1-9,0がランチャーアクティブ時のみ有効)と同じ設計思想で一貫性がある
2. **右クリック並び替え(↑/↓)は、行番号ベースのini書き換えと組み合わせた専用関数(`SwapIniLines`的なもの)で実現できる**という点は、複数メンバーが同意しており、既存の`SnipMgrWriteLine`の設計思想(行番号を検証してから書き換え、外部編集とのズレはfail-closedで検出)と矛盾しない
3. **グループ階層は`snippets.ini`の1行=1定型文という不変条件と両立しない**という指摘があり、「ラベルに`group/label`形式を埋め込む」という代替案が複数メンバーから出ている。これは既にランチャー側で使われている命名慣習(「グループ1/ラベル」)と一致しており、真の階層構造(別データ構造)を新設するより既存パターンの踏襲として妥当
4. **独立編集ダイアログの価値**について、会議は「マクロ/変換機能」より「プレビュー・テンプレート変数補完」に特化させる方が本質的、という意見(groq/qwen3.6-27b)があった。これは「Cliborの模倣で終わらせない」という問いに対する具体的な回答として検討に値する
5. **検索機能の欠如**を複数メンバーが指摘している。これは元の設計書(MVPに入れないものとして明示的に除外されていた)を再考する余地がある論点

## Fableへの申し送り事項

- **`NoSort NoSortHdr`は機能として絶対に外さないこと**。「アイコンだけ隠す」という妥協案は却下済み。並び替えは行番号ベースの明示的操作(右クリックの上下移動)のみで実現すること
- 番号キー参照を導入するなら、既存のランチャー側`HotIf`パターンとの役割分離を明確に設計すること(実行時選択=ランチャー、管理時操作=マネージャーという分離)
- グループ階層は`label`文字列への埋め込み(`group/label`形式)で実現し、`snippets.ini`の1行=1定型文という不変条件を壊さないこと
- インライン編集・全文書き直し・削除確認MsgBox・`ListView.New()`は既存設計書で却下済みなので、これらを蒸し返さないこと
