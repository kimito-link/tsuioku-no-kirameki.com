# 「根治した」と言ってよい条件 — 正本

- 制定: 2026-08-04（会議 `council/why-fixes-dont-stick-*` の結論）
- 対象: このリポジトリで作業する全AI・全開発者
- 位置づけ: **AGENTS.md と同格の規律。テストやゲートより上位。**

---

## なぜこの規則が要るのか（動かぬ事実）

git履歴の実測（2026-08-04時点）:

```
「根治」「真因」を名乗ったコミット   全期間 203回 / 直近90日で 164回
同じ症状での修正回数（直近180日）:
  サムネ    41回
  読み上げ  37回
  固まる    15回
  重い       8回
  ちらつき  11回（ちらつき6/ちかちか2/点滅3）
```

**90日で164回「根治」を宣言している。本当に根治していれば164回も要らない。**

### 決定的な実例（2026-08-04・1日のうちに起きた）

1. 読み上げの取りこぼしを実測（39%）→ 床2→4に変更 → **「根治」とコミット・版を出した**
2. 反映後の実測で**悪化**していた（合成待ち2.5倍・合成失敗52件が新規発生）
3. 真因は自己強化ループと判明 → 床4→5 → **また「根治」とコミット・版を出した**
4. **床5の効果は一度も測れていなかった**（速報が24時間前の化石値を出しており、
   会場モードが開き直されていなかった。それに気づくまで2往復）

同時に、ユーザーが「ちかちかする」と報告していた症状の実体は
**1コメントあたり77回の描き直し**だったが、**どの計器も異常と報告していなかった**
（完全性スコアは「描画・UI健全性 🟢100%」を出していた）。

## 規則

### 第1条 — 「根治」は実機で症状が消えたときにだけ名乗れる

テストが緑・`verify:cc` 全通過は**根治の証拠にならない**。
それらは「自分が書いた期待値を自分で満たした」だけである。

**根治を名乗ってよいのは、次の3つが揃ったときだけ:**

1. **反映の確認** — 実機で動いている版数が、期待する版数と一致している
2. **症状の消失** — 修正前に異常だった計器値が、正常域に入った
3. **値の新鮮さ** — その値が「今の値」である（化石値でない）

1つでも欠けたら、コミットメッセージに「根治」と書いてはならない。

### 第2条 — 未確認のときは、そう書く

確認できていない段階で版を出すこと自体は禁じない（実機がユーザーの手元にしかない
以上、出さないと確認できない）。**ただし言い方を変える。**

| 状況 | 使ってよい言葉 |
|---|---|
| 実機で症状が消えたことを確認済み | 「根治」「直った」 |
| 実装したが未確認 | **「効くはず（未確認）」** |
| 原因の見立てだけ | **「仮説」** |
| 計器を足しただけ | **「計測できるようにした」** |

ユーザーへの報告も同じ語を使う。「根治しました」と言って直っていなければ、
次に本当に直したときも信じてもらえない。**言葉の信用は積み立て。**

### 第3条 — 症状が複数同時なら、個別に直す前に共通根を疑う

「読み上げが飛ぶ」「点滅する」「サムネが白い」「診断が重い」が同時に出ているとき、
4件を順に直すのは**ほぼ確実に間違い**。同じ根から出ている可能性を先に潰す。

判断基準:
- 同じ画面・同じタイミングで出るなら、共通根を疑う
- 別々の版で別々に出ていたなら、個別対処でよい

### 第4条 — 計器は「値」ではなく「判定」を出す

数字を印字するだけの計器は、人もAIも読み飛ばす（実例: 描画2517回は
レポートに印字されていたが誰も気づかなかった）。

**新しく計器を足すときは、必ず正常域と判定を付ける。**
`src/lib/anomalyVerdict.js` の `judge*` 系を使うか、同じ形で書く。

- 正常域は**実測値から決める**（架空の閾値を置かない）
- **「判定不能」を必ず持つ**（母数が小さいときに白黒つけると誤報になり、
  誤報は計器全体の信用を落として読み飛ばしを生む）

### 第5条 — 実測値をテストに焼く

「実際に見落とした値」をテストに固定する。架空の値でテストしても同じ見落としは防げない。

例（`anomalyVerdict.test.js`）:
```js
// 2026-08-04 実測: コメント26件で描画2013回。当時どの計器も異常と言わなかった。
it('【実測・見落とした値】コメント26件で描画2013回 → badと名指しする', () => {
  expect(judgePaintPerComment(2013, 26).level).toBe('bad');
});
```

### 第6条 — テストは書いた直後に壊して赤を見る

緑を確認しただけのテストは、実効性がゼロのことがある（v0.1.1201で実際にあった）。
**わざと壊して赤くなることを確認**してからコミットする。

## ユーザーとのやりとりの規律

### 往復を減らす

ユーザーは開発の当事者ではなく**利用者**である。毎回テスターをさせない。

- 1回の依頼で**複数の情報をまとめて**取れるようにする
- 「これを試してください」を複数回に分けない
- 取れなかった場合の代替手段も同時に示す

### 「触っていない」は言い訳にならない

変更範囲が小さいことを主張しても、ユーザーから見れば
「更新したら壊れた」である。**変更範囲の説明より、切り戻しの提示を先にする。**

## この規則自体の見直し

この規則は2026-08-04の失敗から作られた。
**同じ失敗が再発したら、この規則が不十分だったということ。**
そのときは規則を責めて直す。人（AI）の注意力に頼る規則は失敗する。
