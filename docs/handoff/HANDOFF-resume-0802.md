## ★調査で判明した最重要事実（2026-08-02・Explore 2体）

### 1. 「一度出た人」を覚える仕組みが**どこにも無い**

毎 paint がゼロから候補を作り直す。横断的な記憶は4つだけで、
**どれも「誰がいたか」を持たない**:

| 持っているもの | 実体 |
|---|---|
| `_laneTierLastKey`（WeakMap） | 直前の描画内容の文字列（diff-skip用） |
| `_storyUserLaneLastTiledLid` | 最後に描いた配信ID（文字列1個） |
| `storyUserLaneLastRenderSig` | 署名1個 |
| DOM の `childElementCount` | **個数だけ** |

→ **同じ人数のまま中身が入れ替わると、既存のどのガードも検知できない。**

★前例あり: `src/lib/monotonicCommentCount.js` が「記録件数を後退させない」ために
既に使われている（`popup-entry.js:1167`, `3299`）。同じ考えをレーンへ適用するのが Phase 2。

### 2. 消える経路のランキング

| # | 場所 | 何が起きるか |
|---|---|---|
| 1 | **蓄積器が無い** | 入れ替わりが検知できない |
| 2 | `renderStoryUserLaneDom.js:174` | 第一関門 `entriesProvisional !== true` で即素通り。実測 `shrinkKeepCount: 0` |
| 3 | `storyUserLaneBuckets.js:16-20` | **上限48の配分が段ごとに先取り**。tier3が増えるとtier2/1の枠が丸ごと減る＝供給が同じでも人が押し出される。**最有力** |
| 4 | `popup-entry.js:6768` | `broadcasterUid` が空になると**数値IDの人が全員除外** |
| 5 | `renderStoryUserLaneDom.js:302` | 段ごとに `innerHTML=''`。ガードは5段の合計しか見ない |
| 6 | `popup-entry.js:7074` / `7152` / `venueBar.js:4942` | **ガードが1つも無い描画経路が3つ** |
| 7 | `renderStoryUserLaneDom.js:186` | 発動しても**6割まで減るのは許容** |
| 8 | `laneMirror.js:167-170` | 512KB超で上限を黙って半分に |

### 3. 診断ページが重い理由＝自分のせいではない

**`backfill 7,967ms` は、たった1個・約200バイトの読み取り。** 計算でなく**順番待ち**。

- 診断ページの読み取りは**すべて O(1) or O(配信数)**。コメント件数に比例するものは**皆無**
- 真因は**コメント記録側の書き込み**（最大2000行/2.5秒・backfill中は毎秒）と
  同じ単一 LevelDB を共有していること
- 構造的な穴は2つだけ:
  - 中核5ステップのうち3つ（fastDiagLite/popupDiag/backfill）が**個別読み取り**（バッチ化可能）
  - 混雑中の読み取りサイクル内で **`set`（書き込み）を1回**している（`status-entry.js:1244`）
- 正本: `docs/handoff/status-diag-608s-freeze-DESIGN.md`（608秒の実測あり）
