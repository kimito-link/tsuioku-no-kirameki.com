# 実測 2026-08-16 — 「診断が重い/応答しません」の真因

> ★**推測ではなく chrome-devtools MCP で実測した値**。
> 手順は `/nicolive-selfcheck`。ユーザーに速報を貼らせずに測った。
> 環境: 出荷ビルド v0.1.1411 / storage 26.6MB(実機20〜37MBと同規模) / コメント13万行

---

## 0. 結論（先に）

**真因は「読む量」ではなく【書き込みとの競合】。**

同じ小さな read が、書き込み負荷で **1ms → 217ms（最大65倍）** に膨れる。
`chrome.storage.local` は単一 LevelDB なので、
**記録エンジン/backfill の大きな staged write が走っている間、
status の read が待たされる**。

★status は **backfill 中でもポーリングを緩めない**（2秒固定）。
　混雑している最中に2秒ごとに読みに行く＝自分で競合を増やしている。

---

## 1. 実測値

### ① 読む量そのものは問題ではなかった
| 操作 | 実測 | 備考 |
|---|---|---|
| `getBytesInUse(null)` | 1ms | |
| `getKeys()` | 24ms | |
| `get(サマリ5キー)` | 1ms | |
| `get(コメント全チャンク66キー)` | 1,449ms | 🔴 重い |
| concat+sort(13万行) | 22ms | JS処理は無罪 |

★ただし **status は全チャンクを読んでいない**（§2）。上の1,449msは
　「もし読んだら」の値であって、現在の実装のコストではない。

### ② status が実際に読むキーは最初から軽い
`loadAllSummaries` は per-live で4キーだけ読む
（`nls_panel_summary_` / `nls_watch_snapshot_` / `nls_perf_diag_` / `nls_live_ended_`）。

| 条件 | 実測 |
|---|---|
| 5配信ぶん20キーを read（存在する状態） | **1ms** |

★**ここは既に正しく実装されている**。私の最初の仮説
「コメント本体を読んでいるから重い」は**誤り**だった。

### ③ ★真因: 書き込み競合で同じ read が65倍になる
| 条件 | 同じ read の所要 |
|---|---|
| 平常(書き込みなし) | **1ms** |
| 記録中1配信(2並列write) | 54ms |
| 記録中2配信(4並列write) | 98ms |
| **backfill中2配信(8並列write)** | **217ms** |

★ユーザー実機は「⏳取り込み中 5%(記録90/公式1,832)」＝**backfill 稼働中**。
　速報の `summaries 1278ms` / `popupDiag 1471ms` はこの regime の値。

### ④ イベントループ停止
| 条件 | 最大タイマー遅延 |
|---|---|
| 大量書き込み中 | 137ms |
| 13万行 read+merge 中 | **713ms**（1000ms予定→1713ms発火） |

## 2. だから「サマリだけ読む」修正は**不要**だった

着手前に確認して助かった。`loadAllSummaries` は既にサマリキーだけを読む。
★**車輪の再発明を1つ回避した**（ユーザーの「これは車輪の再発明でないか」が正しかった）。

★さらに `nls_csummary_` には**罠**がある: IDBモードでは更新されず、
　SW が書く `cdbSummary` が正本（popup-entry.js:16214 のコメント）。
　もし私が思いつきで「csummary を読む」修正をしていたら、
　**IDBモードの配信で件数が0/古い値になる**退化を作っていた。

---

## 3. 次にやるべきこと（実測に基づく順）

### A. ★backfill 中はポーリングを止める/大幅に緩める（最優先・効果が最大）
現状 status は「前回が遅かったら次を間引く」＝**事後**の backoff しかない。
`backfillLiveMetric.running === 1` は既に読めている（status-entry.js:1699）ので、
**取り込み中は 2秒→10秒等へ明示的に落とす**。
＝ 競合の原因を減らす。読み方を変えるより効く。

### B. 可視でないときは読まない
`document.hidden` は既に見ているが、
**backfill 中の可視タブ**が問題なので A の方が効く。

### C. 【調査中】storage.onChanged による差分更新
2秒ポーリングそのものをやめる案。ディープリサーチの結果待ち。
