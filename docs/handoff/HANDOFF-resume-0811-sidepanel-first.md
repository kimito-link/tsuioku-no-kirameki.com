## 何をやろうとしているか（会議で決めた方針）

**サイドパネル(B)を主役にし、ページ埋め込みパネル(A)は非推奨にする。**

### 実測された問題

ユーザーのバンドル（v0.1.1320・実機）:

```json
"inlinePanel": {
  "viewportInnerWidth": 319,        // ニコ生タブの幅
  "besideMinWidthPx": 1100,         // 横付きに必要な幅
  "placementMode": "beside",         // 「横付き」を選んでいる
  "placementEffective": "below",     // 実効は「下」に降格
  "viewportWideEnoughForBeside": false,
  "host": { "computedDisplay": "none", "rectW": 0, "rectH": 0 }  // ★無言で消えている
}
```

★**サイドパネル自身は 531〜664px**（サイドパネル自己診断より）。
＝Chrome の既定が悪いのではなく、**サイドパネルが広すぎてニコ生が319pxに潰れている**。
幅はユーザーがドラッグで変えられる＝**逃げ道はある**。

### 会議の結論（scripts/meeting.mjs・design カテゴリ・3/4成功）

| メンバー | 結論 |
|---|---|
| groq/llama-3.3-70b（速い視点） | (b) サイドパネル主役・埋め込み廃止 |
| groq/qwen3.6-27b（発散） | (b)主役。他にPiP/フローティング案も提示 |
| **groq/gpt-oss-120b（批判）** | **(b)に反対**。「サイドパネルだけだと動画が実質見えなくなる」 |
| nvidia/nemotron（統括） | タイムアウト脱落 |

★**批判役の懸念は妥当だが、原因の特定が誤り**（司令塔判断）。
批判役は「Chromeの既定でタブが300px以下になる」と書いたが、実測は上記のとおり
**サイドパネルが広すぎるだけ**。だから「廃止」ではなく「幅の手当て」で応える。

### 採用理由（(b)にする根拠）

1. **埋め込みはニコ生のDOMに間借り**＝相手の改修で壊れ続けている（実績多数）
2. **記録は表示と独立**＝パネルを出さなくても記録は続くので機能は失われない
3. **3通りを高品質に保つ余力がない**（サイドパネル/埋め込み/別窓）

## 実装（次のセッションでやること）

### ★最優先: 無言で消えるのをやめる（Q2への回答）

いま埋め込みは `display:none` で**理由も出さずに消える**。診断は理由を持っているのに
画面に出していない（`placementInterpretationHintJa` に文言まである）。

**幅が足りないときは、消さずに案内を出す。** 文言案:

```
📐 このタブが狭いため（319px）、ここには表示できません。
   サイドパネルで応援状況を見られます  → [サイドパネルを開く]
   （サイドパネルの左端をドラッグすると、動画を広げられます）
```

★最後の1行が**批判役への回答**＝動画が潰れたときの逃げ道をその場で教える。

### 触る場所（調査済み）

- `src/extension/content-entry.js` … 埋め込みホストの表示/非表示（`ensurePageFrameOverlay` 周辺）
- `inlinePanel` 診断の出どころ … `viewportWideEnoughForBeside` / `placementEffective` を作っている箇所
- 既存の純関数が使えるはず: `src/lib/inlinePanelShowGate.js` / `inlinePanelViewportWide.js` /
  `inlinePanelPlacementResolver.js`（**新規に作らず既存を再利用すること**）

### 順序（1回に1つずつ）

1. **案内を出す**（消さない）＝ユーザーが迷わなくなる。ここだけで体験は大きく改善する
2. 「サイドパネルを開く」ボタンを案内内に置く（`chrome.sidePanel.open` は**ユーザー操作起点が必要**）
3. 埋め込みを既定OFFにするかは**2の反応を見てから**決める（いきなり廃止しない）
