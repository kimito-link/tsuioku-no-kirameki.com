# 会場へ運ぶ演出（サイドパネル → 会場）SPEC

> 2026-08-08 / ユーザー要望「サイドパネルでだしておいて、そこから個々のみんなを会場に運ぶよー
> みたいな演出があれば確実かとおもう」／方向は **「飛んでいく」** で確定。

---

## 0. なぜこの演出が「確実」なのか（要望の再解釈）

ユーザーの言葉は演出の希望だが、**実は解決策の提案でもある**。

いま会場は「気づいたら居る／気づいたら居ない」で、
**誰がいつ入ったのかが分からない**。だから「全部載ってない」と感じても
①本当に載っていないのか ②載ったが目立たないのか が区別できない。

**運ぶ演出を入れると、入場が"イベント"になる＝目視で検証可能になる。**
つまりこれは演出であると同時に **常時稼働の計器**でもある。
（今日の教訓 [[settled-state-hides-flash-bugs]]＝落ち着いた後を見ても分からない、と同型。
　運ばれる瞬間を見せれば、載らない人がいれば「飛んでこない」で即分かる。）

★この観点は実装時に落とさないこと。演出を「飾り」として作ると、
　`prefers-reduced-motion` で全部消して終わりになり、検証価値がゼロになる。

---

## 1. 何を作るか（1行）

**サイドパネル（①POP）に出ている人のアイコンが、会場モードの自分の席へ弧を描いて飛んでいく。**

- 飛ぶのは **新規入場者だけ**（既に座っている人は飛ばさない＝毎paint飛ぶと地獄）
- 着弾したら席が `nlsb-seat-enter` で一度ふくらんで確定
- 同時多発時は **束ねて間引く**（後述の上限）

---

## 2. 既存資産を使う（新規実装を最小に）

| 使うもの | 場所 | 理由 |
|---|---|---|
| `nlsb-gift-fly` の弧アニメ | venueBar.js:909-915 | **既に「飛ぶ」表現の正本**。CSS変数 `--nlsb-gift-mx/my/dx/dy` で始点終点を渡す設計がそのまま流用できる |
| `nlsb-gift-proj` の投射体DOM | venueBar.js:896-905 | 画像を貼って飛ばす箱。中身をアイコンに差し替えるだけ |
| `resolveStoryLaneAvatarSrc` | 正本の解決器 | v1286で広告段を配線した解決器。**必ずこれを通す**（白丸事故の再発防止） |
| `prefers-reduced-motion` 分岐 | venueBar.js:916-927 | 既にある。同じ作法で足す |

**新規に書くのは「誰が新規か」を出す差分検出だけ。** アニメは既存を再利用する。

---

## 3. 「誰が新規か」の出し方（ここが唯一の新規ロジック）

会場は既に `seatByKey`(venueBar.js:3871) で席を key 管理している。

```
前回の key 集合 prevKeys
今回の key 集合 nextKeys
新規 = nextKeys − prevKeys
```

★**ただし初回は飛ばさない**。会場を開いた瞬間に150人が一斉に飛ぶと事故。
　初回(prevKeys が空)は全員そのまま着席させ、2回目以降の差分だけ飛ばす。

★**配信を切り替えたら prevKeys を捨てる**（liveId 変化でリセット）。
　これを忘れると別配信の人が「新規」に見えて全員飛ぶ。
　（[[broadcaster-uid-tracker]] が liveId 変化で全リセットしているのと同じ作法）

---

## 4. 上限と間引き（大配信で壊さないため）

実測値ベース: あなたの配信は **来場1,477人・会場参加者152人**。
バックフィル直後は一度に数十人が「新規」になり得る。

| 制御 | 値 | 理由 |
|---|---|---|
| 同時に飛ぶ最大数 | **6** | それ以上は視覚的に区別できない |
| 1秒あたり発火上限 | **8** | 超過分はキューに積んで順次 |
| キュー上限 | **24** | 溢れたら**飛ばさず直接着席**（落とさない・出さないのではない） |
| 1回の所要 | **900ms** | gift(1500ms)より速く。入場は軽く見せる |

★**溢れた人を「表示しない」のは禁止**。演出を省くだけで、席には必ず着かせる。
　（v0.1.1232「上限こそが消失の実行者」の教訓＝上限は演出にだけ掛ける）

---

## 5. どこから飛ばすか（始点）

サイドパネルと会場は**別ウィンドウ／別ドキュメント**なので、
DOM をまたいで実際に飛ばすことは**できない**。

→ **会場側の画面端から飛んでくる**ように見せる。
   サイドパネルが右にあるなら右端、左なら左端。
   `chrome.sidePanel` の位置は取れないので **既定は右端**、
   設定で左右を選べるようにする（既存の dock 設定に相乗り）。

★ここは正直に「見立て」。実座標の連続性は諦める。
　ユーザーの要望「サイドパネルから運ばれる感」は**方向が合っていれば伝わる**。

---

## 6. 音（任意・既定OFF）

既存の効果音基盤（操作音/ギフト音）に相乗りできるが、
**入場音は既定OFF**にする。152人が入場するたび鳴ると配信事故になる。
鳴らすとしても「まとめて1回」（束ね発火）に限る。

---

## 7. 受け入れ条件（実装した／していないの判定）

1. 会場を開いた**初回は誰も飛ばない**（全員そのまま着席）
2. 新しい人が1人来たら**1人だけ飛ぶ**
3. 30人同時でも**同時に飛ぶのは6人まで**、残りは順次 or 直接着席
4. **飛ばなかった人も必ず席に居る**（演出の間引き ≠ 表示の間引き）
5. `prefers-reduced-motion` で**飛ばないが着席はする**
6. 配信を切り替えたら前配信の人が飛ばない
7. アイコンは `resolveStoryLaneAvatarSrc` 経由（白丸にならない）

★7項目とも **e2e で機械判定できる**形にする。
　「動いてるっぽい」で出荷しない（今日の v1286/v1287 の反省）。

---

## 8. 実装順（別コミットに割る）

1. `venueEntryQueue.js`（純ロジック・差分と間引きだけ・DOM無し）＋ unit test
2. venueBar.js に配線（既存 gift-fly を流用）＋ wiring test
3. e2e で受け入れ条件 1〜7 を機械判定
4. 設定UI（左右／ON-OFF）＝ 最後。無くても動く

★1 を純ロジックに切るのは、**大配信の間引きを実データでテストするため**。
　DOM に埋めると 152人ケースをテストできない。
