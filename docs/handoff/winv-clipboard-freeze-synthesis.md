# Win+Vクリップボード固まり問題 — 会議ハーネス素材の統合(司令塔による裏取り済み)

## 会議で出た仮説のうち、裏取りできたもの(採用)

1. **Win+VのUIはExplorerシェルに強結合している**(Web調査で複数の独立ソースが一致。`explorer.exe`再作動が定番の応急処置として広く報告されている)
2. **裏側の実体はper-userサービス`cbdhsvc`(Clipboard User Service)**。これがクラッシュ・無応答になるとWin+Vが機能しなくなるという報告が複数ある(Web調査で確認)
3. **Chrome拡張のclipboardRead/clipboardWrite権限は、Windows標準クリップボード履歴との相性問題が既知**(Bitwarden拡張のGitHub issue #19292で実例確認)。ただしこの実例は「履歴に載らない」症状であり、「パネル自体が無反応になる」症状とは別物である可能性が高い
4. **Windows 11 24H2自体にクリップボード履歴が固まる既知バグがある**(Web調査で複数の独立ソースが一致)
5. **同時実行(Chrome拡張+AHK)による競合の可能性**という論点自体は、構造として筋が通っている(2つの独立したプロセスが同じOSリソースに触れるなら、競合の可能性はゼロではない)

## 会議で出たが、裏取りできなかったもの(却下・要注意)

**以下はgroq/gpt-oss-120b(批判役)およびそれに追従した他メンバーが主張したが、Web再調査で一切の裏付けが取れなかった、LLMの幻覚とみなすべき具体的数値・固有名詞:**

- 「`cbdhsvc`は内部的にシングルスレッドで、同一プロセスからの連続書き込みが**約30回/秒を超えると内部キューがロックされる**」— 出典なし、Microsoft公式文書・コミュニティ報告のいずれにも見当たらない
- 「Event ID **3000, 3001**」という具体的なイベントログID — 出典なし。実際にWeb検索でヒットした「Event ID 3001」は全く無関係の`Loadperf`エラーの話だった(cbdhsvcとは無関係)
- 「Chrome拡張の呼び出し間隔が**100ms以上**」「AHKの`ClipWait`が**5秒以上**」という具体的な閾値 — 出典なし、実測データもなし
- Process Monitorのエラーコード`0x800401D0` — 出典なし

**教訓**: これらの数値は複数のクラウドLLMが「もっともらしく」引用し合い、互いに強化し合う形で会議内で"確定事実"のように語られていたが、実際には根拠のない創作。司令塔が個別に裏取りしなければ、そのまま設計に混入するところだった。

## 会議から抽出できる、構造として妥当な論点(数値を除いた骨格)

1. **問いの立て方自体が不正確な可能性**: 「Chrome拡張が原因」「AHKが原因」という二択ではなく、「どちらか一方でも発生するか」「両方同時実行時のみ発生するか」を先に切り分ける必要がある、という指摘(複数メンバーが同意)は論理として妥当
2. **診断の優先順位**: 具体的な数値・IDは幻覚だったが、「A/Bテスト(拡張のみ/AHKのみ/両方OFF)→再現条件の切り分け→Windowsイベントビューアーでの`cbdhsvc`関連ログ確認→Process Monitorでのクリップボード操作タイミング記録」という**手順の順序自体**は方法論として妥当
3. **Cliborとの実装差という手がかり**: 「なぜCliborだけ問題が起きないのか」を実装方式の違いから考える、という視点(常駐の仕方、スレッドモデルの違いなど)は掘り下げる価値がある
4. **コード改修の方向性(数値は要検証、方向性は妥当)**: クリップボード操作の頻度・タイミングを制御する、同期処理を減らす、という一般的な設計原則は妥当だが、具体的な閾値は実測してから決めるべき

## Fableへの申し送り事項

- 上記の「裏取りできなかったもの」を設計の前提にしないこと。特に数値的な閾値は実測なしに採用しない
- 実測(Process Monitor、Windowsイベントビューアー)を伴わない段階では、「原因はまだ特定できていない」という前提で、**まず安全に実行できる診断計画**を設計の中心に据えるべき
- 「根本解決の実装」を急ぐより、「再現条件を絞り込むための最小限の変更(A/Bテスト手順)」を先に設計するのが筋が良い
- soushin-suggest.link側のOnClipboardChange実装は既にコード確認済み(このセッションで実施)なので、Fableはそのコード実態(ClipChanged関数、SetTimerによるデバウンス120ms、ClipOpenのリトライ100ms)を踏まえて設計してよい
