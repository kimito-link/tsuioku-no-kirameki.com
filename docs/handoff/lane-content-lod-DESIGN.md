## 0. ユーザーの症状

- サイドパネルが**真っ黒**（★**横縞**が見える＝中身は描けているが地が塗られていない）
- 「**診断が重い**」
- 更新所要 115ms → **1,722ms** / 描画完了が最悪**112秒** / **コメント取りこぼし**

---

## 1. ★真因（世界の標準手順で実測・推測ではない）

`Performance.getMetrics`（CDP）で時間軸測定。コメント1,200件:

| | t=0s | t=27s | t=57s |
|---|---|---|---|
| DOMノード総数 | 25,015 | **55,448** | 55,888 |
| 拡張内DOM | 7,108 | **13,682** | 13,682 |
| タイル | 8 | **1,108** | 1,108 |
| リスナー | 259 | 528 | 573 |
| JS Heap | 4.3MB | **126.8MB** | 112.7MB |

**確定事項**
1. **メモリリークではない** — 27秒で増えて以後横ばい。Heap は 126.8→112.7MB と**減っている**（GC が効いている）
2. **業界基準の9〜37倍** — Web業界の推奨は **DOM総数1,500以下 / 1親要素60以下**
3. 「時間とともに悪化」ではなく「**最初に一気に作って居座る**」

★**既存LODは効かない**: `popup.html:1162-1203` の `nth-child(n + 25)` は
`display:none`／サイズ縮小のみ＝**DOM要素は1つも減らない**。しかも**たぬ姉段だけ**。

---

## 2. 採用する方式 —「枠は残す。中身だけ空にする」

会議の批判役が決め手:
> 「**DOMから完全に削除せず、常に可視要素を保持**し、位置情報をキーにしない形で同期させる」
> 「『データ上は残っているが視覚的に消えている』は**C1の価値を根本的に損なう**」

＝**世界の標準的な仮想化（DOMごと消す）は、この製品には合わない。**

### 効果の見積り（司令塔が計算）

| | 要素数 |
|---|---|
| 現在 | **5,540**（1,108枚 × 5要素） |
| 適用後 | **1,228**（可視30枚×5 + 枠のみ1,078枚×1） |
| **削減率** | **78%** ／ 業界基準1,500以下 ✅ **達成** |

★**枠を1,108個残したまま基準を満たす。誰も消えない。**

### 具体形
1タイル＝5要素（cell / img / metaEl / idRow / nameRow）のうち、
**cell（枠）だけ作り、子4要素を最初から作らない**。
★「作ってから外す」ではない — `img.src` への代入は**DOM未接続でもフェッチが始まる**ため、
「作って隠す」「作って外す」はどちらも churn の種になる。

★**一方通行（hollow→full のみ。full→hollow に戻さない）**
戻す運用は「img を捨てて作り直す」＝**7版かけて消した churn の再生産**。
最悪でも「全員を見に行ったら現状と同じ DOM 数」＝**現状より悪くならない**。

## 3. ★司令塔の裏取り（Fable の主張を全件検証）

| 主張 | 検証結果 |
|---|---|
| `countStoryUserLaneDomTiles` は `childElementCount` を数える＝**枠も1枚と数える** | ✅ `popup-entry.js:6889-6896` で確認。**幕の解除条件は無傷** |
| `storyLaneTierBodyKey` は items（データ）だけで鍵を作る＝**DOMを見ない** | ✅ `renderStoryUserLaneDom.js:248-261` で確認。**鍵は揺れない** |
| 会場は `loading="lazy"` で**サムネが出なくなり撤回した前科**がある | ✅ `personTileDom.js:86-90` に明記。**IOも同じ穴に落ちる** |
| 会場だけが `wrapTileEl` を渡す | ✅ `venueBar.js` に4箇所 |

### ★司令塔が事前に特定した「最大の罠」と、その解決

**罠**: 中身を空にした後 `fillLaneTier` が再実行されると、鍵が一致して
diff-skip が「何もしない」→ **空のまま戻らない**。

**Fable の答え**: **一方通行 + `_filledKeysByLane` で既fill者を記憶**
＝空にする操作は**初回生成時のみ**。後から空にすることが無いので、
この状態は**構造的に発生しない**。✅ **解けている**

1. **即時（1行）**: `LANE_CONTENT_LOD_ENABLED = false` → 挙動が完全に旧へ戻る
   （テスト6が「false = 現行とバイト一致」を保証）

3. **撤回判定を先に固定**: 合格ラインを満たさない／更新所要が改善しない／
   明滅・白抜け・クリック不能を観測 → **原因調査より先に kill スイッチを倒す**

## 8. 捨てた案

| 案 | 理由 |
|---|---|
| **世界標準の仮想化**（画面外をDOMから削除） | **C1「消す」解そのもの**。かつ 0枚の瞬間を作り得て C2（黒画面）を再生産 |
| `content-visibility: auto` | **2回撤去済み**（白い隙間／クリック不能）。3回目は無い |
| `loading="lazy"` | 会場の3D変形で**サムネが出なくなり撤回済み**。かつ**DOM数が1つも減らない** |
| CSSだけで隠す（`display:none` 拡張） | 既存LODで実証済み: **DOM要素は減らない** |
| スクロール位置の自前計算 | flex-wrap の折り返しは幅依存で脆い。`getBoundingClientRect` は強制リフロー |
| full→hollow の双方向 | img の破棄→再生成＝**7版かけて消した churn の型** |
| 全5段・全位置への適用 | 前列 pill は幅可変で寸法一致が取れず**layout shift**。効果の大半は匿名後列にある |

| 1 | **hollow と full の寸法ズレ＝スクロール位置が飛ぶ** | 出荷ビルドで `getBoundingClientRect` 実測してからCSS値を確定（±1px超は出荷しない） |
