# 読み上げ系 リファクタ基線（版0・コード変更ゼロ）

> **この文書の目的**: 読み上げ系を12〜15版かけて移設する前に、
> 「**いま鳴っている**」という事実を退行判定の基準として固定する。
> 移設後に「鳴らない」が出たとき、比較できる対象がこれ。
>
> 記録日: 2026-08-11 / 拡張バージョン: **v0.1.1331**（無改変）/ ブランチ: `feat/sidepanel-first-layout`

---

## 1. なぜ今日この基線を採るのか

2026-08-11、読み上げが「ONにならない」症状を **10時間・6版** 追い、
**真因は拡張ではなく VOICEVOX の音声合成エンジンが起動していなかった**ことだった。
エンジンを起動したところ **拡張のコードを1行も変えずに鳴った**。

★つまり **「鳴る」という基準が、この日この瞬間に実測で確定した**。
 リファクタ着手の直前にこれが揃っているのは偶然だが、逃すと基線が無いまま移設することになる。

### ★★コメビュが鳴らない（2026-08-11 夜に判明・未解決）

**エンジンは動いているのに、コメビュだけ「VOICEVOXが見つかりません」と出る。**

| 確認したこと | 結果 |
|---|---|
| エンジン `/version` `/speakers` `/audio_query` | **全部 HTTP 200**（ボタンを押した直後に測定） |
| 会場モードの読み上げ | ✅ **鳴っている**（同時刻） |
| コメビュの読み上げボタンを押し直す | 🔴 **「VOICEVOXが見つかりません」のまま** |
| `manifest.host_permissions` | ✅ `http://127.0.0.1:50021/*` あり |
| `proxyFetchFn` の経路 | ✅ 拡張ページなら直接fetchに切替（`voicevoxClient.js:52-54`）＝配線は正しい |

★**司令塔が立てて外した仮説2つ**（次の人が同じ道を辿らないため）:
1. 「表示が古いだけ（化石値）」→ **外れ**。押し直しても同じ文言が出た
2. 「`_voiceToggleBusy` が立ちっぱなしでprobeが走らない」→ **外れ**。

★**コードは正しく見えるのに失敗している**。ここから先は推測になるため、
 **計器を入れて次の1回で確定させる**方針に切り替えた（下記）。

### ★なぜ原因が特定できないか＝これ自体が設計の不在

**会場側は失敗理由を計器に残すが、コメビュ側は残さない**（今日の地図 A-4 の片肺）。

```
voicePlayer.js:355-357（会場・v0.1.1331で追加）
  this.diag.lastEnableFailReason = String(probe.reason || 'unknown');
  this.diag.enableFailTotal = ...
  this._emitDiag();
→ comeview-entry.js には grep 0ヒット（＝コメビュで失敗しても記録がどこにも残らない）
```

しかも文言は DOM にしか出ず（A-3）、`refused` と「理由不明」が**同じ表示**になる。
＝**ユーザーが何度報告しても、原因を名指しできる情報が1つも上がってこない**。

★これは「画面にしか出さない情報は報告に乗らない＝無いのと同じ」の実例。
 → **次の1版でコメビュにも失敗理由の計器を配線する**（Phase 1 の直後）。
   配線すれば、次にボタンを押した1回で `refused` / `timeout` / `http-error` /
   `not_wired` のどれかが状態速報に出て、**推測ゼロで原因が確定する**。

### ★同時に鳴らす設計は「邪魔」（ユーザー指摘・2026-08-11）

> 「コメビュと同時は邪魔じゃない？」

**その通り**。会場とコメビュが同時に読み上げたら同じコメントを2回喋る。
しかも A-5 の通り**同じstorageキーを3秒ごとに奪い合う**＝音も診断も二重になる構造。

★**この論点は前回の設計に入っていなかった**（2実装を畳む話はしたが、
 **どちらの面が読み上げを担当するかの調停**が抜けていた）。
 → Phase 3 に「読み上げ担当面の調停（同時再生の禁止）」を追加すること。
 → ★したがって**コメビュが今OFFであること自体は実害が無い**。
   直すべきは「鳴らないこと」ではなく「**理由が嘘であること**」。

★コメビュの確認手順: popup の「読み上げ付きで開く」（`?voice=1`）→ コメントが流れたら鳴るか。
★**両方が基線でなければならない理由**: A-4 の通り実装が2系統あり、
 片方だけを基線にすると、もう片方の移設で壊れたときに検知できない。

## 3. ★消してはいけない非対称（実コードに理由が文書化済み）

移設で「対称にしたくなる」が、**理由があるので温存する**もの。

### 3-1. タイムアウト 5000ms vs 1500ms 【消すな・確定】

正本: `src/lib/voicevoxClient.js:157-166`（`defaultVoicevoxAliveTimeoutMs`）

> 2026-06-14 真因(3モデル会議全員一致+実コード検証): 会場モード下端バーは
> content script で、VOICEVOX へは background SW プロキシ経由で叩く。
> **MV3 の SW はコールド起床するため「sendMessage 往復 + SW 起床 + /version 応答」が
> 1500ms を超えやすく**、isVoicevoxAlive が false→「VOICEVOX が見つかりません」で
> 読み上げが始まらなかった(**comeview は拡張ページ=直接 fetch で速いから動いていた
> =非対称の正体**)。

★**重要な符合**: 2026-06-14 も 2026-08-11 も、ユーザーに出た文言は
 **同じ「VOICEVOXが見つかりません」**だが、真因は別（前者=タイムアウト不足 / 後者=エンジン未起動）。
 → **同じ文言が別の原因で2回出ている**。これが「文言でユーザーの誤認を名指しせよ」の根拠。

### 3-2. プロキシ経路で AbortSignal が効かない 【消すな・構造的制約】

`voicevoxClient.js:58, :86`。`chrome.runtime.sendMessage` 越しに AbortSignal は渡せない。
「直す」のではなく、輸送層のヘッダに **「渡らない・渡せない」と明記して温存**する。

### 3-3. `forceOn:true`（会場が保存値を無視してON試行）【裏取りまで温存】

`venueBar.js:2953`。自動再生解錠の事情がある可能性。**削る前に3つ確認**:
1. `git log -S "forceOn" -- src/` で導入コミットの動機を読む
2. 自動再生解錠（ユーザージェスチャ文脈）との関係
3. 削った状態で会場の自動再生が解錠されるか実機確認

→ Phase 3-② は**調査のみの版**にする。

### 3-4. キュー上限 動的 vs 8固定 【値を統一するな】

統合は「ポリシー表から注入する形」まで。**初期値は現状のまま**
（会場=動的 / コメビュ=8固定 `comeview-entry.js:828-832`）。値の統一は実機観察後の別版。

## 4. 退行検知の3層（会議の結論）

| 層 | 手段 | いつ走る | 検知対象 |
|---|---|---|---|
| **S1** 契約テスト | vitest（入出力表） | **毎版**・pre-push | 純粋関数の移設ミス・値域のズレ |
| **S2** 既存計器 | 状態速報（v1328 / v1330 / v1331） | ユーザーの実機コピペ | 配線切れ・storage退行 |
| **S3** 手動スモーク | 下記3分手順 | **L1〜L3を触った版のみ** | 「鳴らない」そのもの |

★**計器の新設は原則0**。今日入れた3つを退行判定器として転用する。
 [[instrument-spiral-25-versions]]（計器を2版続けて入れたら止まる）を、
 **そもそも計器版を作らない**ことで回避する。
 例外は Phase 2 の新旧キー並走突合の1版のみ。

### 4-1. S3 手動スモーク手順（3分・これが正本）


## 5. ★エラー経路が退行検知の要（会議の最重要指摘）

> **この構造の退行はエラー経路でしか発現しない。正常系だけの契約テストは緑のまま壊れる。**

移設ミスがあっても**正常時は鳴る**ので、テストが緑のまま出荷される。
したがって契約テストには **失敗経路の全値域** を必ず含める:

| 分類器 | 全値域（リテラルで表に書き写す） |
|---|---|
| `classifyVoicevoxAliveFailure`（`voicevoxClient.js:195-208`） | `no-fetch` / `timeout` / `refused` / `http-error` / `''` |
| `classifyVoiceSynthFailureReason`（`voiceSynthFailureReason.js:64-96`） | `timeout` / `unreachable` / `query_http` / `query_body` / `synth_http` / `synth_body` / `unknown` |

★新関数が旧関数を内部で呼ぶ形にすると**恒真**になる（[[comparison-needs-two-origins]]）。
 旧トークン表は**テストにリテラルで書き写す**こと。

## 6. 移設版の DoD（1版=1変更を守るための4点・全部機械確認可能）

**判定式**: 「**状態速報のフィールド集合と、鳴る/鳴らないの条件が、前版と1ビットも変わらない版**」= 移設版。

1. 契約テスト全緑（新旧突合を含む）
2. `git diff --numstat` で行数爆発なし
   （★LF→CRLF事故は行数で即バレする。**テストが赤いときまず差分の行数を見る**）
3. 状態速報のフィールド集合が前版と同一
4. 触った層が L0 のみなら S3 スキップ可。**L1〜L3 なら S3 実施**

★changelog のプレフィックスで宣言する: `refactor(voice)` = **挙動差ゼロ宣言** /
 `fix(voice)` `feat(voice)` = 挙動変更。

★**片肺の解消は「挙動変更」**。移設版に混ぜたくなるのが最大の敵。
 原則: **先に移設で1実装に畳む → 片肺は畳んだ瞬間に自動解消される**。
 畳む前の個別移植（v1329型）は二重実装を延命させるだけ。

★**Codexが報告した注意点**: `publishVoiceDiag()` には**3秒のmin-gap**があり、

 実害は「一度失敗してすぐ成功したとき古い理由が最大3秒残る」程度だが、
 読むときはこの間引きを念頭に置くこと（化石値で2回騙された日なので）。

## 7. 次の1版（次セッションはここから）

**v0.1.1332: `src/lib/voiceFailureTaxonomy.js` 新設 + 契約テスト。配線ゼロ（どこからもimportしない）。**

設計の中心: A-2 の値域不一致の真因は、両分類器が**「原因(cause)」と「段階(stage)」を
1トークンに焼き込んでいた**こと（`refused` vs `unreachable` は同じ cause の別名、
`query_http` vs `synth_http` は stage 違いの同 cause）。**2軸に分解する**:

```
cause ∈ { down, timeout, http, payload, not_wired, unknown }
stage ∈ { probe, query, synth }

fromAliveFailure(token) : no-fetch→not_wired / timeout→timeout / refused→down / http-error→http
fromSynthFailure(token) : unreachable→down / query_http→{http,query} / synth_body→{payload,synth} …
canonicalLabel({cause,stage}) : 日本語ラベル（voiceLoadingState.js の文言の将来の正本）
```

**この版でやらないこと**（1つでもやったら 1版=1変更 違反）:
- 既存2関数の書き換え
- 文言の変更
- どこかへの import 追加
