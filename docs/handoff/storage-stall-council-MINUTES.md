## 1. 確定した事実(実測・すべて chrome-devtools)

### (a) storage の規模と読みのコスト

| 操作 | 実測 |
|---|---|
| `get(null)` 全件読み(20.7MB) | **1,157ms** |
| `getKeys()` キー名だけ(152キー) | **81ms** |
| `getBytesInUse(null)` | 66ms |
| 旗4本の `get([4キー])` | **95ms** |

### (b) migration 4本の実像

- **初回1回だけ 3,570ms**。以後は旗が立ち95msで終わる(＝毎回2.5秒止まるわけではない)
- 掃除対象は v0.1.172〜200(**2026-05-08**追加)の汚染。真因(スクレイパのバグ)は当時修正済み
- 書き込み側に**恒久フィルタが配線済み**(`src/lib/persistableCommentRow.js:32-36` →
  `content-entry.js:11913`)＝**新規汚染は入らない**
- 現代データ24,901行に判定を適用 → **汚染0件**
- ★ただし判定ロジック自体は生きている(汚染7行を注入したら6行検出・正常行1件は温存)
  ＝「0件」はデータ側の事実であり、判定の故障ではない
- ★コメント記録に **retention が無い**(古い `nls_comments_<lv>` が残り続ける)
  ＝2026-05以前の記録が残っている可能性は**否定できない**

### (c) ★★真犯人の所在(会議後に司令塔が特定)

**書き込み経路にチャンク化されない分岐が残っている。**

`content-entry.js:12476`:
```js
chrome.storage.local.set({
  ...(chunkMode ? chunkCommentWrite.writes : { [key]: next }),  // ★falseなら巨大配列を丸ごと
```

`chunkMode = liveChunkMigrated && !!liveChunkIndex` (12151行)。
そして **10980行の分岐**:
```js
} else if (metaBag[chunkMigratedKey(lid)] === true) {
  // フラグだけ立つがインデックス破損＝安全側で従来 main 運用に戻す（チャンク無効）
  main = ...;   // ★ liveChunkMigrated を true にしない = false のまま
}
```
＝**インデックスが壊れた配信は、以後ずっと全件書き戻しになる**。

実測(24,000件の配列):
| 書き方 | 所要(5回) | 停止 |
|---|---|---|
| 丸ごと書き戻し | 2,522ms | 410ms |
| 末尾チャンクだけ | **371ms** | **63ms** |
＝**6.8倍**。

★これは v0.1.769 が「storage stall spiral の根治」として塞いだのと**同じ穴**。
当時は timeout 経路を塞いだが(11019行で `liveChunkMigrated = true` に倒す)、
**インデックス破損の経路(10980行)は塞がれていない**。
＝[[fail-open-recurs-under-new-names-2026-08-12]] の**6件目**(通す条件が別名で残っていた)。

### (d) 観測手段の欠落

- 旗4本は**速報にも status にも一切出ていない**(出現は定義と changelog のみ)
  ＝実機の状態を知る手段が無い
- `chunkMode` が今どちらかも速報に出ていない ＝**真犯人が計器の死角にいる**
- `migrateClearStaleSelfPostedOnce`(get(null)を使うとテストが名指し)は**src に本体が無い**(残骸)

## 2. 会議の結論と、司令塔の修正

### 主査(Fable)の推奨: migration 4本を削除
### 反証役の推奨: 実装ゼロで旗の状態を先に観測

### ★司令塔の判断(両者を統合し、(c)の発見を加える)

**次の1版は「計器1つ + 穴1つ」に絞る。migration の削除は【この版ではやらない】。**

理由:
1. migration は**初回1回3,570ms**であり、毎回の凍結を説明しない(実測で否定済み)
   → 削除しても症状は消えない。**症状に効かない変更を9版目にしない**
2. 真犯人候補は (c) の**全件書き戻し**。こちらは**毎回**効き、6.8倍の差がある
3. しかし「実機が (c) の状態か」も**まだ証拠が無い**。同じ過ちを繰り返さない
   → **まず観測**。ただし前回のように「計器だけの版」で終わらせない。
     (c) は**コードで確定したfail-open**なので、観測と同時に塞いでよい
     (会議 Q5 の「コードで確定済みのバグは推測で版を重ねるに当たらない」に従う)

## 4. 「直った」の判定(2レジーム・前回を踏襲)

- **レジームA(検証ハーネス)**: 20.7MB fixture で、書き込みを回したときの
  イベントループ停止が **<300ms**(現状1,035ms)。★旧コードで1,035msが**再現することも**
  同じハーネスで確認してから緑を主張する([[prove-fix-by-replaying-old-code-2026-08-09]])
- **レジームB(実機)**: 速報に `chunkMode` が出ること + 最大タイマー遅延 **<1,000ms**
  ★遅延が1,000ms以上のままなら**この版を「外れ」と呼ばない**。
    「chunkMode がどちらか」という新情報を得た＝次の一手が決まる
