## 1. ★真因の確定(ユーザーが既に送った速報だけで証明・新版不要)

```
観測格子(sidepanel-entry.js:519)のうち 0〜12000ms の点数 = 16
速報が報告した「窓0x0」の点数                          = 16   ← 一致
予定12000ms のサンプルの実発火時刻                      = 14574ms
────────────────────────────────────────────
イベントループ遅延 = 14574 - 12000 = 2,574ms
```

**Chrome のパネル滑り出しではタイマーは遅れない。**
＝**拡張ページのメインスレッドが約2.6秒止まっていた**。

さらに `iframe load + 50ms` のサンプルが 14778ms＝**iframe の load が14.6秒まで完了していない**。

同じ速報の別の数字が背景を示す:
```
更新所要 7,883ms (lives(stale) 3301ms / fastDiagLite 1754ms) / 保存 3,489件
```
拡張の全ページ(sidepanel / popup iframe / status / live-view)は
**同一プロセス・同一メインスレッド**を共有する。storage の巨大な読みは読み手の文書のスレッドで走る。

### ★過去の結論の適用範囲を取り違えていた

正本メモリ [[sidepanel-black-is-zero-area-window-2026-08-12]] は
「窓0x0＝Chromeの滑り出し＝拡張から触れない＝**版を重ねない**」と結論している。
**滑り出し分(数百ms)については今も正しい。**
しかし今回はその上に**別現象(スレッド停止)が12秒以上乗っている**。
同メモリ自身が「**窓が面積を持ってからの遅れは引き続き詰める価値がある**」と但し書きしており、
**今回はその『詰める側』に属する**。＝結論の例外ではなく、私の**適用範囲の取り違え**。

## 2. 会議の回答(要点)

### Q1. 窓0x0が20倍に延びた原因 / 過去の結論は成立するか
**成立しない。** 第一現象はメインスレッド停止で、窓0x0・幕残留・シェード残留は**すべて下流**。
確かめ方は3段(安い順):
- (a) **新版不要**: 保存済み `sizeSeries` の各 t と予定値を突合 → **§1で実施済み・確定**
- (b) 予定時刻 `sched` を1フィールド足し「最大タイマー遅延=Xms」を速報に1行 → **触れる/触れないの分岐そのもの**
- (c) chrome-devtools で storage 量だけ変えて面積確定時刻を比較 → **因果**が確定する

### Q2. cloak 再付与の直し方
**再付与機構は消さない**(初回チラつき防止の設計が壊れる)。
`cloak-failsafe.js` が外すときにマーカー(`window.__nlPopupCloakFailsafeFired`)を立て、
`ensurePopupPrimaryCloakedBeforeFirstReveal` がそれを見て `revealPopupPrimaryOnce()` へ倒す。
＝[[shared-knowledge-is-not-shared-judgment-2026-08-10]]:**判定を共有して初めて止まる**。
★ただしこれが効くのは**イベントループが生きている場合**(今朝の48.8秒型)。
凍結型では JS が走らないので効かない。**「これで黒が消える」とは言わない。**

### Q3. シェードの起点問題(5秒待ってから2.5秒)
上限を「呼ばれた時刻からの相対」→**「初回可視からの絶対締切」**へ付け替える。
prewarm(画面外先読み)対策は「boot起点」でなく「**可視起点**」なら両立する。
★`dismissInlineShadeWhenDataReady` は再入時に既存タイマーを掃除しない穴があるので1行足す。
＝[[timer-delay-is-not-timer-origin-2026-08-12]] を**私が今日また踏んでいた**。

### Q4. ユーザーへの見せ方
- **窓0x0の間は1pxも描けない**(塗るピクセルが無い)＝「読み込み中」表示も**原理的に不可能**。ここに版を使わない。
- **面積が付いた後**は、シェード(クリーム地+キャラ)が静的HTML/CSSで既に存在し、**JSが死んでいても描画される**。
  ＝status.html で成功した「静的な読み込み中表示」と**同型のものが既にある**。追加UIは不要。
- 残る問題は「シェードの上に幕が乗る」時間で、Q2/Q3 がそれを短縮する。

### Q5. 優先順位
**測定の確定(§1・完了) → 修正版1つ(Q2+Q3+遅延注記) → 因果実験(c) → 飽和対策(別版)。**
Q2/Q3 は**コードで確定済みのバグ**なので「推測で版を重ねる」に当たらない。
**窓0x0そのもの(凍結型)には次版で手を付けない。**

## 4. 「直った」の機械的判定(★2レジームに分ける)

- **最大タイマー遅延 < 1000ms(健全)**: 幕は complete 到達後1500ms以内に解除 /
  シェードは初回可視+2500ms+500ms以内 / 「中身が出ていません(≥4000ms)」が**出ない**
- **最大タイマー遅延 ≥ 1000ms(凍結)**: 上の3条件で**合否を判定しない**(この版の守備範囲外)。
  合格条件は「遅延Xmsが速報に現れること」だけ。
  ★**凍結レジームで黒が残っても『この版は外れ』と呼ばない**(呼ぶと9版目の空振り連鎖に戻る)

## 5. やらないこと(Out of Scope)

- storage を軽くする対策 — **因果が未証明**。(c)の実験後に別版で
- 窓0x0を短くする直接の試み — 塗るピクセルが無い時間帯は不可侵
- 再付与機構の削除 — ガードで足りる。削除は初回チラつき防止を壊すリスクだけ増やす
- 白フラッシュ / diff-skip機構 — 結論済み・触らない
- 観測格子を細かくする — 必要なのは点の密度でなく**遅延の注記**。点を増やすのは計器のための計器
