### ★自己増殖する構造(これが7版効かなかった理由の下流)

1. データが多い → `get(null)` が遅い/失敗する
2. 失敗すると**旗が立たない**(旗を立てるのが読みの後だから)
3. → 次にパネルを開くとまた4本走る
4. → 記録は増え続けるので**さらに遅くなる**

＝一度ハマると**永久に抜けられない**。ユーザーの実機はこの状態の可能性が高い。

## 4. ★会議への注文(ラテラルシンキング指定)

ユーザーの指定: **「ラテラルシンキングで思考して最高の結果を得る」**

垂直思考(与えられた枠の中で最適化)ではなく、**枠そのものを疑う**視点を必ず入れること:

- 「migrationを速くする」ではなく「**migrationを無くす**」道はないか
- 「全件読みを速くする」ではなく「**読まない**」道はないか
- 「凍結を短くする」ではなく「**凍結してもユーザーが困らない**」道はないか
- 「storageを軽くする」ではなく「**重いまま平気**にする」道はないか
- そもそも**症状(黒画面)と真因(凍結)を切り離す**道はないか
  ＝メインスレッドが止まっても画面が黒くならない構造はありうるか
- 他分野の解法の転用(DBのマイグレーション運用 / OSのページング / ゲームのLOD /
  CDNのキャッシュ無効化 / 医療のトリアージ 等)から借りられる型はないか

### 判定基準(ユーザー確定・ここを外すと価値が無い)

- **計器の価値は「真因に導いたか」だけ**。読んでも直せないなら価値が低い・誤誘導なら負
- **推測で版を重ねない**(黒画面で7版外した実績がある)
- **両方向を実機で確認するまで完了と言わない**(正常時に出ない/壊したら出る)
- **fail-open は名前を変えて再発する**(5件実績あり)。通す条件そのものを狭める

## 4.5 ★会議中に司令塔が追加で実測したこと(会議はこれも踏まえること)

### (a) キー一覧は全件読みなしで取れる = 案2は成立する

```
chrome.storage.local.getKeys()        →  81ms で152キー名(値は読まない)
chrome.storage.local.getBytesInUse()  →  66ms で総容量(28.48MB)
chrome.storage.local.get(null)        → 1,157ms(全件読み)
```

`getKeys()` は Chrome 130+。実機は Chrome 151。**14倍速くキー名だけ取れる**。

### (b) ★この修正パターンは【既にこのリポに在る】

`src/extension/content-entry.js:18250` `readPrunableStorageBagCheap()` が
**まさにこの形**で実装済み(v0.1.419):

```
① getKeys() でキー名だけ取得(無ければ get(null) に fallback)
② prefix で対象キーだけに絞る(純関数 pickPrunableStorageKeys・テスト付)
③ その分だけ get([...keys]) で値を読む  ← 巨大配列を読まない
```

＝**記録エンジン側では既に解決済みの問題**が、popup-entry.js の migration 4本には
**適用されていない**。新しい発明ではなく【既存資産の横展開】で直る。
★これは「作り直さず薄く束ねる」という本リポの原則にも合致する。

### (c) 修正案の実測(掃除の実務込み)

| | 所要 | イベントループ停止 |
|---|---|---|
| 現状: `get(null)`×4本 | 4,197ms | 556ms |
| 修正案: getKeys→対象のみ→**1件ずつ**+毎回 `setTimeout(0)` で譲る | 756ms | **156ms** |

★「1件ずつ読んで毎回イベントループへ譲る」を入れると、
**migration が走っている最中でもパネルは描画を続けられる**(停止156ms=人が気づかない)。
＝「速くする」だけでなく「**止めない**」形にできる。

## 4.6 ★★会議中の追加調査で、問題の性質が変わった(必読)

### (d) 4本の migration が掃除しているのは【3ヶ月以上前の汚染】だけ

実コードとgit履歴で確認:

| migration | 何を消すか | 真因fix | 追加日 |
|---|---|---|---|
| GiftSystemMessages | v0.1.172〜194 のギフトシステム行混入 | v0.1.195 | 2026-05-08 |
| RecommendedLivePollution v1/v2 | v0.1.199以前の「おすすめ生放送」DOM混入 | v0.1.200 | 2026-05-08 |
| RecommendedUserChipPollution | v0.1.27x の user チップ混入 | DOMガード | 2026-05-08 |

**4本とも真因(スクレイパのバグ)は当時すでに直っている。**
＝それ以降に書かれた記録は**構造的に汚染され得ない**。現在 v0.1.1381(3ヶ月半後)。

### (e) ★現代のデータでは「何も消さずに終わる」

実測(私が作った 24,901行 / 2配信の fixture で判定ロジックを適用):

```
走査した行数     = 24,901
ギフト混入       = 0件
おすすめ生放送混入 = 0件
userチップ混入   = 0件
```

＝**20MBを読んで、何も消さずに終わる**。これが毎回のパネル起動で4回。

★ただし注意: コメント記録に**保持期間(retention)が無い**ことも確認した
(古い配信の `nls_comments_<lv>` は消えずに残り続ける=20MB超の主因でもある)。
よって「3ヶ月前の汚染データがまだ残っている可能性」は**否定できない**。
★「消す」判断をするなら、この点への手当て(1回だけ走らせて終わりにする等)が要る。

### (f) 問題の再定義(ラテラル思考の材料)

当初の問い: 「全件読みをどう速くするか」
　　↓
実測後の問い: 「**もう何も消さない掃除を、なぜ毎回走らせているのか**」

＝これは性能問題ではなく【**役目を終えた処理の退役計画**】の問題かもしれない。
会議はこの再定義を踏まえて判断すること。ただし (e) の但し書き
(retention が無いので古い汚染が残っている可能性)を無視しないこと。

### (g) ★「汚染0件」は判定が壊れているせいではない(自分の主張への反証を先に実施)

§4.6(e) の「汚染0件」は**私が作った fixture で測っただけ**なので証拠として弱い。
そこで当時の汚染データを**意図的に作って**判定に通した:

```
投入: 7行(35分経過 / LIVE / 2時間前 / ギフト文言 / 数値ID / u/ID / ふつうのコメント)
検出: ギフト1 + おすすめ生放送3 + userチップ2 = 6行
温存: ふつうのコメント 1行  ← 誤検出なし
```

＝**判定ロジックは正しく効く**。「0件」はデータ側の事実であって、判定の故障ではない。

★したがって導かれる結論は「**migrationを消してよい**」ではない:
- 判定は生きている＝**古い記録が残っていれば実際に仕事をする**
- コメント記録に retention が無い＝2026-05以前の記録が残っている**可能性は実在**する
- ＝**単純な削除は危険**。「1回だけ確実に走らせて、以後は走らせない」形が要る

### (h) ★★会議後の検証で【司令塔の主張が2つ崩れた】(重要・記録として残す)

反証役の指摘を受けて実測し直した結果:

**崩れた主張① 「旗が立たず永久に再試行する自己増殖」= 誤り**

```
旗を4本消して migration 4本を実際に走らせた
→ 結果: done×4 / 所要3,570ms / ★旗は4本とも立った
```
`get(null)` は遅いだけで例外を投げない。＝**旗は立つ。永久ループにはならない**。
反証役が正しく、司令塔(私)が誤っていた。§0 の「自己増殖」の記述は**取り下げる**。
migration のコストは**初回1回だけの3,570ms**。

**崩れた主張② 「migration が凍結の主犯」= 不十分**

```
旗を【立てた】状態(=migrationは何もしない)で、記録エンジンの書き込みだけを再現
→ 旗チェックの所要        = 95ms(無視できる)
→ ★イベントループ最大停止 = 1,035ms  ← 🔴凍結レジームに入る
```
＝**旗が立っていても凍結する**。migration を消しても凍結は残る。
反証役の「更新所要7,883msの内訳が説明されていない」という指摘が正しかった。
