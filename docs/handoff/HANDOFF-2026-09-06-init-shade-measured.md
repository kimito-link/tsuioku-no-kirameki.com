# 初回ロードの幕（黒く見える件）— 実測記録

> ★ユーザー指摘:「黒く画面をおおうのは解決すべきだが、なおるまで
> z-indexの重なり順でコンテンツが見えないのを回避できるかも」
> ★**推測で直さず、先に測った**（84版の教訓）。

---

## ★実測（2026-09-06・Playwright・rAFごとに440フレーム観測）

```
中身が幕に覆われていた : 89ms 〜 ★1,486ms
完全不透明(opacity≥.99): 〜1,253ms
opacity 0 到達         : 1,503ms（★1,269msから220msかけて滑らかに）
幕がDOMから消えた      : ★8秒観測しても消えない
```

### ★分かったこと1: 幕は「黒く」ない
`popup.html:128`: `background: linear-gradient(180deg, var(--nl-bg, #f6fff8), ...)`
★**クリーム色**。★黒く見えるのは色ではなく **中身を完全に覆っているから**。
　`popup.html:236-238` のコメントが既にそう書いている:
> 幕は暗色ではないが、**中身を完全に覆う**のでダーク環境では暗く見え、
> **いずれにせよ何も見えない**

### ★分かったこと2: 幕は正常に解除されている（DOMに残るのは無害）
```
89〜1,002ms : opacity=1 / pointer-events=auto  ← 覆っている
1,503ms〜   : opacity=0 / pointer-events=none  ← ★害はない
```
★220msかけて滑らかに消えている＝`transition: opacity 220ms`
　⟹ ★**CSS保険(5s)ではなく JS が `--done` を付けた**＝正常な経路。
★DOMに残り続けるが `pointer-events:none` なので**消す必要はない**。

### ★★分かったこと3: 真因は「解除の起点が遅い」
```
JS の上限   : INLINE_SHADE_DATA_FALLBACK_MS = 900ms (popup-entry.js:18975)
理論値      : 幕の出現 89ms + 900ms = 989ms
実測        : 1,253ms
★差         : 264ms
```
★`arm()`（締切の起点）を呼ぶのは **`popup-entry.js:22594`**
★総行数 22,654 に対して **100%地点＝ファイルの末尾**。

⟹ ★**1.4MBのバンドルをパースし終えるまで、900msの計測すら始まらない。**
　★264ms はそのパース時間。

## ★ユーザー提案（z-indexで回避）の評価

★**効かない。** 理由:
- 幕は `z-index:99999` で `inset:0`。★下に潜らせても**中身は覆われたまま**
- ★中身側の z-index を上げると、幕の目的（要素のチラ見え・ガタつきを隠す）が完全に消える
- ★このリポは「私が足した幕が黒の正体だった」という前科がある。
  ★**z-index をいじる方向は、同じ型の事故を作りやすい**

★**代わりに効くのは「起点を早くする」**（真因に直接効く）。

# ★★ユーザー指摘（2026-09-06）: 「コンポーネント化したときに、問題の切り分けで解決できるはずでは？」

★**そのとおり。実測で裏付けられた。**

## ★幕の264msは「巨大な1ファイル」が直接生んでいる

```
今の構造:
  popup-entry.js（22,654行の1ファイル）
    :1036  INLINE_MODE を定義
    ...    ★22,000行のパース
    :22594 arm() ← ここまで来ないと900msの計測が始まらない
  ⟹ 起点が【ファイルの物理的な位置】に縛られている

コンポーネント化された世界:
  createInitShadeController({ document, timers }).start()
  ⟹ ★呼ばれた瞬間に締切が始まる。ファイルのどこに書いてあるかは関係ない
```

## ★★幕だけの問題ではなかった（実測）

末尾100行で起動されているもの＝**7つ**:
```
initPopup()                             ← 本体の起動
armInlineShadeDeadlineOnFirstVisible()  ← ★幕の締切（今回の264ms）
startInitShadeCharCycle()               ← 幕のアニメ
dismissInitialLoadShade()               ← 幕の解除
revealPopupPrimaryOnce()                ← 表示
finalRevealFallback()                   ← 保険
mountOuenBanner()                       ← バナー
```
★**全部が「22,000行パースし終えるまで待つ」**。

## ★今日追っていた症状との対応（★切り分けの問題だった）

| 症状 | 構造的な原因 | コンポーネント化で解けるか |
|---|---|---|
| ★幕が1.4秒 | `arm()` が末尾(22594)＝100%地点 | ★**解ける**（controller の start() が起点になる） |
| ★描き直しの理由が `unknown` 61% | `_refreshReasonTag` が**モジュール直下の let**(:1986)を、★`safeRefresh()` **22箇所**が共有 | ★**解ける**（各 controller が自分の理由を持てば原理的に unknown が消える） |
| 表示遅延253秒 | 「iframeのイベントループが詰まっている」＝1スレッドに全部載っている | ★**部分的に解ける**（所有者が分かれれば、どの処理が詰めているか特定できる） |
| サイドパネルの縞 | 環境差（Playwrightで再現せず） | ★**解けない**（別要因） |

★★つまり **今日1日追っていた症状の多くは「切り分けができない」ことの症状**だった。
★個別に直すより、コンポーネント化の方が**根に効く**。

## ★ただし順序は変えない

★それでも Codex の推奨順（`popupFrameSettingsController` から）は変えない。理由:
- ★幕の周辺（`initShade` 系7つ）は**起動シーケンスの中核**で、壊すと**何も表示されなくなる**
- ★`popupFrameSettingsController` は**表示の枠だけ**＝壊れても記録・取得は無事
- ★このリポの掟「記録系はデータ欠落リスクが最大なので最後」と同じ思想

⟹ ★幕は「コンポーネント化が進めば自然に解ける」ものとして**記録に残す**。
　★今すぐ `arm()` を移動させる小手先の修正は**しない**（264msのために起動順を触るリスクが高い）。
