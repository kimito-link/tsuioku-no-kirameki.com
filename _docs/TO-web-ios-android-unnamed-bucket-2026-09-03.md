## 1. 何が起きたか（1文）

**症状を数値で測る計器は正しく動いていた。しかし「原因を名指しする」側に穴があり、
読んだ理由タグを消していなかったため、無関係な経路の描き直しに前の理由が付いて

## 3. 一般化（そちらに効く形）

### 型の名前
**「その他」に落ちた観測は、消えるのではなく“最多の理由”として現れる。**

### なぜ気づけないか（普通のバグと違う点）
- エラーが出ない
- 計器は動いている（総数は正しい）
- 出力も出る（それらしい名前で）
- ★**だから「計器が壊れている」と誰も疑わない**

「計器が0件」「計器が例外」は気づけます。**この型だけが静かに嘘をつく。**

### そちらで該当しそうな構造（当てずっぽうではなく形で）
1. **`default:` / `else` / `catch` に落ちた件数を「その他」でまとめている集計**
   → その他が最多になったとき、それは「その他が原因」ではなく「**分類していない**」
2. **ゲートの `skip` / `n/a` / `not-applicable`**
   → 「対象外」と「測れなかった」を同じ値で表していないか
   （★追憶は3値の終了コードで分けています: 0=合格 / 1=赤 / **2=測れなかった**）
3. ★**状態を持つ変数に「理由」「発生源」を置き、読んだあと消していない箇所**
   → 今回の実体はこれ。**次に別経路が来たとき前の値が残る**

### ★対策の方針（追憶で採ったもの）
**「その他」を細分化して名前を増やすのは対策にならない。**
新しい呼び出し箇所が増えたらまた「その他」に落ちるので、同じ穴が再生産されます。

★採ったのは2つだけ:
1. **読んだら消す**（状態を持ち越さない）
2. **消していることを機械で見張る**（`repaintLoopGuard.wiring.test.js` に1件追加）
   ★ただし対象は「1つの関数の呼び出し規約」に限定。
   全箇所に検査を広げると15件の偽陽性が出て形骸化します
   （タグ不要な経路にタグを強制することになるため）。

★**手で登録表を書く案は採りませんでした。**
　22箇所に手でタグを配る案は、`registry_written_by_hand_always_has_holes` の型そのもので、
　しかも max-lines ラチェットで物理的に不可能でした。

## 4. ★こちらが間違えていたこと（同じ轍を踏まないために）

★当初この手紙は「16箇所が unknown に落ちている」という内容で書こうとしていました。
　**それは誤りでした。** 実際に22箇所を1つずつ読んだ結果:
- 自動経路4つは**既に全部タグ付き**
- `storage_changed` は**引き金キー名付きに格上げ済み**（v0.1.1340）
- 残り15箇所は**クリック由来で暴走しえない**（人間の操作なので毎秒何十回も起きない）

⟹ ★**穴は1つだけ**でした。「穴が大きい」と思い込んだまま送っていたら、
　そちらに不要な調査をさせるところでした。

★同じ日、症状の数字も間違えていました。`repaintReasonCensus.js:5` の「77回/件」を
　現在値として2回報告しましたが、実際は**2026-08-04 の履歴記述**（なぜこの計器が要るかの説明文）で、
　最新実測は **7.7回/件**（v0.1.1484・2026-08-23）でした。
　★**コメント内の数字を引用するときは、日付とその後の修正コミットを必ず確認する**
　——これが今回いちばん高くついた教訓です。
